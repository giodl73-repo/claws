LobsterClaw gives Lobster an immutable, testable OpenClaw release boundary

Why this exists
Lobster currently carries Microsoft-required OpenClaw changes as a patch queue. Replaying that queue only while building a container made the source identity, patch provenance, release qualification, rollback, and retirement lifecycle too tightly coupled to one Docker build. It was difficult to answer a basic operational question with one durable artifact: exactly which OpenClaw source are we shipping?

The mission
LobsterClaw is the private distribution and control plane for that answer: one signed OpenClaw base, one ordered ledger of byte-identical Lobster patches, and one immutable generated source tree that CI, image builds, support policy, and rollback can all reference.

Immutable generations, not a long-lived fork
Each Git commit and generation tag is a permanent release identity. The manifest records every patch's source commit, SHA-256, owner, reason, validation, repair lineage, and deletion condition. Patches are retained, rebuilt, or removed deliberately as OpenClaw evolves; published tags never move.

Independent release roles
LobsterClaw lets Lobster validate more than one supported OpenClaw line without conflating them. Today that means a 2026.5.28 fallback/Active lineage and a strict-parity 2026.6.33 Candidate lineage, each independently reconstructable and eligible for controlled promotion or rollback.

Qualification of the source we will actually ship
The generated tree is materialized without LobsterClaw metadata and run through OpenClaw's release-relevant checks: Linux checks, build/package, full tests, Node 22 compatibility, and Windows. Patch-focused acceptance and dependency evidence remain separate, explicit proof layers.

No governance hand-wave
Lobster still owns image construction, live provider and channel validation, deployment assignment, and rollback. LobsterClaw does not automatically promote a release; it supplies the immutable source and evidence that Lobster's deployment process consumes.
