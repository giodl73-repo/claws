LobsterClaw: qualify patched releases once, then let Lobster promote them

Why this exists
Omar, your 2026.6.33 Candidate dogfooding is exactly the workflow LobsterClaw is meant to support. Instead of Lobster rebuilding OpenClaw by replaying patches inside Docker, LobsterClaw produces an immutable, qualified source generation for each OpenClaw release that Lobster may need to deploy or roll back to.

The mission is simple: LobsterClaw owns patched-release construction and qualification; Lobster owns deployment policy and decides which qualified generation is Candidate, Active, rollback, or retired.

The operating rule

1. Patch every supported release in LobsterClaw first.
If a behavior must exist across releases, add or repair the patch on every release branch Lobster still needs to run. Today those lines are 2026.5.28 and 2026.6.33.

2. Qualify the exact patched release.
Each release reconstructs its ordered patch tree, tests the canonical source without repository metadata, and publishes an immutable generation. Qualification is release-scoped, never Active/Candidate-label-scoped.

3. Advance Lobster only after qualification.
Lobster updates its pinned LobsterClaw generations and runs both release contracts. No Docker-time patch replay, no mutable release pointer, and no role decision hidden inside LobsterClaw.
