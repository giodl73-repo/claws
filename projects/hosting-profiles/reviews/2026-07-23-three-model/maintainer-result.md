**Findings**
- `Blocking profiles only`: PR2 is not opt-in. In `openclaw-107765-rebase`, `src/gateway/server.impl.ts:1314-1348` always resolves and passes `activation`, and `src/readiness/conditions.ts:157-189` always adds `RuntimeActivationIdentified` plus top-level `activation` whenever the Gateway runs, even with no selected hosting profile. RFC 0023 says profile selection is opt-in and unprofiled installs keep the universal baseline: `openclaw-rfcs-0023-refresh/rfcs/0023/hosting-profile-v1-spec.md:62-71`, `openclaw-rfcs-0023-refresh/rfcs/0023-standard-hosting-profiles.md:171-205`. This will surprise existing `/readyz`, `/healthz`, and `status --json` consumers because PR2 changes their payload and condition set without any profile config.

- `Blocking profiles only`: the public protocol/schema was not regenerated for that new payload. In `openclaw-107765-rebase`, runtime readiness now emits `activation` from `src/readiness/conditions.ts:29-38` and `src/readiness/conditions.ts:184-189`, but `packages/gateway-protocol/src/schema/snapshot.ts:64-69` still defines the canonical readiness object as only `ready`, `conditions`, `failures`, and `advisories`. `docs/cli/ready.md:25` repeats the old four-field claim. That is a concrete generated-file/doc mismatch for validators and generated clients.

- `Blocking profiles only`: the machine-readable profile-reporting contract from RFC 0023 is not implemented. In `openclaw-107765-rebase`, `src/hosting/profiles.ts:69-84` has sane precedence (`override -> env -> config`) but discards the selection source; `src/hosting/profiles.ts:230-253` exposes only a human `ProfileSelected` condition; `src/hosting/runtime-activation.ts:9-12` and `src/readiness/conditions.ts:29-38` only carry `runtimeId` and `incarnationId`. RFC 0023 expects readiness/health/status to report effective profile, selection source, and the fuller activation summary: `openclaw-rfcs-0023-refresh/rfcs/0023-standard-hosting-profiles.md:201-232`. As shipped here, hosts and control planes cannot reliably inspect the selected profile from JSON.

- `Blocking readiness`: plugin readiness validation does not enforce the v1 sidecar contract. In `openclaw-104018-rebase`, `src/readiness/plugin-readiness.ts:43-69` accepts any non-empty `reason` and `message` and forwards them unchanged. RFC 0018 requires a constrained reason format, a bounded/redacted message, and `CriterionInvalidResult` on invalid provider output: `openclaw-rfcs-0018-refresh/rfcs/0018/readiness-v1-spec.md:107-112`. That leaves the new SDK surface under-specified at runtime and allows invalid plugin output onto the canonical readiness API.

- `Blocking readiness`: the baseline workspace reason set already diverges from the RFC. In `openclaw-104018-rebase`, `src/readiness/workspace.ts:39-47` returns `WorkspaceMissing` for `ENOENT`. RFC 0018 only allows `WorkspaceStorageFull`, `WorkspaceNotWritable`, `WorkspaceProbeFailed`, `WorkspaceProbeTimedOut`, and `WorkspaceNotChecked`: `openclaw-rfcs-0018-refresh/rfcs/0018/readiness-v1-spec.md:153-161`. Stable reason strings are public API here; adding an unspecced one before landing creates immediate contract drift.

- `Can follow later, but not if you want to claim sidecar conformance on merge`: deterministic condition ordering is not implemented. In `openclaw-107765-rebase`, `src/gateway/server.impl.ts:1323-1348` feeds profile conditions first and selected criteria after that, while `src/readiness/conditions.ts:150-179` appends `RuntimeActivationIdentified` after both. RFC ordering is explicit: baseline conditions first, then `ProfileSelected`, then `RuntimeActivationIdentified`, then `WorkspaceWritable`, then the remaining profile-owned conditions in profile order: `openclaw-rfcs-0018-refresh/rfcs/0018/readiness-v1-spec.md:134-144`, `openclaw-rfcs-0023-refresh/rfcs/0023/hosting-profile-v1-spec.md:75-83`. Today a container profile will report a different `conditions`/`failures` order than the spec promises.

- `Can follow later`: the SDK docs overclaim an enumeration surface I could not find in code. `openclaw-104018-rebase/docs/plugins/sdk-overview.md:239-243` says readiness descriptors are retained in the active Gateway-pinned provider catalog “for enumeration”, but the code I found only stores them in the in-memory registry and consumes them for evaluation: `src/plugins/registry-api.ts:227-228`, `src/plugins/registry-types.ts:526`, `src/readiness/selection.ts:60-86`. This should either be implemented or the docs trimmed before the SDK contract is advertised.

**Landing Shape**
The repository fit and naming are mostly good. `src/readiness/*`, `src/hosting/*`, `gateway.readiness`, `hosting.profile`, and `api.registerReadinessCriterion(...)` all sit in plausible owner boundaries, and the profile precedence model itself is straightforward in `openclaw-107765-rebase/src/hosting/profiles.ts:69-84` and `src/cli/gateway-cli/run.ts:713-729`.

The current two-PR sequence is not cleanly reviewable, though, because PR2 is not actually “profile-only”. It changes the canonical readiness payload, docs, schema, CLI surface, and release validation burden for unprofiled installs. It also adds a permanent blocking Docker lane in `openclaw-107765-rebase/package.json:1695`, `scripts/lib/docker-e2e-scenarios.mjs:435-440`, `.github/workflows/openclaw-release-checks.yml:902-903`, and `docs/reference/test.md:162`. That cost is defensible only after the public readiness/profile contract is stable and truly opt-in.

Recommended landing shape:
1. Fix PR1 first as the canonical readiness baseline: enforce provider-output validation, align workspace reasons, and either implement or explicitly relax the promised ordering contract.
2. Rework PR2 so unprofiled installations stay byte-compatible. If activation/profile reporting is intended to be global, move that decision into PR1 and update the base schema/docs there; otherwise gate it behind selected profiles.
3. In the profile PR, add machine-readable `profile` and `selectionSource` reporting plus the full activation summary promised by RFC 0023, then regenerate `packages/gateway-protocol` and any generated client/docs in the same change.
4. Keep the Docker hosting-profile lane only after that contract is settled.

I did not find an import-cycle or dead-export blocker in the touched modules. The blockers are contract and rollout shape, not module topology.

**Verdict**
Request changes.

I would not approve either the readiness landing as currently specified or the profile follow-up as a “profile-only” PR. The readiness baseline needs spec-tightening, and the profile PR needs to stop changing unprofiled readiness consumers before it is reviewable as an independent second step.
