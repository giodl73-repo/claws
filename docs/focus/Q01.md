# Q12a: One CLI or two? And what naming surface does the user see?

**Priority**: High
**Status**: Proposed
**Owner**: giodl
**Resolves**: claws-only vs claws+clawops; config file naming (craft.json vs openclaw.json vs claws.json); directory naming (.craft/ vs .claws/ vs .openclaw/governance/)
**Blocks**: Q12 finalization, claws package design, SDK workspace-detector behavior
**Experiments**: a, b, c, d (4 total)

---

## Question

Q12 proposed two CLIs (claws + clawops) based on SU-01's verb-family separation test.
But a counterargument exists: OpenClaw users are often the **same person** doing workspace
and fleet work. A solo developer running 5 agents doesn't think "I'm switching to ops mode."

Separately, when `claws init` runs, what does the user see on disk? `.craft/` directories
and `craft.json` expose Craftworks internals. OpenClaw users don't know what Craftworks is.
The naming surface is the product's first impression.

These two questions are entangled: if one CLI, the directory should match the CLI name.
If OC-native, it should extend the existing `openclaw.json`. The naming decision constrains
the CLI decision and vice versa.

### Hypothesis

One CLI (`claws`) with `--fleet` scope flag for org-wide operations. OC-native naming:
extend `openclaw.json` with a `governance` section and store governance artifacts in
`.openclaw/governance/`. This keeps the entire experience native — no alien naming, no
second CLI, no "what is craft?" moment.

## Working Notes

### The One-CLI Argument

The strongest case:

```bash
claws build                              # workspace (always)
claws check                              # workspace (always)
claws scan                               # fleet (discovers workspaces)
claws broadcast                          # fleet (pushes policies)
claws snapshot save "v2"                 # workspace (default scope)
claws snapshot save "v2" --fleet         # fleet-wide (explicit)
claws rollback "v2"                      # workspace (safe default)
claws rollback "v2" --fleet --confirm    # fleet-wide (requires confirm)
```

**Safety model**: Default scope is always workspace (safe). `--fleet` escalates scope.
Destructive fleet operations (`rollback --fleet`, `kill --fleet`) require `--confirm`.
This makes scope explicit without requiring a second CLI.

**Simplicity win**: One CLI to install, one to learn, one `--help`. No collision redirects.
No "did you mean clawops?" No split-brain about where a command lives.

**The tradeoff**: Large enterprises with separate platform/security teams lose the
separation-of-concerns signal that two CLIs provide. A CISO typing `claws build` is
confusing. But a CISO probably uses a dashboard, not a CLI.

### The Naming Surface Argument

When an OpenClaw user runs `claws init`, what appears on disk?

**Option A (Craftworks-native)**:
```
my-agent/
  .craft/policies/soc2-baseline.yaml
  .craft/.track/audit-chain.jsonl
  .craft/cache/
  craft.json
```
Problem: "What is craft?" First-impression fail.

**Option B (OC-native — extend openclaw.json)**:
```
my-agent/
  openclaw.json           ← existing, extended with governance section
  .openclaw/
    governance/
      policies/soc2-baseline.yaml
      audit/chain.jsonl
      cache/
```
Feels native. Governance lives alongside OC config. But: cross-compilation to Cursor/Claude
Code would also write to `.openclaw/`? That's confusing — Cursor output in an OC directory.

**Option C (Product-native)**:
```
my-agent/
  claws.json
  .claws/
    policies/soc2-baseline.yaml
    audit/chain.jsonl
    cache/
```
Ties to the tool name. Clear brand. But: if the tool gets renamed, directories are wrong.
And `.claws/` next to `.openclaw/` is two dot-directories for one agent.

**Option D (Generic)**:
```
my-agent/
  .governance/
    policies/soc2-baseline.yaml
    audit/chain.jsonl
    cache/
  governance.json
```
Platform-agnostic. Works for OC, Claude Code, Cursor — any agent format. But: bland.
No brand association. Discoverable? "What is .governance/"

### The Entanglement

| CLI decision | Best naming match | Why |
|-------------|-------------------|-----|
| One CLI (claws) | Option C (.claws/) or B (.openclaw/) | Single product, single directory |
| Two CLIs (claws + clawops) | Option A (.craft/) or C (.claws/) | Split product, split responsibility |

If we go **one CLI + OC-native naming (B)**, the user's experience is:

```bash
$ npm install -g @craftworks/claws    # or: npx @craftworks/claws
$ cd my-openclaw-agent/
$ claws init --template soc2
  Detected OpenClaw workspace (SOUL.md, AGENTS.md)
  Extended openclaw.json with governance configuration
  Created .openclaw/governance/policies/soc2-baseline.yaml
  
$ claws check
  2 violations found in your OpenClaw workspace.
  
$ claws scan                          # fleet operation
  Found 12 OpenClaw workspaces in /home/user/agents/

$ claws broadcast --fleet             # explicit fleet scope
  Pushed soc2-baseline to 12 workspaces. 0 violations.
```

Zero "what is craft?" moments. Zero "what is clawops?" moments. One tool, one directory, native naming.

## Answer

**One CLI (`claws`), product-native naming (`claws.json` + `.claws/`), complementing the existing OpenClaw CLI.**

### Resolution

claws is a **governance compilation CLI** that sits alongside OpenClaw's runtime management CLI (`openclaw`). They operate on different layers with zero command overlap:

| | OpenClaw CLI (`openclaw`) | Governance CLI (`claws`) |
|--|--------------------------|---------------------------|
| **Purpose** | Runtime management | Governance compilation |
| **Commands** | gateway, agents, channels, memory, cron, skills | build, check, scan, broadcast, snapshot, comply |
| **Config** | `~/.openclaw/openclaw.json` (global) | `claws.json` (per-workspace) |
| **Directory** | `~/.openclaw/` (global state) | `.claws/` (per-workspace artifacts) |
| **Scope** | Single Gateway, single operator | Workspace + fleet (--fleet flag) |
| **Install** | `npm install -g openclaw` | `npm install -g @craftworks/claws` |

### Naming Surface

| Element | Name | Why |
|---------|------|-----|
| CLI binary | `claws` | "Claw compiler" — memorable, no collision with `openclaw` |
| Config file | `claws.json` | Per-workspace governance config. `openclaw.json` is global at `~/.openclaw/` — cannot extend it per-workspace |
| Artifact directory | `.claws/` | Product-native. OC workspaces are flat — no `.openclaw/` per-workspace to extend |
| Build output | `build/` | Standard, gitignored, platform-agnostic |
| Fleet scope | `--fleet` flag | Explicit escalation on ~6 scope-sensitive commands |

### claws.json Schema

```typescript
type ClawscConfig = {
  enabled: boolean;                          // master toggle
  template?: string;                         // "soc2" | "hipaa" | "eu-ai-act" | "minimal"
  trustTier?: 0 | 1 | 2 | 3 | 4;          // T0-T4, default T2
  policies?: string[];                       // paths to policy YAML files
  audit?: {
    enabled: boolean;
    chain?: string;                          // audit chain file path
    siem?: {
      format: "cef" | "json" | "syslog";
      endpoint?: string;
    } | null;
  };
  budget?: {
    ceiling?: number;
    currency?: string;                       // "USD" default
    enforcement?: "warn" | "alert" | "throttle" | "pause" | "stop";
  };
  compliance?: {
    frameworks?: string[];                   // ["soc2", "hipaa", "eu-ai-act", "nist-ai-rmf"]
    autoAssess?: boolean;
  };
  fleet?: {                                  // only present in fleet-managed workspaces
    registryUrl?: string;
    lastBroadcast?: string;                  // ISO timestamp
    driftHash?: string;
  };
};
```

### Integration with OpenClaw Runtime

Compiled governance policies inject into OC workspaces through existing OC mechanisms:

1. **Skills**: `claws build` emits a governance skill at `skills/claws-governance/SKILL.md` — enforces policies at runtime
2. **Tool hooks**: FE5 trust-tier rules emit as `before_tool_call` hooks in the OpenClaw Gateway
3. **AGENTS.md amendments**: Policy-derived behavioral constraints injected via FORMA amendments into AGENTS.md

The Gateway never knows claws exists. It just sees workspace files that happen to contain governance artifacts.

### Bottom Line

claws and openclaw are complementary tools for the same user. `openclaw` manages the agent runtime. `claws` compiles governance. They share the workspace directory but touch different files. One CLI, product-native naming, zero "what is craft?" moments.

## Key Principles

### d: claws complements openclaw — different layers, zero overlap

- OpenClaw CLI has ~100+ commands for runtime management (Gateway, agents, channels, memory, cron, skills)
- OpenClaw has zero governance compilation: no policy language, no audit chain, no compliance IR, no fleet management
- `~/.openclaw/` is a global state directory, not per-workspace — `.openclaw/governance/` was designed on a false premise
- OpenClaw workspaces are flat (no hidden directories) — `.claws/` introduces no collision
- The only point of contact is `openclaw security audit` (diagnostic) vs `claws check` (prescriptive) — different concerns
- Integration via workspace files: compiled policies emit as OC skills, tool hooks, or AGENTS.md amendments

> **Principle: When extending an ecosystem, verify the existing directory and config architecture before designing your naming surface.** The `.openclaw/` extension path was attractive in theory but impossible in practice — `.openclaw/` is global, not per-workspace.

---

### c: Config schema extends naturally with per-workspace claws.json

- GovernanceConfig type covers: master toggle, template, trust tier, policies, audit, budget, compliance, fleet
- `governance.enabled = false` lets developers try compilation without committing to policies
- `governance.fleet` section is auto-populated by `claws broadcast` — developer never writes it
- Three gitignore categories: cache (don't commit), secrets (don't commit), policies+audit+compliance (commit)
- SDK path resolution maps `.claws/` to the same internal types as `.craft/` — workspace-detector handles translation

> **Principle: Per-workspace config should live in a per-workspace file.** `openclaw.json` is global config at `~/.openclaw/`. A per-workspace `claws.json` keeps governance config where governance artifacts live.

---

### b: Product-native naming (.claws/) wins when the ecosystem has no per-workspace hidden directory

- Option B+ (OC-native, extend `.openclaw/`) scored highest in the abstract decision matrix (7.10)
- But the premise was wrong: `.openclaw/` is global, not per-workspace
- User override: "claws and claws.json is safe" — direct decision from the product owner
- Option C (.claws/) has clear ownership, no collision with OC's flat workspace layout, and works for any workspace format
- Option D (.governance/) is portable but unbranded — misses product identity

> **Principle: Score matrices are only as good as their premises.** Option B+ scored highest but was built on a false assumption about directory architecture. Always validate the ecosystem's actual layout before designing your surface.

---

### a: One CLI with --fleet scope flag — simplicity wins over ceremony

- Most commands are inherently scoped: ~20 always workspace, ~7 always fleet, ~6 scope-sensitive
- Safety preserved via `--fleet` + `--confirm` double gate on destructive fleet operations
- CISO objection doesn't hold: CISOs use dashboards, not CLIs
- Enterprise RBAC is enforced by identity (CP-4a), not CLI binary name — two CLIs don't add security
- One CLI is strictly simpler: one install, one `--help`, one tab-completion namespace, one doc surface

> **Principle: Default to the safer scope and make escalation explicit.** `--fleet` turns a two-CLI complexity problem into a one-flag clarity pattern. The user says what they mean.

## Design Impact

- **Q12**: Revise from two CLIs to one. claws absorbs all 40 commands. Update SDK domain accordingly.
- **SDK workspace-detector**: Must handle `.craft/` (internal), `.claws/` (product), and resolve both to same internal types
- **compiler-sdk**: Config resolution checks `claws.json` for governance (per-workspace), NOT `openclaw.json` (global)
- **SU-01**: Single package `@craftworks/claws`. No `clawops` registration needed.
- **Cross-format compilation**: Output goes to `build/<target>/` — standard, gitignored, platform-agnostic
- **OC integration**: Compiled governance emits as OC skills + tool hooks + AGENTS.md amendments

## Follow-Up Questions

1. **Q12a-F1**: Should `glint init` auto-detect platform config? → **Resolved: Yes, but broader than OC.** `glint init` auto-detects the agent platform from workspace files (SOUL.md → OpenClaw, .cursorrules → Cursor, CLAUDE.md → Claude, etc.) and reads platform-specific config where available. For OC: reads `~/.openclaw/openclaw.json` for provider defaults. Cross-platform by design (Q12d).
2. **Q12a-F2**: Should compiled governance skills appear in ClawHub? → **Resolved: Yes, for OC targets only.** `glint build openclaw` can emit a governance skill to `skills/glint-governance/SKILL.md`. Other platforms get their native output format. ClawHub distribution is an OC-specific feature, not a glint-wide one.
3. **Q12a-F3**: How should `glint build` emit `before_tool_call` hooks for OC Gateway? → **Deferred to SU-05 spec work.** This is implementation detail for the `openclaw` build target. The H1 handshake bridge maps FE5 trust-tier rules to OC Gateway exec approval hooks. Spec it when building the OC emitter.
4. **Q12a-F4**: Should `glint doctor` check for a running platform runtime? → **Resolved: Yes, platform-aware.** `glint doctor` checks whatever runtime is relevant to the detected platform — OC Gateway for OpenClaw workspaces, Claude API for Claude workspaces, etc. Platform-specific health checks are part of the doctor command.
5. **Q12a-F5**: What runtime governance primitives should be contributed upstream? → **Resolved by Q12b.** 5 runtime packages + GuardrailProvider spec PR across 3 waves (16 weeks). See Q12b for full contribution roadmap.
