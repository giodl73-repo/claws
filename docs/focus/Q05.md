# Q12e: What is the right upgrade and continuous governance experience for glint?

**Priority**: High
**Status**: Proposed
**Owner**: giodl
**Resolves**: The "upgrade script" problem — active agent maintainers need continuous governance, not checkpoint-only checks; what happens when the platform upgrades, when the user changes things, when policies update, when drift accumulates
**Blocks**: glint doctor design, glint watch behavior, upgrade hook integration, GLINT-MAP refinement
**Experiments**: a, b, c (3 total, 3 complete)

---

## Question

The boss runs a script on every OpenClaw upgrade. It does "a ton of shit" because upgrades
break things. It also does a security drift review. This script IS glint — but today it's
manual, platform-specific, and only runs at upgrade checkpoints.

The real problem is broader than upgrades. Four vectors can break governance:

| Vector | What changes | Trigger | Boss's current solution |
|--------|-------------|---------|----------------------|
| **Platform upgrade** | OC/Cursor/Claude ships new version | `npm update openclaw` | The upgrade script |
| **User changes** | Added a skill, changed SOUL.md, modified permissions | Developer edits files | Manual review / hope |
| **Policy update** | Org tightened SOC2 rules, new EU AI Act requirement | Platform engineer broadcasts | Manual re-check |
| **Drift** | Teammate changed something, time passed, config diverged | Entropy | Security drift review in upgrade script |

Today, the upgrade checkpoint is the ONLY governance checkpoint. Everything else is hope.
Glint should make governance continuous — not a gate that runs once, but a companion that
runs on every save, every commit, every upgrade, every broadcast.

### Hypothesis

The upgrade experience is three concentric rings:

1. **Inner ring: `glint watch`** — continuous governance on every file save. The developer's
   companion. Runs pinch checks in <1s. Catches user changes immediately.

2. **Middle ring: `glint doctor`** — rich diagnostics after platform upgrades, glint upgrades,
   or on-demand. Detects breaking changes, runs migration, re-validates everything. This is
   the boss's upgrade script, built-in.

3. **Outer ring: `glint drift` + `glint pinch --fleet`** — fleet-wide governance. Catches
   drift across all workspaces, re-broadcasts policies, generates compliance evidence.
   Scheduled or on-demand.

The key insight: the boss's upgrade script runs because there's no inner ring. If governance
ran continuously, the upgrade script would only need to handle platform-specific breaking
changes — not accumulated drift and unvalidated user changes.

## Working Notes

### What the Upgrade Script Probably Does

Based on the boss's description ("runs on every upgrade, does a ton of shit, security drift review"):

1. **Version check**: Compare installed OC version to expected
2. **Config migration**: Update openclaw.json for schema changes between versions
3. **Skill compatibility**: Check if installed skills work with the new OC version
4. **Gateway restart**: Stop/start Gateway with new version
5. **Memory reindex**: OC memory uses embeddings — version change may need reindex
6. **Channel reconnect**: Verify all messaging channels still connected
7. **Security audit**: Run `openclaw security audit` (the built-in diagnostic)
8. **Drift check**: Compare current state to expected/baseline state
9. **Permission review**: Check if new version introduced new permission surfaces
10. **Rollback readiness**: Verify backup/snapshot exists before upgrade

### What glint Adds

| Script function | glint equivalent | Improvement |
|----------------|-----------------|-------------|
| Version check | `glint doctor` | Also checks cross-platform compatibility |
| Config migration | `glint doctor --migrate` | Automated, reversible |
| Skill compatibility | `glint pinch` (G2 skill policy rules) | Compile-time, not runtime |
| Security audit | `glint pinch` + `glint audit verify` | Continuous, not checkpoint-only |
| Drift check | `glint drift` | Hash-based, fleet-wide |
| Permission review | `glint pinch` (FE5 trust tier rules) | Policy-enforced, not manual |
| Rollback readiness | `glint snap save pre-upgrade` | Named snapshots with restore |

### The Missing Command?

Is `glint doctor` enough, or does glint need a dedicated `glint upgrade` command?

Arguments for `glint doctor` handling it:
- Doctor already means "diagnostics + fix"
- `glint doctor --post-upgrade` is a flag, not a new command
- Keeps the command count at 35

Arguments for `glint upgrade`:
- Dedicated UX for a high-stakes workflow
- Can be opinionated: snap → migrate → pinch → drift → report
- The boss expects a named command for this

## Answer

**Three concentric rings of continuous governance — live (every save), upgrade (per-event), fleet (periodic) — using zero new commands. The boss's 10-step upgrade script becomes 3 glint commands, but the real win is the inner ring: continuous governance eliminates 7 of 10 upgrade-checkpoint scenarios before they reach the upgrade.**

### The Three-Ring Model

| Ring | Trigger | Latency | Scope | Commands |
|------|---------|---------|-------|----------|
| **Inner (live)** | File save, git commit, build | <1s | Changed files | `glint watch`, `glint pinch --staged`, `glint build` |
| **Middle (upgrade)** | Platform/glint upgrade | <15s | One workspace | `glint doctor --post-upgrade`, `glint snap save/restore`, `glint diff` |
| **Outer (fleet)** | Scheduled, on-demand | <120s | All workspaces | `glint drift`, `glint pinch --fleet`, `glint broadcast` |

### The Upgrade Script Replacement

| Before (10 manual steps) | After (3 glint commands) |
|--------------------------|-------------------------|
| Stop gateway, backup ~/.openclaw/, record state, upgrade, run doctor --fix, manually fix what doctor missed, security audit, diff configs, check skills, restart, verify, rollback if broken | `glint snap save pre-upgrade --pinch` → upgrade → `glint doctor --post-upgrade --fix` → `glint pinch --fix` (or `glint snap restore pre-upgrade` on failure) |

### The Dead Man's Switch

```bash
glint snap save pre-upgrade --pinch && \
  npm install -g openclaw@latest && \
  glint doctor --post-upgrade --fix && \
  glint pinch || \
  glint snap restore pre-upgrade
```

If any step fails, auto-restore. This is what the community asked for (GitHub issues #14526, #21488, #6477).

### Why the Inner Ring Changes Everything

The boss's upgrade script exists because governance only runs at upgrade checkpoints. With `glint watch` running continuously:

- **7 of 10** persona scenarios are caught by the inner ring (before any upgrade happens)
- **User changes** (wrong trust tier, removed guardrail, bad skill) are caught on save — 0 seconds to detection
- **Drift** is caught on commit — `glint pinch --staged` blocks bad commits
- The upgrade script shrinks to: snapshot → migrate → verify. That's it.

### New Flags (Not New Commands)

| Flag | Command | Purpose |
|------|---------|---------|
| `--post-upgrade` | `glint doctor` | Upgrade-specific checks: version gap, config migration, skill compat |
| `--pre-upgrade` | `glint snap save` | Tag snapshot for easy restore reference |

Command count stays at 35. The three-ring model composes from existing commands.

### Cross-Platform Upgrade Support

| Platform | What `glint doctor --post-upgrade` checks |
|----------|------------------------------------------|
| OpenClaw | Config schema migration, skill API compat, gateway auth changes, env var prefix migration |
| Cursor | .cursorrules schema changes, deprecated fields |
| Claude Code | CLAUDE.md format changes, tool permission model changes |
| Bedrock | Guardrail policy JSON schema changes |
| LangGraph | Guard decorator API changes |

`glint doctor` detects the platform from workspace files and runs platform-specific upgrade checks.

### The Pitch

**To the boss (30s)**: "Your upgrade script is glint. But instead of 10 steps once a month, it's 3 commands — and governance runs on every save so most issues never reach the upgrade."

**To the developer (60s)**: "Install glint, run `glint watch`. Every time you save, governance validates your agent in under a second. When you upgrade your platform, `glint doctor` handles the migration. If it breaks, `glint snap restore` rolls back instantly. No more 'it worked before I upgraded.'"

**To the CISO (15s)**: "Signed audit trail. Tamper-proof hash chain. Fleet-wide compliance evidence on demand. SOC2/HIPAA/EU AI Act packages."

### Bottom Line

Continuous governance is three rings, not one checkpoint. The inner ring (live) catches 70% of issues instantly. The middle ring (upgrade) handles platform migration with snapshot/restore safety. The outer ring (fleet) ensures fleet-wide consistency. Zero new commands. Two new flags. The boss's upgrade script becomes unnecessary when governance runs on every save.

## Key Principles

### c: The inner ring handles 70% of scenarios — continuous governance eliminates checkpoint pain

- 10 persona scenarios tested across 5 personas and 4 break vectors
- 7 of 10 caught by the inner ring (watch, pinch --staged, build)
- The boss's upgrade script is a symptom: governance running at checkpoints instead of continuously
- Pre-commit hooks (`glint pinch --staged`) prevent accidental guardrail removal, trust tier escalation, and subagent deletion
- The new hire scenario validates progressive disclosure: 4 commands to "governed" in 5 minutes

> **Principle: If governance runs continuously, upgrade checkpoints shrink to platform-specific migration only.** The upgrade script is large because it compensates for drift accumulated between upgrades. Eliminate the drift window and the script collapses.

---

### b: Three rings compose from existing commands — zero new commands needed

- Every ring maps to existing GLINT-MAP commands (#2, #7, #10, #12, #15, #16, #22, #27-31, #34, #35, #45)
- Only 2 new flags: `--post-upgrade` (doctor) and `--pre-upgrade` (snap tag)
- Command count stays at 35
- The dead man's switch pattern composes: snap → upgrade → doctor → pinch → or restore
- Ring interactions follow escalation: inner → middle → outer, never the reverse

> **Principle: A good command surface composes into workflows; a bad one requires new commands for each workflow.** The three-ring model validates Q12c's verb surface — every upgrade/governance scenario maps to existing commands.

---

### a: OpenClaw's upgrade pain is structural — 3 breaking releases per quarter, doctor --fix is unreliable

- 3 breaking releases in 90 days (Q1 2026): config renames, plugin path changes, security defaults
- `openclaw doctor --fix` reports issues but doesn't fix them — users must manually edit configs
- v2026.4.5 caused 10 gateway restarts in 8 hours post-upgrade
- Community demands: auto-backup (#6477), safer self-update with rollback (#14526), dead man's switch (#21488)
- The 10-step upgrade script maps to 3 glint commands with semantic (not file-level) snapshots

> **Principle: When the ecosystem's own migration tooling is unreliable, a compile-time governance layer becomes essential — not optional.** The boss's script exists because `openclaw doctor --fix` doesn't work. Glint's `doctor --post-upgrade` is compile-time deterministic, not runtime guessing.

| exp-c | **Three rings validated: inner handles 70%, middle handles 20%, outer handles 10%** | *(nothing — this holds)* |

## Design Impact

- **GLINT-MAP.md**: Add `--post-upgrade` flag on doctor and `--pre-upgrade` tag on snap save. No new commands. Count stays at 35.
- **SU-05 (guard)**: Upgrade checks map to guard policy rules (G1-G6) + fence passes (FE1-FE5). Doctor's platform-specific checks are a new guard module.
- **Q12c verb surface**: Confirmed — zero new commands needed. Three-ring model validates the 35-command surface.
- **Q12b upstream**: The upgrade-checker logic for OpenClaw could be a contributed package (`@openclaw/upgrade-checker`). Platform-specific migration logic is separable.
- **Marketing**: "Your upgrade script is glint. But it runs on every save." is the boss pitch. "Three rings of continuous governance" is the architecture pitch.

## Follow-Up Questions

1. **Q12e-F1**: Should `glint watch` auto-start on terminal open (like ESLint in VS Code), or require explicit `glint watch`? Auto-start improves inner ring coverage but adds process overhead.
2. **Q12e-F2**: Should `glint doctor --post-upgrade` detect the platform upgrade automatically (comparing cached version to installed), or require the user to tell it an upgrade happened?
3. **Q12e-F3**: Should the dead man's switch be a first-class `glint upgrade` alias that wraps snap → doctor → pinch → restore? Or keep it composable from individual commands?
4. **Q12e-F4**: How should `glint drift` schedule itself? Cron job, systemd timer, or built-in `glint drift --schedule weekly`?
5. **Q12e-F5**: Should `glint doctor` check for available platform upgrades proactively ("OpenClaw v2026.4.9 available, you're on v2026.4.5")?
