# Q12f: How should glint integrate with CI/CD pipelines?

**Priority**: High
**Status**: Proposed
**Owner**: giodl
**Resolves**: Pre-commit hooks, GitHub Actions, CI gates, CD governance enforcement, fleet governance in deployment pipelines, SARIF/SAST integration
**Blocks**: glint CI package design, GitHub Action marketplace listing, pre-commit hook config
**Experiments**: a, b, c (3 total, 3 complete)

## Question

Q12e established three rings of continuous governance: live (every save), upgrade (per-event),
fleet (periodic). The inner ring runs locally. But enterprises also need governance in CI/CD:

1. **Pre-commit**: `glint pinch --staged` as a git hook — already designed but not specced for distribution
2. **CI (pull request)**: Run `glint pinch` on every PR. Block merge on violations. Output SARIF for GitHub code scanning.
3. **CD (deploy)**: Run `glint comply` before deployment. Gate releases on governance. Sign artifacts.
4. **Scheduled**: Run `glint drift` on a cron. Alert on fleet-wide drift.

Each integration point has different requirements: latency tolerance, output format, failure
mode, secrets handling, caching strategy. A GitHub Action has different constraints than a
pre-commit hook.

### Hypothesis

Three integration tiers:

1. **Local hooks** (pre-commit, husky): `glint pinch --staged --quiet` — fast, blocking, zero config
2. **CI action** (GitHub Actions, GitLab CI): `@craftworks/glint-action` — runs pinch + comply, outputs SARIF, caches .glint/, gates PR merge
3. **CD gate** (deploy pipeline): `glint comply --sign` — signs compliance evidence, gates deployment, integrates with artifact registries

The CI action is the highest-leverage integration — it brings governance to every PR without
requiring developers to install glint locally.

## Working Notes

### Integration Points

| Stage | Trigger | Latency budget | Output format | Failure mode |
|-------|---------|---------------|---------------|-------------|
| Pre-commit | `git commit` | <2s | Pass/fail + inline messages | Block commit |
| PR check | Push to PR branch | <60s | SARIF + PR comment + check status | Block merge |
| CD gate | Pre-deploy hook | <30s | Signed compliance artifact | Block deploy |
| Scheduled | Cron / timer | <300s | Fleet report + alerts | Notification |

### SARIF Integration

GitHub code scanning accepts SARIF (Static Analysis Results Interchange Format). If `glint pinch` outputs SARIF, violations appear as code annotations on the PR — inline, next to the offending line. This is the eslint/semgrep pattern.

### Caching Strategy

`.glint/cache/` contains compiled IR, boost cache, and eval cache. In CI:
- Cache key: hash of governance-relevant files (glint.json, policies/, workspace files)
- Restore: pull from GitHub Actions cache
- Save: push updated cache after successful run
- This makes repeated CI runs fast (incremental, not full recompile)

## Answer

**A four-stage governance pipeline — pre-commit, PR check, CD gate, fleet scan — using `@craftworks/glint-action` as the primary CI distribution mechanism. SARIF output integrates with GitHub code scanning for inline PR annotations. Compliance evidence chains from local audit trail through signed CD artifacts to fleet-wide reports. The pipeline extends Q12e's three-ring model: CI/CD is not a fourth ring but the enforcement mechanism for the inner and middle rings.**

### The Four-Stage Pipeline

| Stage | Trigger | Command | Latency | Failure mode | Output |
|-------|---------|---------|---------|-------------|--------|
| **0: Pre-commit** | `git commit` | `glint pinch --staged --quiet` | <1s | Block commit | Pass/fail + audit event |
| **1: PR check** | Push to PR | `glint pinch --diff $BASE --format sarif` | <30s | Block merge | SARIF + PR annotations + check status |
| **2: CD gate** | Push to main/tag | `glint comply <framework> --sign` | <30s | Block deploy | Signed compliance evidence + audit export |
| **3: Fleet scan** | Weekly cron | `glint pinch` (matrix) + `glint drift` | <300s | Alert + issue | Fleet report + drift alerts |

### The `@craftworks/glint-action`

The GitHub Action is the highest-leverage integration point. Key design decisions:

1. **Composite action** (bash steps) for transparency and debuggability
2. **SARIF-first output** — code scanning is the primary value proposition
3. **Built-in cache management** (`cache: true`) — no separate `actions/cache` config needed
4. **Auto-detect PR context** — diff-base defaults to PR base SHA
5. **Gradual adoption** — `warn-only` mode for onboarding, then tighten over weeks
6. **Auto-init** — if no `glint.json` exists, init with template

### Compliance Evidence Chain

```
Local (Stage 0)            CI (Stage 1)              CD (Stage 2)            Fleet (Stage 3)
──────────────            ──────────                ──────────              ───────────
glint pinch --staged  →   glint audit verify    →   glint comply --sign →  glint comply --fleet
     │                         │                         │                       │
     ▼                         ▼                         ▼                       ▼
audit/chain.jsonl         chain integrity OK        soc2.json (signed)     fleet compliance report
(hash-chained log)        SARIF → code scanning     manifest.sig           aggregated evidence
```

Every `glint pinch` result appends to the hash-chained audit log. The chain travels with the code. CI verifies chain integrity. CD embeds the chain hash in signed compliance evidence. Fleet aggregates evidence across workspaces.

### CI Landscape Patterns Applied

Six existing tools surveyed (ESLint, Semgrep, Snyk, Trivy, Checkov, Ruff). Key patterns adopted:

| Pattern | Source tool | glint implementation |
|---------|------------|---------------------|
| Native SARIF output | All 6 tools | `--format sarif` on pinch, comply |
| GitHub native annotations | Ruff (`--format github`) | `--format github` for `::error`/`::warning` output |
| Built-in cache management | Trivy (`cache: true`) | Action manages `.glint/cache/` automatically |
| Differential scanning | Semgrep (`semgrep ci`) | `--diff <ref>` scans only PR-changed files |
| Severity-based gating | Snyk (`--severity-threshold`) | `--fail-on critical,high` |
| Soft-fail for adoption | Checkov (`soft_fail`) | `--warn-only` mode |
| CI-specific entry point | Semgrep (`semgrep ci`) | `--ci` flag auto-detects environment |

18 of 23 pitfalls from GLINT-PITFALLS.md are detectable across the four stages:

### Gradual Adoption Path

```
Week 1:  CI only, warn-only: true          → See what glint finds (visibility)
Week 2:  CI only, fail-on: critical        → Start blocking critical violations
Week 4:  Pre-commit + CI, fail-on: high    → Add local enforcement
Week 8:  Full pipeline, fail-on: all       → Complete governance
```

### New Flags for GLINT-MAP.md

| Flag | Command | Purpose |
|------|---------|---------|
| `--format sarif` | pinch, comply | SARIF 2.1.0 output for code scanning |
| `--format github` | pinch | Native GitHub Actions `::error`/`::warning` annotations |
| `--diff <ref>` | pinch | Scan only files changed since ref (PR diff scanning) |
| `--fail-on <sev>` | pinch | Severity gating: fail only on specified severity levels |
| `--warn-only` | pinch | Soft-fail mode: all findings are warnings, exit 0 |
| `--sign` | comply | Sign compliance evidence with HMAC-SHA256 |
| `--ci` | pinch | Auto-detect CI environment, set defaults |

### Three-Ring Integration

CI/CD is not a fourth ring. It is the enforcement mechanism for the existing three rings:

- **Stage 0 (pre-commit)** IS the inner ring
- **Stage 1 (PR check)** is the inner ring's backstop (catches `--no-verify`, bots, external contributors)
- **Stage 2 (CD gate)** is the middle ring's enforcement (compliance evidence at release)
- **Stage 3 (fleet scan)** IS the outer ring

The 70/20/10 split from Q12e becomes 70/25/5 with CI/CD: inner ring catches 70% locally, CI/CD catches 25% as backstop and compliance evidence, outer ring catches 5% as drift detection.

### Bottom Line

The CI/CD pipeline makes governance unavoidable. Pre-commit hooks are optional (developers can `--no-verify`). But CI runs on every PR, and CD gates every deployment. `@craftworks/glint-action` is a single YAML block that brings governance to every repo in an org. SARIF output makes violations visible inline on PR diffs. Signed compliance evidence chains from local audit trail to fleet-wide reports. The boss's upgrade script becomes unnecessary when every PR and every deploy is governed.

## Key Principles

### c: The four-stage pipeline extends the three-ring model without adding a fourth ring

- Pre-commit (Stage 0) IS the inner ring. PR check (Stage 1) is its enforcement backstop.
- CD gate (Stage 2) IS the middle ring in CI. Fleet scan (Stage 3) IS the outer ring.
- The 70/25/5 split: inner ring catches 70% locally, CI/CD catches 25%, outer ring catches 5%.
- CI/CD is the mechanism that makes the ring model work for teams, not just individuals.
- A solo developer needs only the inner ring. A team needs CI. An enterprise needs all four stages.

> **Principle: CI/CD is the enforcement mechanism for the ring model, not a separate ring.** Adding governance to CI makes the inner ring unavoidable — even when developers bypass pre-commit hooks.

---

### b: The GitHub Action is the highest-leverage distribution channel

- One YAML block adds governance to any repo. No local glint install required.
- SARIF output integrates with GitHub code scanning — violations appear inline on PR diffs.
- Built-in cache management, auto-init, auto-detect PR context — zero-config for simple cases.
- Gradual adoption (warn-only → fail-on-critical → fail-on-high → fail-on-all) enables enterprise rollout.
- 6 existing tools surveyed: all have official GitHub Actions. This is the expected distribution model.

> **Principle: The action IS the product for 80% of users.** Most developers never install glint locally. They experience governance through PR annotations and merge gates. The action must be the best possible first impression.

---

### a: SARIF is the universal CI lingua franca — two-tier annotations for coverage

- All 6 surveyed tools support SARIF. GitHub, GitLab, Azure DevOps accept it. Non-negotiable.
- Two-tier strategy: `--format github` for lightweight native annotations (zero-config), `--format sarif` for full code scanning (dashboard, tracking, security tab).
- Differential scanning (`--diff <ref>`) is the key latency optimization — only scan PR-changed files.
- Severity-based gating (`--fail-on`) enables gradual adoption without blocking entire organizations.
- Compliance evidence signing (`--sign`) chains audit trail from local to fleet.

> **Principle: Meet developers where they already work.** PR annotations, merge gates, code scanning tabs — these are existing surfaces. Glint governance must appear in these surfaces, not require developers to visit a separate dashboard.

## Follow-Up Questions

1. **Q12f-F1**: Should the glint action support GitLab CI and Azure DevOps in addition to GitHub Actions? If so, should there be separate action packages or a single cross-platform CI script?
2. **Q12f-F2**: Should `glint comply --sign` use HMAC-SHA256 (symmetric, org key) or asymmetric signatures (RSA/ECDSA, per-user keys) for compliance evidence? Asymmetric enables individual attribution but adds key management complexity.
3. **Q12f-F3**: Should the fleet scan create GitHub issues for each violation, or aggregate into a single fleet report issue? Per-violation issues enable tracking but risk issue flood.
4. **Q12f-F4**: Should `glint pinch --diff` auto-detect the PR base from CI environment variables (GITHUB_BASE_REF, CI_MERGE_REQUEST_TARGET_BRANCH_NAME) or require explicit `--diff <ref>`?
5. **Q12f-F5**: Should the glint action support a `glint.yml` config file (like `.eslintrc`) that specifies CI-specific overrides (fail-on, warn-only, skip rules) separate from `glint.json`?
