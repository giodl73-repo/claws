## Question

The atoms audit found `atom:language-service` (A189) and `atom:compilation-host` (A185) as
high-impact investigation targets. The user confirmed: "VS Code for OpenClaw would be huge."

Current OC VS Code landscape (April 2026):
- **OpenClaw Node for VS Code** (4,200 installs) — file ops, search, diagnostics via sandbox
- **OpenClaw Studio** — config doctoring, plugin scaffolding
- **OpenClaw VS Code Agent** — local CLI from inside VS Code
- All are basic infrastructure. NONE provide governance IntelliSense.

The opportunity: a **claws VS Code extension** that provides:
1. Real-time governance diagnostics as you edit SOUL.md, TOOLS.md, AGENTS.md
2. IntelliSense for policy rules (RELAX expression completion)
3. Inline risk classification (hover over a tool → see R1-R5 score)
4. Cross-file conflict detection (edit TOOLS.md → see tension with SOUL.md)
5. OBO boundary highlighting (tools that cross the impersonation line)
6. `claws pinch` on save (like ESLint on save)
7. Governance diff view (what changed in the governance IR since last compile)
8. Trust tier visualization (color-coded by risk level)

The compilation host daemon (atom:compilation-host, A185) powers this: a long-lived
process with cached GovernanceIR, incremental recompilation on file change, and LSP
(Language Server Protocol) for VS Code communication.

### Hypothesis

Three components:

1. **claws-lsp** — Language Server Protocol server. Reuses atom:language-service patterns.
   Provides: diagnostics (governance violations inline), completion (RELAX expressions,
   tool names, policy templates), hover (risk classification, OBO status), code actions
   (fix violations, add elicitation annotation).

2. **claws-vscode** — VS Code extension that wraps claws-lsp. Provides: extension UI,
   tree view (workspace governance summary), status bar (governance health indicator),
   command palette (claws pinch, claws build, claws test), settings.

3. **Compilation host** — Long-lived daemon (atom:compilation-host pattern) that maintains
   cached GovernanceIR and recompiles incrementally when files change. The LSP server
   communicates with this daemon. `claws watch` IS this daemon.

## Answer

claws integrates with VS Code through three components: a Language Server Protocol
server (claws-lsp), a VS Code extension (claws-vscode), and a compilation host daemon
that powers both.

### Three-Component Architecture

**1. claws-lsp** -- The governance language server. A Node.js process that speaks LSP,
wrapping the claws compilation pipeline (PARSE/EXTRACT/ANALYZE from Q12j). Provides:
- **Diagnostics**: 10 diagnostic categories (G-PARSE, G-SOUL, G-CLASS, G-ELICIT,
  G-BOUND, G-CONFLICT, G-BUDGET, G-A2A, G-POLICY, G-WORKFLOW) published inline as
  the developer types, with 300ms debounce and per-URI AbortSignal cancellation.
- **Completions**: Context-aware completions in SOUL.md (constraint templates), TOOLS.md
  (tool names, trust tiers), AGENTS.md (delegation patterns), and RELAX expressions
  in policy/workflow YAML (delegated to RELAX completion provider from compiler-sdk).
- **Hover**: Risk classification on tool hover (R1-R5 + OBO status + governance chain),
  constraint extraction details on SOUL.md hover, delegation analysis on AGENTS.md hover.
- **Code actions**: Quick fixes for every diagnostic category -- fix deny-grant conflicts,
  add elicitation annotations, add trust entries, rewrite vague constraints.
- **Cross-file tension detection**: The differentiating feature. Edit SOUL.md and see
  diagnostics appear in TOOLS.md. 7 conflict categories (deny-grant, tier-override,
  OBO-clash, budget-exceed, memory-retention, A2A-untrust, workflow-bypass).
- **Semantic tokens**: Risk-level color coding (R1=green through R5=red), OBO boundary
  highlighting, deny strikethrough, elicit italic.
- **Code lenses**: Aggregate governance summaries above file sections.
- **Go-to-definition**: Cross-file navigation between related governance entries.

**2. claws-vscode** -- Thin VS Code extension client. Starts claws-lsp, contributes
tree view (workspace governance summary), status bar (governance health indicator),
command palette (claws pinch, claws build, claws test), and settings. No compilation
logic -- all intelligence is in the LSP server.

**3. Compilation host** -- Long-lived daemon maintaining cached GovernanceIR with
incremental recompilation. Embedded inside the LSP server for v0.1 (simplest). Extracted
to `claws serve` daemon for v0.3+ when CI/CD and Gateway integration land. Core data
structures: GovernanceIR cache with generation counter, dependency graph with typed
edges (8 edge types mapping static relationships between governance files), snapshot
store (20 frozen IR snapshots for diff computation).

### Incremental Compilation Model

PARSE is incremental (only changed files, using SHA-256 content hashing). ANALYZE runs
on the full workspace AST (cross-file tensions require complete context). Latency targets:
single-file PARSE <50ms, full ANALYZE <150ms, total round-trip <200ms. Batch window
collects multiple file saves within 300ms into a single compilation pass.

### `claws serve` API

12 HTTP endpoints for programmatic governance access: /compile, /status, /diagnostics,
/tensions, /classify/:tool, /ir, /snapshot, /diff, /invalidate, /health, plus WebSocket
event stream. Serves CI/CD pipelines (pre-merge governance checks), OC Gateway
(hot-reload governance rules), and custom tooling.

### OC VS Code Landscape Positioning

The three existing OC VS Code extensions (OpenClaw Node 4,200 installs, OpenClaw Studio
2,800, OC VS Code Agent 1,500) are basic infrastructure -- file ops, scaffolding, CLI
access. None provide governance analysis. claws-vscode positions as the "governance
layer" (Layer 4) that complements existing extensions, not replaces them. Blue ocean:
zero existing competition for governance IntelliSense.

### Architecture Reuse from Compiler-SDK

The Astro LSP server (`compiler-sdk/src/astro/lsp/server.ts`) provides the exact
patterns claws-lsp needs: factory function for testability, 300ms debounce with
generation counter, per-URI AbortController, two-phase analysis, DocumentCache with
LRU eviction, ProjectIndex for cross-file queries. The RELAX LSP providers
(`relax/lsp/`) are directly reusable for governance RELAX expressions: CompletionProvider,
DiagnosticProvider (with type-checking), HoverProvider (scope-chain resolution),
YamlOffsetMapper. The tension runtime (`agent-sdk/src/runtime/`) provides the
negotiation model for compile-time tension detection between governance files.

## Key Principles

1. **LSP-first**: All intelligence lives in the language server, not the VS Code extension.
   This enables future editors (JetBrains, Neovim, Zed) with zero rewrite.

2. **Incremental PARSE, full ANALYZE**: Parse only changed files; analyze the full workspace
   for cross-file tensions. This is the performance sweet spot.

3. **Complement, don't replace**: Position alongside existing OC extensions, not against them.
   claws-vscode fills the governance gap that no other extension addresses.

4. **Consumer-decoupled compilation**: The CompilationConsumer interface means LSP, CLI watch,
   and HTTP API all share the same compilation host with zero protocol-specific logic in the
   pipeline.

5. **Snapshot-based temporal governance**: Capture GovernanceIR snapshots on every change.
   Diff between snapshots for governance changelog. Novel capability no other tool provides.

## Model Evolution

This question evolved through three experiments:

- **exp-a** established the competitive landscape: all three existing OC VS Code extensions
  are basic infrastructure with zero governance analysis. This confirmed the blue-ocean
  positioning and the complement-not-replace strategy.

- **exp-b** designed the LSP server by mapping every governance capability to a standard LSP
  feature. The key insight was that cross-file tension detection (editing SOUL.md produces
  diagnostics in TOOLS.md) is the differentiating feature that requires
  `interFileDependencies: true` and a workspace-level TensionIndex.

- **exp-c** designed the compilation host daemon and showed that the same GovernanceIR cache
  serves three consumers (LSP, CLI watch, HTTP API) through a common CompilationConsumer
  interface. The process model evolved from "always separate daemon" to "embedded for v0.1,
  extracted for v0.3+" based on complexity analysis.

## Design Impact

- **CLAWS-MAP**: `claws serve` is a new command (HTTP API daemon for governance state). `claws watch` is a new command (terminal governance feedback). Both share the CompilationHost.
- **Q12m claws-sdk**: claws-lsp imports GovernanceIR compilation pipeline from claws-sdk. The LSP server is in the `@claws/language-server` package.
- **Q12o maker experience**: VS Code governance IntelliSense IS the maker experience. Skill creators see risk classification, policy violations, and cross-file tensions as they edit.
- **Q12p atoms**: Uses 7 atoms: compilation-host (A185), compilation-snapshot (A186), dependency-graph (A187), emission-staging (A188), language-service (A189), forest-session (A205), command-gate (A207).
- **Q12j compilation model**: The 5-phase pipeline (PARSE/EXTRACT/ANALYZE/OPTIMIZE/EMIT) is reused directly. claws-lsp runs phases 1-3 for diagnostics. `claws serve` runs all 5 on demand.
- **Q12h security model**: Risk classification R1-R5 is surfaced in VS Code hover and semantic tokens. OBO boundary visualization uses the elicitation gates from Q12h.
- **Q12f CI/CD**: `claws serve --idle-timeout` enables CI-native governance checks via HTTP API.

## Follow-Up Questions

1. **Multi-workspace support**: How does claws-lsp handle VS Code workspaces with multiple
   OC agent directories? One compilation host per workspace root, or a single host with
   multi-root awareness?

   may want RELAX expressions inline for precision. Should claws-lsp support a "RELAX block"
   syntax in SOUL.md (e.g., ` ```relax ... ``` `) with full RELAX IntelliSense?

3. **Extension marketplace strategy**: Should claws-vscode be published on the VS Code
   Marketplace as `claws-governance` or bundled in an "OpenClaw Enterprise" extension pack?

4. **JetBrains + Neovim**: Because claws-lsp speaks standard LSP, how much work to support
   JetBrains (via LSP plugin) and Neovim (via native LSP client)? Estimate: <1 week each
   for basic support (diagnostics + hover).
