# Q12g: What is the right glint.json schema for cross-platform governance?

**Priority**: High
**Status**: Proposed
**Owner**: giodl
**Resolves**: glint.json schema v2 — extend from OpenClaw-only (Q12a) to cross-platform (Cursor, Claude, Bedrock, LangGraph, CrewAI, custom); platform detection, target-specific config, shared vs platform-specific policy sections
**Blocks**: glint init implementation, cross-compile target config, platform-specific doctor checks
**Experiments**: a, b, c (3 total)

---

## Question

Q12a designed `ClawsConfig` (now `GlintConfig`) for OpenClaw governance:

```typescript
type GlintConfig = {
  enabled: boolean;
  template?: string;
  trustTier?: 0 | 1 | 2 | 3 | 4;
  policies?: string[];
  audit?: { enabled: boolean; chain?: string; siem?: { format; endpoint } };
  budget?: { ceiling?: number; currency?: string; enforcement?: string };
  compliance?: { frameworks?: string[]; autoAssess?: boolean };
  fleet?: { registryUrl?: string; lastBroadcast?: string; driftHash?: string };
};
```

This schema assumes OpenClaw. But Q12d established glint as cross-platform — governing
Cursor, Claude Code, AWS Bedrock, LangGraph, CrewAI, and custom agents. Questions:

1. **Platform detection**: How does glint know which platform(s) this workspace targets? Auto-detect from files? Explicit `platform` field? Both?
2. **Target-specific config**: Cursor needs `.cursorrules` output config. Bedrock needs guardrail policy JSON config. Do these live in glint.json or in target-specific files?
3. **Multi-platform workspaces**: A workspace might target OpenClaw AND Cursor (cross-compile both). How does the schema handle multiple targets?
4. **Shared vs platform-specific policies**: Some policies are universal (trust tiers, budget, audit). Some are platform-specific (OC skill governance, Cursor rule format). Where's the boundary?
5. **Schema versioning**: How does the schema evolve as new platforms are added?

### Hypothesis

The schema splits into three layers:

1. **Core** (platform-agnostic): enabled, trustTier, policies, audit, budget, compliance, fleet — these apply to any agent on any platform
2. **Targets** (platform-specific): a `targets` map keyed by platform name, with platform-specific build/emit config
3. **Detection** (auto + explicit): auto-detect platform from workspace files, with explicit `platform` field as override

```typescript
type GlintConfig = {
  $schema?: string;           // JSON Schema URL for IDE autocomplete
  version: 1;                 // Schema version
  // Core (platform-agnostic)
  enabled: boolean;
  template?: string;
  trustTier?: 0 | 1 | 2 | 3 | 4;
  policies?: string[];
  audit?: AuditConfig;
  budget?: BudgetConfig;
  compliance?: ComplianceConfig;
  fleet?: FleetConfig;
  // Targets (platform-specific)
  platform?: string;          // explicit: "openclaw" | "cursor" | "claude" | ...
  targets?: Record<string, TargetConfig>;
};
```

### The Multi-Target Problem

A workspace might contain BOTH `SOUL.md` (OpenClaw) AND `CLAUDE.md` (Claude Code). This means:
- `glint build` should detect both and ask which to target, or build both
- `glint build openclaw` and `glint build claude` should work explicitly
- Target-specific config (e.g., OC skill governance vs Claude tool permissions) needs to live separately

### Q12a Schema (Current)

The existing schema from Q12a covers:
- ✅ enabled, template, trustTier, policies — platform-agnostic, keep as-is
- ✅ audit, budget, compliance — platform-agnostic, keep as-is
- ✅ fleet — platform-agnostic, keep as-is
- ❌ No platform field — assumes OpenClaw
- ❌ No targets map — no platform-specific config
- ❌ No schema version — no migration path
- ❌ No $schema — no IDE autocomplete

## Answer

**Three-layer schema: core (platform-agnostic) + targets (platform-specific) + detection (auto + explicit). Schema version 2, backwards-compatible with Q12a's v1.**

### Resolution

GlintConfig v2 splits glint.json into three layers that scale with workspace complexity:

1. **Core layer** (platform-agnostic): `enabled`, `trustTier`, `template`, `policies`, `audit`, `budget`, `compliance`, `fleet`. These apply to every agent on every platform. A developer who writes `{ "version": 2, "enabled": true }` gets a working governance setup.

2. **Targets layer** (platform-specific): A `targets` map keyed by platform name (`openclaw`, `cursor`, `claude`, `github`, `bedrock`, `langgraph`, `crewai`). Each target holds build/emit config (output format, merge strategy, runtime integration) and optional governance overrides (target-specific trustTier, additional policies). Target trustTier overrides core; target policies append to core (never weaken).

3. **Detection layer**: Optional `platform` field overrides auto-detection for `glint build` default. When omitted, auto-detection scans workspace marker files (SOUL.md -> OpenClaw, .cursorrules -> Cursor, CLAUDE.md -> Claude Code, etc.). When `targets` is present with multiple entries, `glint build` builds all configured targets.

### Schema Summary

```typescript
type GlintConfig = {
  $schema?: string;                    // IDE autocomplete
  version: 2;                          // schema version
  platform?: Platform;                 // explicit detection override
  enabled: boolean;                    // master toggle
  template?: PolicyTemplate;           // soc2, hipaa, eu-ai-act, minimal, ...
  trustTier?: TrustTier;              // T0-T4, default T2
  policies?: string[];                 // paths to policy YAML files
  audit?: AuditConfig;                 // chain, SIEM, retention
  budget?: BudgetConfig;               // ceiling, unit, enforcement, warnAt
  compliance?: ComplianceConfig;       // frameworks, autoAssess, signing
  fleet?: FleetConfig;                 // registryUrl, groups, driftHash
  targets?: Partial<Record<Platform, TargetConfig>>;  // per-platform config
};
```

Full type definition with all nested types in `results/exp-b.md`.

### Workspace Examples

**Minimal** (4 lines -- governance without platform commitment):
```json
{ "$schema": "https://glint.dev/schemas/v2.json", "version": 2, "enabled": true, "trustTier": 2 }
```

**Single platform** (8 lines -- auto-detected, no `targets` needed):
```json
{
  "$schema": "https://glint.dev/schemas/v2.json",
  "version": 2,
  "enabled": true,
  "template": "soc2",
  "trustTier": 2,
  "audit": { "enabled": true }
}
```

**Multi-target** (30 lines -- OC production + Claude dev, different trust tiers):
```json
{
  "$schema": "https://glint.dev/schemas/v2.json",
  "version": 2,
  "enabled": true,
  "template": "soc2",
  "trustTier": 2,
  "targets": {
    "openclaw": { "trustTier": 3, "config": { "emitSkill": true } },
    "claude": { "trustTier": 2, "config": { "emitSettings": true } }
  }
}
```

### Platform Detection

| Platform | Primary marker | Confidence | Default trustTier | Enforcement model |
|----------|---------------|------------|-------------------|-------------------|
| OpenClaw | `SOUL.md` | Definitive | T2 | Runtime (Gateway hooks) |
| Cursor | `.cursorrules` | Definitive | T1 | Advisory (instructions) |
| Claude Code | `CLAUDE.md` | Definitive | T2 | Semi-enforced (tool perms) |
| GitHub Copilot | `.github/copilot-instructions.md` | Definitive | T1 | Advisory (instructions) |
| AWS Bedrock | *(none reliable)* | Requires explicit `--platform` | T3 | Runtime (API guardrails) |
| LangGraph | `langgraph.json` | Definitive | T2 | Runtime (decorators) |
| CrewAI | `crewai.yaml` | Definitive | T2 | Semi-enforced (config + callbacks) |

Platforms fall into three enforcement tiers: runtime-enforced (OC, Bedrock), semi-enforced (Claude, CrewAI), and advisory-only (Cursor, GitHub Copilot). Advisory-only platforms default to lower trust tiers because governance is instruction-based with no programmatic enforcement.

### Migration from V1

V1-to-V2 is nearly non-breaking:
- **14 of 15 v1 fields unchanged** -- carry over directly
- **1 rename**: `budget.currency` -> `budget.unit` (now also accepts `"tokens"`)
- **9 new optional fields**: `$schema`, `version`, `platform`, `targets`, `audit.retention`, `budget.warnAt`, `compliance.outputDir`, `compliance.signing`, `fleet.groups`
- **0 removals**

V1 configs work indefinitely. `glint doctor` detects v1 format and offers `glint doctor --fix` for automated migration. Legacy directory names (`.clawsc/`, `.claws/`) are also detected and migrated.

### Bottom Line

The schema scales from 4 lines (minimal) to 33 lines (fleet-managed enterprise) with no wasted config. Single-platform users never touch `targets`. Multi-platform users get isolated per-target config. Fleet managers ignore platform entirely. V1 configs work forever. IDE autocomplete via `$schema` is the highest-ROI DX feature.

## Key Principles

### c: Platform defaults must vary at init time even though the schema is platform-agnostic

- Advisory-only platforms (Cursor, GitHub Copilot) default to T1 with audit disabled -- governance is instruction-based with no enforcement mechanism
- Runtime-enforced platforms (OpenClaw, Bedrock) default to T2-T3 with audit enabled -- enforcement is programmatic and auditable
- Bedrock cannot be auto-detected reliably -- requires explicit `--platform bedrock` at init
- `glint init` must read platform context to set the right defaults, even though the resulting schema is platform-agnostic
- V1-to-V2 migration is nearly non-breaking: 14 unchanged fields, 1 rename, 9 additions, 0 removals

> **Principle: Schema migration should be additive, not structural.** The gentlest migration is one where existing configs work unchanged and new capabilities arrive as optional fields. Breaking changes (renames, removals, restructures) should be minimized to one or two per version.

---

### b: Core governance is universal; platform-specific config is thin

- 90%+ of governance semantics (trustTier, policies, audit, budget, compliance, fleet) are platform-agnostic
- Platform-specific `config` objects hold 3-5 fields at most (merge strategy, output toggles, runtime URLs)
- Target-specific `trustTier` overrides core; target-specific `policies` append to core -- targets can only add stricter governance, never weaken it
- `$schema` field for IDE autocomplete is the single highest-ROI developer experience investment
- Fleet metadata (lastBroadcast, driftHash) is auto-populated, never manually written

> **Principle: Make the universal layer carry the weight.** When 90% of semantics are shared, the schema should make the shared layer primary and the platform-specific layer optional. A developer targeting one platform should never need to write a `targets` section.

---

### a: Auto-detection resolves the multi-platform ambiguity without requiring explicit config

- Each platform has a primary marker file with definitive detection confidence (SOUL.md, .cursorrules, CLAUDE.md, langgraph.json, crewai.yaml)
- Bedrock is the outlier: API-driven, no local workspace files, requires explicit `platform` field
- Multi-platform detection (SOUL.md + CLAUDE.md in same workspace) requires either explicit `--target` flag or `targets` map in glint.json
- No platform detected = platform-agnostic governance only (`glint pinch` works, `glint build` emits IR)
- Detection priority: `targets` map > `platform` field > auto-detect from workspace files

> **Principle: Default to auto-detection, support explicit override.** Auto-detection eliminates config for the common case (single platform, standard marker files). Explicit `platform` and `targets` handle the uncommon cases (Bedrock, multi-platform, custom). The user writes config only when auto-detection fails.

## Follow-Up Questions

1. **Q12g-F1**: How should `glint build` handle instruction-only platforms (Cursor, GitHub Copilot) at T3-T4 trust tiers? Advisory governance with no runtime enforcement may not satisfy compliance requirements. Compensating controls (pre-commit hooks, CI gates) are needed but the schema doesn't express them. Should there be a `compensatingControls` section?
2. **Q12g-F2**: Should the `targets` map support custom platform plugins? The current schema hardcodes 7 platforms. A `"custom"` platform type with user-defined emitter config would allow glint to govern proprietary agent frameworks without schema changes.
3. **Q12g-F3**: How should `glint.json` interact with monorepo structures? A monorepo might have multiple agent workspaces, each with its own `glint.json`. Should there be a root-level `glint.json` that provides shared core config inherited by workspace-level configs?
4. **Q12g-F4**: Should the `$schema` URL support version ranges or pinning? `latest.json` is convenient but may break on schema updates. Pinned versions (`v2.json`) are stable but require manual updates. What's the right default for `glint init`?
5. **Q12g-F5**: How should platform-specific `config` objects be validated? The TypeScript union type (`PlatformSpecificConfig`) works at compile time, but JSON Schema conditional validation (`if platform == "openclaw"`) is more complex. What's the right JSON Schema pattern for polymorphic target config?
