## Answer

Three experiments confirm that Craftworks atoms provide deep, ready-to-use infrastructure for claws's core capabilities across all three investigation areas.

### Area 1: CREST-to-OC File Mapping (exp-a)

**7 of 12 OC file types** benefit from CREST pattern reuse:
- **3 DIRECT** (AGENTS.md, skills/, lobster.yaml) — shared adapters already exist (`read-agents-md.ts`, `read-skill-dir.ts`, StageTaskIR)
- **3 EXTEND** (SOUL.md, TOOLS.md, MEMORY.md) — CREST patterns (ROLE.md reader, tool-list parser, memory-list parser) provide the parsing foundation that OC readers extend with OC-specific semantics
- **1 INSPIRE** (HEARTBEAT.md/BOOT.md) — CREST TASK.md reader's stage/gate/graph model could enhance lifecycle governance
- **5 OC-STANDALONE** (IDENTITY.md, USER.md, BOOTSTRAP.md, openclaw.json, canvas/) — OC-specific concepts but still use shared FORMA infrastructure

Critical finding: The **OCWorkspaceIR is already the bridge**. `readOCWorkspaceViaFORMA()` runs FORMA as primary parser with heuristic shadow comparison. `projectFormaToOCWorkspace()` type-safely projects FormaIR to OCWorkspaceIR (no `as` casts). claws's parser reuses this entire infrastructure by defining `openclaw.format.yaml` and projecting FormaIR to GovernanceIR.

### Area 2: Tension Analysis for Governance Conflicts (exp-b)

**5 of 7** Q12j conflict categories map to cross-cluster tensions that `negotiateTension()` auto-resolves:
- DENY-vs-TOOL: A (governance) > D (execution) — boundary wins
- TRUST-ESCALATION: B (authority) > D (execution) — trust tier wins
- OBO-WITHOUT-ELICIT: A (governance) > F (social) — consent wins
- DATA-LABEL-MISMATCH: A (governance) > D (execution) — containment wins
- SCHEDULE-NO-APPROVAL: B (authority) > D (execution) — approval wins

**1 category** (CIRCULAR-DELEGATION) maps to same-cluster escalation (E vs E) — human review required. **1 category** (SKILL-TOOL-GHOST) is referential integrity, better handled by G1 assertions.

Critical finding: **The tension model is both a runtime negotiation tool AND a compile-time governance lint.** The existing synonym detection (10 curated pairs), duplicate rejection, and schema validation from `role-md-reader.ts` already catch incoherent boundary declarations at parse time. Custom `priorityOverride` in `negotiateTension()` lets enterprises tune their governance priority ordering via `openclaw.json`.

### Area 3: Eval Framework for `claws test` (exp-c)

The existing 4-tier eval architecture maps naturally to governance testing:
- **G0 (from L0)**: Schema validation — pure predicates, free, instant. Workspace files parse, required files present, frontmatter valid.
- **G1 (from L1)**: Cross-file integrity — pure cross-file predicates. Q12j's 7 conflict categories, referential integrity, trust tier consistency. Fast enough for pre-commit hooks.
- **G2 (from L2)**: Semantic governance — LLM-as-judge with governance-specific rubrics. Boundary specificity, tool coverage, boundary-tool alignment scoring.
- **G3 (from L3)**: Runtime enforcement — Mock OC Gateway executes compiled governance. Verifies "tool call blocked", "approval requested", "audit event recorded".

Critical finding: **The eval framework needs no modification — only governance-specific content.** Rubric YAML, assertion builders, and a Mock Gateway adapter. The type system (`EvalTierResult`, `EvalAssertionResult`, `EvalJudgeCriterionScore`), judge execution, pass^k consistency, baseline comparison, section ablation, and JSON output envelope all transfer directly. CI integration via `claws test --ci --max-tier G1` outputs SARIF for GitHub Code Scanning.

## Key Principles

1. **The FORMA dual-path architecture is the reuse mechanism.** OC readers are not standalone — they are FORMA-aware through `readOCWorkspaceViaFORMA()`. claws's parser reuses FORMA, not individual readers.

2. **Tension clusters encode governance priority.** The 7-cluster model (A-G) with configurable priority ordering directly expresses enterprise governance hierarchy. 5/7 cross-file conflicts auto-resolve; 1 escalates; 1 is referential.

3. **Progressive disclosure applies to governance testing.** G0+G1 is free and fast (pre-commit). G2 requires an LLM (CI). G3 requires Mock Gateway (CD). Same `claws test` command, escalating depth via `--max-tier`.

4. **The eval framework is content-driven, not code-driven.** Adding governance evaluation means writing YAML rubrics and scenario files, not modifying the eval engine. The 5 eval atoms (A129, A229, A237, A238, A203) provide the execution infrastructure.

5. **The tension model is dual-use: compile-time lint + runtime negotiation.** Same `negotiateTension()` function powers both `claws pinch` (static conflict detection) and OC Gateway (runtime agent-agent conflict resolution).

## Follow-Up Questions

1. **Should claws ship `openclaw.format.yaml` as a FORMA mapping file?** This would let claws use the FORMA dual-path architecture out of the box, rather than relying on heuristic-only readers. The CREST format mapping is 170 lines and covers 13 files — OC would need ~80 lines for 9 files.

2. **Should the tension priority ordering be governance-domain-specific or reuse the default A>C>B>D>F>E>G?** For enterprise governance, cluster A (safety/governance) should always be highest priority. The current default already has A first, but organizations may want B (authority/compliance) higher than C.

3. **Should G2 governance rubrics be bundled with claws or maintained separately?** The existing eval rubric system loads from `config/rubrics/` with `loadRubric(name)`. Governance rubrics could live in `@claws/governance/config/rubrics/` or be user-provided.

4. **What is the right granularity for governance scenarios?** One scenario per conflict category (7 total) or per tool/boundary combination (potentially hundreds)? The pass^k pattern suggests per-category with k=3 for workspace graduation.

5. **Should SKILL-TOOL-GHOST detection use semantic matching or exact string match?** The current OC skill reader stores tool names as strings. If TOOLS.md uses `postgres-cli` but a skill references `postgres`, should that be a ghost or a match? Fuzzy matching adds complexity.
