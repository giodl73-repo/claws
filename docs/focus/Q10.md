# Q12j: What is the compilation model for agent governance?

**Priority**: Critical
**Status**: Proposed
**Owner**: giodl
**Resolves**: How the compiler reads 9 OpenClaw workspace files and emits typed governance enforcement code; the source language (workspace files), intermediate representation (governance IR), optimization passes, and emission targets (TypeScript/Python/JSON); whether the "compiler" identity changes the name (glint → claws / typeclaw); guard library architecture
**Blocks**: Compiler implementation, name finalization, guard library design, astro integration
**Experiments**: a, b, c, d (4 total, 4 complete)

---

## Question

Q12i proved glint is a real compiler: it reads workspace files and emits executable
TypeScript enforcement programs. But we haven't designed the compilation model itself.

The Craftworks astro compiler already has a pipeline:
```
prose → parse → IR → optimize → emit
```

The governance compiler needs the same rigor. The input is 9 OpenClaw workspace files.
The output is typed enforcement code. What happens in between?

### The Source Language

OpenClaw workspaces have 9 files that define an agent's identity, capabilities, and behavior:

| # | File | What it defines | Governance signal |
|---|------|----------------|------------------|
| 1 | SOUL.md | Identity, personality, behavioral constraints | WHO the agent is, what it must/must not do |
| 2 | AGENTS.md | Subagent definitions, delegation config | WHO the agent can talk to, with what authority |
| 3 | TOOLS.md | Tool definitions, permissions, capabilities | WHAT the agent can do (the capability surface) |
| 4 | IDENTITY.md | Agent roles, SSO/RBAC binding | HOW the agent authenticates |
| 5 | USER.md | User preferences, context | WHOSE authority the agent acts under |
| 6 | MEMORY.md | Memory config, knowledge bases | WHAT the agent remembers (data governance) |
| 7 | HEARTBEAT.md | Cron jobs, scheduled tasks | WHEN the agent acts autonomously |
| 8 | skills/ | Installed skills (Markdown + TS) | HOW the agent extends its capabilities |
| 9 | lobster.yaml | Workflow definitions | HOW the agent orchestrates multi-step work |

Each file is a facet of the agent's **mechanical intent** — what the agent CAN do, IS
configured to do, and SHOULD be allowed to do. The compiler's job is to:

1. **Parse** each file into a typed representation
2. **Extract** mechanical intents (capabilities, permissions, trust relationships)
3. **Apply** governance rules (G-CLASS, G-A2A, G-ELICIT, G-INPUT, etc.)
4. **Optimize** (dead-code eliminate rules that don't apply, merge redundant checks)
5. **Emit** platform-native enforcement code (TypeScript for OC, Python for LangGraph, etc.)

### The Name Question (Reopened)

The compiler identity changes the name calculus:

| Name | Identity it signals | Strength | Weakness |
|------|-------------------|----------|----------|
| `glint` | Governance linter | Community vibe, modern DX | Undersells the compiler; "linters" don't generate code |
| `claws` | Claw compiler ({lang}c convention) | Compiler identity clear, OC-native | Weakens with managed agents (Q12d) |
| `typeclaw` | TypeScript-for-Claw (like TypeScript-for-JS) | "Types" for your agent; typed governance | 8 chars; pronunciation ("type-claw"?) |
| `tsc` analogy | TypeClaw = tsc for agents | Strong compiler precedent | Collision with TypeScript's tsc |

### Hypothesis

The compilation model has 5 phases:

1. **PARSE** — Read 9 workspace files into a typed AST (GovernanceAST)
2. **EXTRACT** — Walk the AST to extract mechanical intents (CapabilityManifest)
3. **ANALYZE** — Apply governance rules against the manifest (GovAnalysis with violations/warnings)
4. **OPTIMIZE** — Dead-code eliminate rules that don't apply to this workspace's tools
5. **EMIT** — Generate platform-native enforcement code from the analysis

The governance IR (intermediate representation) is the CapabilityManifest + GovAnalysis.
This is what `glint compile` produces. `glint build` takes the IR and emits code.

For the name: if the compiler identity is primary, `claws` or `typeclaw` earns its place.
If the cross-platform linter identity is primary, `glint` is correct. The answer depends on
what the BUYER perceives as the value — "types for my agents" or "lint for my agents."

## Working Notes

### The Astro Parallel

The Craftworks astro compiler has this pipeline:

```
CREST prose → parse → FormaIR → optimize (boost passes) → emit (platform targets)
```

The governance compiler parallels it:

```
Workspace files → parse → GovernanceIR → optimize (dead-code) → emit (TS/Python/JSON)
```

Both are compilers. Both have an IR. Both have optimization passes. Both emit to multiple
targets. The governance compiler is the GUARD counterpart to astro's CRAFT compiler.

### The "TypeScript for JavaScript" Analogy

TypeScript didn't replace JavaScript. It added a type system that catches errors at compile
time and emits plain JavaScript. The value proposition:

```
JavaScript → TypeScript → safer JavaScript
Workspace → TypeClaw → safer workspace + enforcement code
```

If we call it TypeClaw, the pitch writes itself:
- "TypeClaw adds types to your agent workspace"
- "Like TypeScript made JavaScript safe, TypeClaw makes agents safe"
- "TypeClaw: a type system for AI agents"

But: TypeClaw is 8 chars. And "TypeScript" only works as an analogy if people already
understand the TS→JS relationship.

### Skills Are Specs, Not Just Prompts

Most OC skills are SKILL.md — natural language prompts. The agent reads them and hopefully
follows them. But they're actually SPECIFICATIONS for behavior:

```
SKILL.md (spec):  "draft emails, never send without asking"
guard.ts (code):  if (tool.name === "send-email") { await elicit(user); }
```

The prompt DESCRIBES the intent. The compiled TypeScript ENFORCES the intent.
The compiler reads the natural language spec and generates the enforcement code.

This is the astro parallel:
- astro: CREST prose → FormaIR → platform code
- governance: SKILL.md prose → GovernanceIR → TypeScript guards

Every SKILL.md in the workspace is a governance source file. The compiler extracts
mechanical intents from the natural language and emits typed enforcement code.

### What the Compiler Actually Produces (Example)

Input: TOOLS.md
```markdown
## Tools
- web-search: Search the web for information
- file-write: Write files to the workspace
- send-email: Send emails on behalf of the user
```

GovernanceIR (extracted):
```typescript
{
  tools: [
    { name: "web-search", risk: "R1", capabilities: ["READ"], dataLabels: ["PUBLIC"] },
    { name: "file-write", risk: "R3", capabilities: ["WRITE"], dataLabels: ["INTERNAL"] },
    { name: "send-email", risk: "R5", capabilities: ["COMMUNICATE"], obo: true, 
      dataLabels: ["CONFIDENTIAL"], elicitation: "REQUIRED" }
  ]
}
```

Emitted TypeScript (guard handler):
```typescript
export async function classifyTool(toolName: string): Promise<Classification> {
  const table = {
    "web-search": { risk: 1, capabilities: ["READ"], failMode: "open" },
    "file-write": { risk: 3, capabilities: ["WRITE"], failMode: "closed" },
    "send-email": { risk: 5, capabilities: ["COMMUNICATE"], failMode: "closed",
                    obo: true, elicitation: { mode: "inline", timeout: 300, denyDefault: true } }
  };
  return table[toolName] ?? { risk: 3, capabilities: ["UNKNOWN"], failMode: "closed" };
}
```

This IS compilation. Source → IR → optimized code.

## Answer

**The governance compiler is a 5-phase pipeline (PARSE, EXTRACT, ANALYZE, OPTIMIZE, EMIT) that reads 9 OpenClaw workspace files, builds a GovernanceIR, applies 29 rules, dead-code eliminates inapplicable governance, and emits platform-native enforcement code. The compiler also performs workflow inversion — reading lobster.yaml and injecting governance steps into the DAG automatically. The name should change from `glint` to `sigil` (governance sigils = typed enforcement symbols).**

### The 5-Phase Pipeline

```
Workspace files      glint compile (phases 1-3)         glint build (phases 4-5)
(9 source files)    ┌──────────────────────────┐    ┌──────────────────────┐
  SOUL.md           │                          │    │                      │
  AGENTS.md         │ 1. PARSE → GovernanceAST │    │ 4. OPTIMIZE          │
  TOOLS.md     ──→  │ 2. EXTRACT → Manifest    │──→ │    (dead-code elim)  │──→ Platform code
  IDENTITY.md       │ 3. ANALYZE → GovAnalysis │    │ 5. EMIT              │    (TS/Python/
  USER.md           │              (29 rules)  │    │    (per-platform)    │     JSON/YAML)
  MEMORY.md         └──────────────────────────┘    └──────────────────────┘
  HEARTBEAT.md               │
  skills/                    ▼
  lobster.yaml       GovernanceIR (serialized, inspectable, diffable)
```

### Phase Summary

| Phase | Input | Output | Latency | Maps to |
|-------|-------|--------|---------|---------|
| 1. PARSE | 9 workspace files | GovernanceAST (typed tree, ~200 node types) | <100ms | `glint compile` |
| 2. EXTRACT | GovernanceAST | CapabilityManifest (flat, queryable) | <50ms | `glint compile` |
| 3. ANALYZE | CapabilityManifest + glint.json | GovAnalysis (violations, warnings, enforcement plan) | <200ms | `glint compile`, `glint pinch` |
| 4. OPTIMIZE | GovAnalysis | OptimizedPlan (dead rules removed, checks merged) | <50ms | `glint build` |
| 5. EMIT | OptimizedPlan | Platform code (TS, Python, JSON, YAML, markdown) | <100ms | `glint build <target>` |

### The GovernanceIR

The IR is the stable pivot between analysis and emission:

```typescript
interface GovernanceIR {
  readonly version: 1;
  readonly manifest: CapabilityManifest;   // what the agent CAN do
  readonly analysis: GovAnalysis;          // what the rules SAY about it
  readonly hash: string;                   // for incremental recompilation
}
```

`glint compile` produces this. `glint build` consumes it. `glint inspect` displays it. `glint diff` compares two. It is serialized to `.glint/compiled/governance-ir.json`.

### Mechanical Intent Extraction

Each workspace file produces typed intents. The compiler pattern-matches natural language against keyword tables:

| File | Intent types | Example |
|------|------------|---------|
| SOUL.md | DenyIntent, ElicitIntent, RequireIntent, LimitIntent, LabelIntent | "Never access production" → `DenyIntent { scope: 'tool', pattern: 'prod-*' }` |
| TOOLS.md | ToolManifestEntry (risk R1-R5, capabilities, OBO detection) | Tool with "send email on behalf of" → R5/OBO/COMMUNICATE |
| AGENTS.md | DelegationIntent, graph analysis (circular, escalation) | Subagent with R4 tools under T2 parent → TRUST ESCALATION conflict |
| IDENTITY.md | IdentityIntent (auth method, attestation L0-L3) | SSO config → L2 attestation |
| USER.md | AuthorityIntent (OBO scope, data access) | "You may send emails" → oboScope includes send-email |
| MEMORY.md | MemoryIntent (labels, retention) | "Customer data (confidential, 30d)" → CONFIDENTIAL label |
| HEARTBEAT.md | ScheduleIntent (risk derived from tools) | Hourly email schedule → R5, approvalRequired: true |
| skills/ | SkillIntent (capabilities, supply chain) | Unsigned marketplace skill → G-SUPPLY warning |
| lobster.yaml | WorkflowIntent (DAG, data flow, governance injection points) | Step uses send-email → inject elicit-step before |

### Cross-File Conflict Detection (7 Categories)

| Conflict | Files | Severity |
|----------|-------|----------|
| DENY vs TOOL | SOUL.md vs TOOLS.md | Error |
| TRUST ESCALATION | AGENTS.md vs parent tier | Error |
| OBO WITHOUT ELICIT | TOOLS.md vs SOUL.md/USER.md | Warning (strict: Error) |
| DATA LABEL MISMATCH | MEMORY.md vs AGENTS.md | Error |
| CIRCULAR DELEGATION | AGENTS.md internal | Error |
| SKILL-TOOL GHOST | skills/ vs TOOLS.md | Warning |
| SCHEDULE NO APPROVAL | HEARTBEAT.md vs TOOLS.md | Error |

### Workflow Inversion

The compiler reads `lobster.yaml`, identifies governance-sensitive steps (R3+ tools, OBO actions, A2A delegation, sensitive data), and INJECTS governance steps into the DAG:

```
Input:  trigger → research → draft → send-email → respond
Output: trigger → glint-classify-research → research → draft →
        glint-elicit-send-email → send-email → glint-audit-send-email → respond
```

The compiler emits both the rewritten workflow (`lobster.compiled.yaml`) and the skill handlers those steps call. "We create the skills and the workflows call us."

### The Guard Library

`glint build openclaw` generates:

| Component | Files | Layer |
|-----------|-------|-------|
| Governance skill | `skills/glint-governance/` (SKILL.md + guard.ts + 5 step modules) | L1: advisory + workflow steps |
| Tool hook | `hooks/glint-guard.ts` | L2: enforcement |
| Gateway plugin | `plugins/glint-gateway/` | L3: A2A + output |
| Runtime engine | `.glint/runtime/` (classify, elicit, audit, a2a, filters, budget) | Shared library |
| Compiled data | `.glint/compiled/` (tables, matrices, IR) | Generated config |

Guard composition pipeline: classify → checkBudget → checkA2A → filterInput → elicit → EXECUTE → validateOutput → audit. Eight extension points for custom guards. Custom guards can DENY but cannot override governance DENYs.

### The Name

The compiler identity changes the name calculus. `glint` scores 4/10 on compiler signal ("lint" implies reporting, not code generation). The recommendation from the bakeoff is `sigil`:

- **Programming sigils ARE type markers** ($, @, %). The tool adds type-like governance to agent workspaces.
- **Cross-platform** (9/10) — works for any agent, not just OpenClaw.
- **Compiler signal** (7/10) — sigils are CREATED, not just checked. "sigil build" implies generation.
- **5 chars**, pronounceable, low collision risk.
- **Weighted score**: 7.65 vs glint's 6.6.

### Bottom Line

This is a real compiler with a real IR. The 5-phase pipeline transforms natural language workspace files into typed enforcement code through mechanical intent extraction, cross-file conflict detection, governance rule analysis, dead-code optimization, and multi-platform emission. The workflow inversion feature — automatically injecting governance steps into workflow DAGs — is the capability that no linter can match. The tool deserves a name that says "compiler," and `sigil` delivers that signal.

## Key Principles

### d: The name must signal "this generates code" — linter names undersell the compiler identity

- `glint` scores 4/10 on compiler signal because "lint" implies reporting, not code generation
- `sigil` scores 7.65/10 weighted — programming sigils are type markers, cross-platform, and imply creation
- The symbolic name family (sigil, glyph, rune) outperforms acronyms (agc, goc) and branded names (claws, typeclaw)
- Cross-platform (9/10) beats OC-specific (3-4/10) for a tool that governs 7+ platforms
- Collision safety eliminates otherwise strong names (forge at 2/10)

> **Principle: The CLI name is a positioning statement.** A name that says "linter" attracts linter expectations (report findings, exit non-zero). A name that says "compiler" attracts compiler expectations (generate code, optimize, emit). The tool is a compiler. The name should say so.

---

### c: The guard library is a layered architecture — runtime engine + generated config, with 8 extension points

- Runtime engine (`.glint/runtime/`): classification, elicitation, audit, A2A, filters, budget — stable API, upgrades with the tool
- Generated config (skills, hooks, plugins, compiled tables): changes when workspace files change — fast recompilation (<500ms)
- 8-stage composition pipeline with 8 extension points for custom guards
- Custom guards can DENY but cannot override governance DENYs — security invariant preserved
- Workflow step modules (classify-step, elicit-step, audit-step, a2a-check-step, data-label-step) are the realization of workflow inversion

> **Principle: Separate the engine from the data.** The runtime engine is semver-stable code that rarely changes. The generated config is workspace-specific data that changes with every `glint build`. This separation makes recompilation fast and custom extensions safe.

---

### b: Mechanical intent extraction turns natural language constraints into typed enforcement across 9 file types

- 5 intent types: DenyIntent, ElicitIntent, RequireIntent, LimitIntent, LabelIntent
- SOUL.md extraction uses keyword-anchored patterns with confidence scoring (0.0-1.0)
- TOOLS.md extraction uses capability keyword tables for automatic risk classification (R1-R5)
- 7 cross-file conflict categories catch contradictions no single-file linter can find
- Skills are the supply chain attack surface — static analysis of TypeScript handlers catches undeclared tool usage
- The OBO boundary is enforceable across 4 files (TOOLS, SOUL, USER, AGENTS)

> **Principle: Every workspace file is a governance source file.** SOUL.md is not a prompt — it is a specification of behavioral constraints. TOOLS.md is not a list — it is a capability declaration. The compiler treats each file as a source language with extractable mechanical intents.

---

### a: The compilation pipeline has 5 phases that map directly to glint's command surface

- PARSE (<100ms): 9 files → GovernanceAST with graceful missing-file handling
- EXTRACT (<50ms): AST → CapabilityManifest (flat, queryable, all intents merged)
- ANALYZE (<200ms): Manifest → GovAnalysis (29 rules, violations, enforcement plan)
- OPTIMIZE (<50ms): Dead-code eliminate, merge redundant checks, compress tables
- EMIT (<100ms): Platform-native code (TypeScript, Python, JSON, YAML, markdown)
- Total pipeline: <500ms for `glint build`, <350ms for `glint pinch`
- The GovernanceIR is the stable pivot — serializable, inspectable, diffable, cacheable

> **Principle: The GovernanceIR is the compilation contract.** Everything before it (PARSE, EXTRACT, ANALYZE) is analysis. Everything after it (OPTIMIZE, EMIT) is code generation. `glint compile` produces the IR. `glint build` consumes it. This decoupling enables incremental recompilation and multi-target emission from a single analysis pass.

## Model Evolution

| Round | Model | What killed it |
|-------|-------|----------------|
| Pre-Q12j | "glint is a linter with code generation" | Q12j exp-a: it has a 5-phase pipeline with IR, optimizer, and multi-target emitter. That's a compiler, not a linter. |
| exp-a | Pipeline designed, IR types defined | exp-b: intent extraction needs per-file extractors with confidence scoring. The pipeline is real but the extraction detail was missing. |
| exp-a+b | Pipeline + extraction | exp-c: the guard library needs a composition pipeline with extension points. Raw code generation isn't enough — guards must compose, extend, and test. |
| exp-a+b+c | **Pipeline + extraction + guard library + workflow inversion** | exp-d: the name doesn't match. `glint` says "linter." The tool is a compiler. `sigil` fits. |

## Design Impact

- **Name**: Recommendation to change from `glint` to `sigil`. GLINT-MAP.md, all design docs, and CLAUDE.md references would update. Pending boss approval.
- **GLINT-MAP.md**: `glint compile` now has a spec (produces GovernanceIR). `glint build` emits `lobster.compiled.yaml` alongside skills/hooks/plugins. `glint inspect` reads the IR. `glint diff` compares two IRs.
- **Q12i**: The 5 runtime enforcement layers are the CONSUME side of what the compiler PRODUCES. The guard library (exp-c) is what `glint init` installs.
- **Q12h**: All 29 governance rules are ANALYZE passes in the compiler. Rule skipping in ANALYZE maps to dead-code elimination in OPTIMIZE.
- **Astro integration**: The governance compiler is the guard counterpart to astro's craft compiler. Same architecture: prose → parse → IR → optimize → emit.
- **Q12g schema**: `glint.json` (or `sigil.json`) needs `customGuards` section for extension points.

## Confidence

- **a** (Compilation pipeline): **High** — the 5-phase pipeline parallels the astro compiler exactly. The type definitions are complete and internally consistent. Performance budget (<500ms) is achievable given the small input size (9 files).
- **b** (Mechanical intent extraction): **High with caveat** — keyword-based extraction handles ~70% of SOUL.md constraints confidently. The remaining ~30% require either LLM assistance or user rephrasing. The cross-file conflict detection is structurally sound.
- **c** (Guard library architecture): **High** — the engine/config separation is a proven pattern (webpack config vs webpack core). The composition pipeline design is straightforward. Extension points are well-bounded.
- **d** (Name bakeoff): **Medium** — name choices are inherently subjective. The weighted rubric provides structure, but the boss's preference is the ultimate tiebreaker. `sigil` leads on the rubric; `glint` may still win on familiarity and existing design doc momentum.
