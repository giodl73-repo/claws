## Question

Q12j designed the compilation model: 5-phase pipeline, GovernanceIR, mechanical intent
extraction, guard library codegen. Q12i designed the 5 insertion points. But what POWERS
the generated code?

Craftworks has three SDKs with rich runtime libraries:

### compiler-sdk (the astro compiler)
- **RELAX** — typed expression engine (parser, type-checker, evaluator, push-down). Spec 139.
  Already used for entity validation, safety guards, sync predicates.
  Could power: policy rule evaluation, data flow predicates, A2A trust expressions.
- **Format readers** — OC, CC, CUR, OAI, CLN, CDX, AGT, GEM. 8 platform readers.
  Could power: workspace parsing (Phase 1 PARSE — already done by readers).
- **Format emitters** — multi-platform output generation.
  Could power: Phase 5 EMIT (already done by emitters).
- **CREST parser** — 13-file workspace parser with YAML concept readers.
  Could power: mechanical intent extraction from workspace files.
- **Meta-format adapters** — SKILL.md + AGENTS.md reader/emitter.
  Could power: skill generation and AGENTS.md governance.
- **PRESS IR** — token optimization (bipartite-split, cache, position optimizer).
  Could power: optimizing generated prompt content in governance skills.
- **SchemaIR** — entity schema compilation (3-pass: parse, validate, emit).
  Could power: configuration schema validation in generated skills.
- **where: compile pipeline** — RELAX where-clause compilation.
  Could power: compiled query expressions in governance rules.

### agent-sdk (the agent runtime)
- **execute/** — Task FSM, dispatch, memory management.
  Could power: generated skills that coordinate multi-step governance workflows.
- **govern/** — Budgets, CGR (Compliance Governance Record), signals.
  Could power: budget enforcement in generated skills (G-BOUND).
- **eval/** — Evaluation framework (rubrics, judges).
  Could power: quality gates in generated skills — "is this output safe?"
- **suite/** — Gates, handshake (H1-H7), intervention ladder, audit chain.
  Could power: handshake integration (generated skill triggers H1 check).
- **diffgram/** — DiffGram / sync engine.
  Could power: drift detection in generated skills (compare current vs baseline).
- **discovery/** — Workspace discovery/scout.
  Could power: fleet scan in generated skills.
- **provider/** — Provider adapters.
  Could power: multi-model support in generated skills.

### craftworks-sdk (the SDK layer)
- **suite/wiring/** — Handler base, SDK context, JSON output.
  Could power: command dispatch in generated skills.
- **suite/config/** — Config loader.
  Could power: claws.json loading in generated skills.
- **domains/** — Command dispatch, domain logic.
  Could power: generated skills calling SDK functions.

### The Question

Not everything should be used. The generated skills run INSIDE the OpenClaw Gateway
process. They need to be:
1. **Fast** — <50ms per tool call interception
2. **Self-contained** — minimal external dependencies
3. **Secure** — can't leak Craftworks internals
4. **Testable** — `claws test` validates generated code

Which modules make the cut? What's the generated skill runtime library?

### Hypothesis

Three tiers of reuse:

1. **Direct reuse** (import into generated code): RELAX evaluator, govern/budgets,
   suite/audit, diffgram, eval framework, config loader, discovery
2. **Compile-time only** (used by claws, not in generated output): CREST parser,
   format readers/emitters, PRESS IR, SchemaIR, meta-format adapters
3. **Not applicable** (wrong abstraction): Task FSM (generated skills don't manage tasks),
   provider adapters (generated skills don't call LLMs), command dispatch (not a CLI)

The generated skill imports a thin runtime library (`@craftworks/claws-runtime`) that
bundles the direct-reuse modules. The compile-time modules stay in `@craftworks/claws`.

## Working Notes

### The RELAX Connection

RELAX (Spec 139) is a typed expression DSL with:
- Scope model with .let() local bindings
- Tiered binding resolution
- Workspace DataFrame injection
- Compile-time type-checking
- Safety guards (Formula amendment)

In claws-generated skills, RELAX expressions could be used for:

```typescript
// Policy rule: "deny tools matching prod-*"
const rule = relax.compile('tool.name matches "prod-*" and workspace.tier < 3');

// In the before_tool_call handler:
if (relax.evaluate(rule, { tool, workspace })) {
  return DENY("Policy: production tools require T3+");
}
```

This is POWERFUL. Instead of generating hardcoded if/then guards, claws generates
RELAX expressions that are:
- Type-checked at compile time
- Evaluated at runtime with workspace context
- Serializable (can be stored in .claws/policies/)
- Diffable (policy changes show as expression diffs)
- Composable (AND/OR/NOT policy combinations)

### The DataFrame Connection

DataFrames (Spec 141, materialization registry) provide:
- 3-level invalidation (workspace, consumer, runtime)
- Lazy-loaded adapters
- Tiered scoping

In claws-generated skills, DataFrames could provide:
- Tool classification table as a DataFrame
- A2A trust matrix as a DataFrame
- Audit chain as a DataFrame with materialized views
- Fleet workspace inventory as a DataFrame

### The Execute Engine — Already Built

`agent-sdk/src/execute/` contains WorkAgentSupervisor — a stage-based execution engine with:
- Multi-stage pipeline (stages with gate conditions)
- Task dispatch with dependency validation
- Gate conditions: `allTasksComplete` and `requireReview` (THIS IS THE HITL GATE)
- DelegationContext with depth limits (THIS IS THE A2A DEPTH LIMITER from Q12h)
- Token tracking, correlation IDs, resume from checkpoint
- WAL (write-ahead log) for crash recovery

This maps DIRECTLY to the claws governance workflow:

| OC workflow concept | Execute engine concept | Governance use |
|--------------------|-----------------------|---------------|
| Workflow steps | Stages | Governance pipeline stages |
| Skill invocations | Task assignments | Tool classification, A2A checks |
| Tool calls | Tasks with deps | Sequential governance checks |
| Approval gates | `gate: { requireReview: true }` | **Elicitation gates (G-ELICIT)** |
| A2A delegation | `DelegationContext` | **Delegation depth limits (G-A2A-ESCALATE)** |
| Workflow completion | Stage advancement | Audit chain finalization |

The generated governance skill doesn't need a custom FSM — it uses WorkAgentSupervisor:

```typescript
const governance = new WorkAgentSupervisor({
  name: 'claws-governance',
  stages: [
    { name: 'classify' },
    { name: 'elicit', gate: { requireReview: true } },  // HITL!
    { name: 'execute', gate: { allTasksComplete: true } },
    { name: 'audit' },
  ]
});
```

that uses RELAX for data validation, DataFrames for state management, and the eval

## Answer

**Three-tier package model**: generated code never imports @craftworks/*. Craftworks SDK powers
the compiler and the contributed libraries, but the generated TypeScript looks OC-native.

### Tier 1: @openclaw/* (5 contributed packages, OC-native APIs)

| Package | Powered by (internal) | Size |
|---------|----------------------|------|
| `@openclaw/audit-chain` | suite/audit hash chain, WAL, verify, prune, query, export | ~20KB |
| `@openclaw/budget-meter` | govern/GovernanceManager, 80/95/100% thresholds | ~8KB |
| `@openclaw/identity-bridge` | suite/permission, suite/entity-id | ~3KB |
| `@openclaw/siem-emitter` | suite/audit/export (SARIF, CEF, JSON, syslog) | ~5KB |
| `@openclaw/secret-scanner` | hashing/computeHash, pattern detection | ~4KB |

### Tier 2: @claws/runtime (thin governance helpers, <50KB)

Seven exported functions, not classes: `classify()`, `elicit()`, `audit()`, `checkA2A()`,
`checkBudget()`, `evaluatePolicy()`, `drift()`. Each composes Tier 1 packages into
governance-specific workflows. An OC developer could write them manually -- claws generates
them for consistency and correctness.

### Tier 3: @craftworks/* (compiler internal only, never in generated output)

Full SDKs used by the claws compiler: WorkAgentSupervisor (orchestrates compilation pipeline),
RELAX (compiles policy expressions to static rule tables), DataFrames (materializes workspace
context at compile time), CREST parser, format readers/emitters, PRESS IR, eval framework.

### The Bridge: RELAX compiles to rule tables

RELAX is the policy expression language. But it powers the compiler, not the runtime. At
compile time, `claws build` type-checks RELAX expressions, resolves scope bindings, and
emits either static rule arrays (common case) or inline evaluator functions (dynamic case).
At runtime, `classify()` does a fast glob-match against the pre-compiled rule table.

### The Bridge: DataFrames materialize to const objects

DataFrames provide rich workspace context at compile time. The compiler materializes tool
classification tables, A2A trust matrices, and workspace inventories, then embeds them as
`const` objects in the generated code. No MaterializationRegistry at runtime.

### Module Audit Results

- **26 modules DIRECT-REUSE** (power @openclaw/* and @claws/runtime internally)
- **40+ modules COMPILE-TIME-ONLY** (used by claws compiler, never in output)
- **30+ modules NOT-APPLICABLE** (wrong abstraction for governance skills)
- **Combined runtime size: ~95-110KB** (well under 500KB budget)

### Generated Code Test

"Would an OC developer reading this generated code understand it without knowing Craftworks
exists?" Yes. Generated skills use standard OC skill patterns (onToolCall, execute), familiar
npm packages (@openclaw/*), plain TypeScript, simple data structures, and standard async/await.
No monads, FSMs, IRs, or unfamiliar abstractions.

## Key Principles

(Reverse order -- most important last)

7. **Size discipline**: Combined runtime (@openclaw/* + @claws/runtime) under 100KB. Comparable
   to a typical OC plugin. Tree-shakeable -- generated skills only import what they use.

6. **Eval compiles to patterns**: Quality gates in generated skills are regex arrays and
   threshold constants, not rubric loaders or LLM judge calls. Complex quality checks
   use the Gateway's model via OC-native APIs.

5. **DataFrames materialize to constants**: Workspace context (tool classifications, trust
   matrices, fleet inventories) is materialized at compile time and embedded as const
   objects. No runtime materialization registry.

4. **RELAX compiles to rule tables**: Policy expressions are type-checked and evaluated at
   compile time, then emitted as static rule arrays or inline functions. The RELAX evaluator,
   scope resolver, and type checker are compile-time-only.

3. **Thin helpers, not frameworks**: @claws/runtime exports 7 functions, not classes. No
   `new GovernanceWorkflow()`. No supervisor. No FSM. Each function takes plain arguments
   and returns plain objects.

2. **Contributed packages look native**: @openclaw/* packages have OC-idiomatic APIs
   (AuditChain.open(), BudgetMeter.create()). Powered by Craftworks internals but the
   OC developer never sees them.

1. **Generated code passes the OC developer test**: The single most important principle.
   Every line of generated code must look like something an OC developer would write
   themselves. Craftworks quality is invisible. Craftworks machinery is invisible.

## Model Evolution

The initial hypothesis proposed three tiers: direct-reuse (import into generated code),
compile-time-only, and not-applicable. The revision sharpened this into a **package-based
three-tier model** where the tiers correspond to npm package scopes:

| Hypothesis | Revised model |
|-----------|--------------|
| Direct-reuse → import into generated code | Split into Tier 1 (@openclaw/* contributed packages) and Tier 2 (@claws/runtime thin helpers). Generated code imports from both. |
| Compile-time-only → used by compiler | Tier 3 (@craftworks/* full SDKs). Compiler internal. Never in output. |
| Not-applicable → wrong abstraction | Confirmed. 30+ modules are CLI-specific, presentation-layer, or wrong-domain. |

The critical insight was that "direct reuse" does not mean "import the class." It means
"contribute the capability as an OC-native package." The capability (hash-chained audit,
budget thresholds, delegation depth limits) transfers. The abstraction (WorkAgentSupervisor,
TaskFsm, GovernanceManager) stays internal.

TaskFsm was originally classified as not-applicable ("generated skills don't manage tasks").
Revised: TaskFsm powers the internal state tracking within @claws/runtime functions, but
the FSM itself is never exposed. The generated code sees `{ allowed: boolean }`, not
`TaskState = 'pending' | 'queued' | 'running' | ...`.

## Design Impact

- **Q12j pipeline**: Phase 5 EMIT now emits code that imports @craftworks/claws-runtime
- **Q12i insertion points**: Generated code quality depends on runtime library capabilities
- **Package architecture**: New package @craftworks/claws-runtime alongside @craftworks/claws
- **RELAX spec (139)**: RELAX becomes the policy expression language for claws rules
- **DataFrames (141)**: DataFrames become the state management layer for generated skills

## Confidence

**High (0.85)**. The three-tier model is well-grounded in the existing SDK architecture.
The module audit covers all 3 SDKs comprehensively. The generated examples are realistic
and complete. Two uncertainty factors reduce confidence below 0.9:

1. OC Gateway's exact skill/hook API is evolving. Generated code patterns may need adjustment
   when the OC API stabilizes (affects elicit() integration and onToolCall signature).
2. Dynamic RELAX rules (inline evaluator functions for expressions that can't be statically
   resolved) introduce runtime code generation concerns that need a sandboxing answer (Q12p).
