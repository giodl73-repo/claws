# Q12h: What is the right security model for glint?

**Priority**: Critical
**Status**: Proposed
**Owner**: giodl
**Resolves**: Security classification beyond trust tiers; A2A (agent-to-agent) attack vectors; prompt injection defense; tool access control granularity; security incident tracking; runtime security boundaries that compile-time governance can enforce
**Blocks**: glint security rules (G5+), FE5+ fence passes, security policy templates, incident response workflow
**Experiments**: a, b, c, d, e (5 total, 5 complete)

---

## Question

The current glint design has trust tiers (T0-T4), tool governance (G3), and fence passes
(FE1-FE5). But the boss's operational experience reveals deeper security gaps:

1. **"Things it can do that it should not be able to"** — trust tiers are coarse (5 levels).
   A T2 agent with web access and file system access has very different risk profiles for
   each tool. Need per-tool or per-capability security classification.

2. **"Agent to Agent is a big attack vector"** — A2A communication (Google A2A protocol,
   OpenClaw ACP, custom agent-to-agent calls) allows one compromised agent to escalate
   through another. No governance model for inter-agent trust.

3. **"Prompt injection"** — compile-time governance can't prevent runtime injection, but it
   CAN define injection-resistant patterns (input validation rules, output sanitization,
   context isolation, tool confirmation gates).

4. **"Better security classification/mgmt"** — the boss has a security incident file for
   his Lobster deployment. Real incidents from production. Need a classification taxonomy
   that maps to governance rules.

5. **ClawPilot** — security tool used by the boss. Need to understand what it does and how
   glint complements/replaces it.

### Hypothesis

The security model has four layers:

1. **Classification layer**: Fine-grained capability classification (not just T0-T4 but
   per-tool risk scoring, data sensitivity labels, communication permissions).

2. **A2A governance layer**: Inter-agent trust policies — which agents can talk to which,
   what data can cross agent boundaries, escalation prevention.

3. **Injection defense layer**: Compile-time patterns that reduce injection surface —
   input validation rules, output guards, context isolation, tool confirmation gates.

4. **Incident layer**: Security incident tracking integrated with the audit chain —
   incident classification, automatic detection of known attack patterns, response playbooks.

These four layers extend the existing trust tier model (T0-T4) without replacing it.
Trust tiers become the COARSE gate; the four layers provide FINE-GRAINED control within
each tier.

### Elicitation / Human-in-the-Loop

The boss flagged: any **impersonation tool call is dangerous**. Specific examples:

| Action type | Example | Risk | Current defense |
|-------------|---------|------|----------------|
| **Send-as-user (OBO)** | Agent sends email as the user | Impersonation, reputation, legal | exec-approvals.json (manual) |
| **Post-as-user** | Agent posts to Slack/Teams as the user | Impersonation | **NONE** |
| **Financial transaction** | Agent processes a payment | Financial loss | **NONE** |
| **Data deletion** | Agent deletes files/records | Data loss | exec-approvals (partial) |
| **External API with user creds** | Agent calls third-party API using user's OAuth tokens | Credential abuse | **NONE** |
| **A2A delegation** | Agent A asks Agent B to act on user's behalf | Transitive impersonation | **NONE** |

The pattern: anything that **acts AS the user** (not just FOR the user) needs a human-in-the-loop gate. This is the **elicitation boundary** — the agent must elicit explicit approval before crossing it.

OpenClaw has `exec-approvals` (allowlist + runtime approval) but it's:
- Coarse (per-tool, not per-action)
- Not compile-time enforced
- Drifts from documentation (P-008)
- No timeout/deny-default

## Answer

**Four security layers extending trust tiers: Classification (per-tool R1-R5 risk scoring), A2A governance (agent identity + default-deny trust + FE6 fence pass), Injection defense (16-rule guardrail sandwich), and Elicitation gates (deny-default OBO approval). Raises OWASP Agentic Top 10 coverage from 3/10 partial to 7/10 full.**

### The Security Model

```
Trust Tier (T0-T4)          ← CEILING: can this workspace use this tool at all?
  │
  ├── Classification (R1-R5) ← FLOOR: how much governance does this tool need?
  │     READ → audit only
  │     WRITE → audit + confirmation
  │     COMMUNICATE → audit + data labels
  │     EXECUTE → audit + confirmation + sandbox
  │     TRANSACT/OBO → audit + elicitation gate
  │
  ├── A2A Governance         ← BOUNDARY: what crosses agent trust boundaries?
  │     Agent identity (L0-L3)
  │     Default-deny trust groups
  │     Data flow labels (PUBLIC→RESTRICTED)
  │     No transitive trust, chain depth limits
  │     FE6 fence pass (compile-time A2A validation)
  │
  ├── Injection Defense      ← SURFACE: what reduces the prompt injection attack surface?
  │     Input validation (G-INPUT, 4 rules)
  │     Context isolation (G-CONTEXT, 4 rules)
  │     Output guards (G-OUTPUT, 4 rules)
  │     Bounded reasoning (G-BOUND, 4 rules)
  │
  └── Elicitation Gates      ← IMPERSONATION: what needs human approval?
        OBO boundary (FOR-user vs AS-user)
        Deny-default with timeout
        Signed approval tokens
        No transitive OBO delegation
```

### New Fence Pass: FE6 (A2A Boundary Enforcement)

FE6 runs after FE1-FE5 and validates:
- Agent identity completeness
- Trust policy consistency (no contradictions)
- Transitive trust detection (flag and block)
- Data flow label coverage (every A2A channel labeled)
- Delegation scope validation (never exceeds delegator)
- Chain depth limits

### The OBO Boundary

The simplest test for whether a tool call needs an elicitation gate:

> **"Would a reasonable person expect to be asked before this happens?"**

| Action | FOR the user (no gate) | AS the user (gate required) |
|--------|----------------------|---------------------------|
| Email | Read inbox, draft response | **Send email** |
| Chat | Read messages, summarize | **Post message** |
| Finance | Check balance, generate report | **Process payment** |
| Data | Read files, search | **Delete files** |
| API | Read-only endpoints | **Write with user credentials** |
| Delegation | Ask Agent B for information | **Ask Agent B to act as user** |

### The ClawPilot Relationship

ClawPilot is advisory documentation-as-skill. glint is compile-time enforcement. They're complementary:
- ClawPilot teaches coding assistants WHAT the security risks are
- glint enforces THAT the security rules are followed
- A workspace could use both: ClawPilot for developer education, glint for governance enforcement

### Bottom Line

The security model is four layers built on top of trust tiers. Classification (R1-R5) gives per-tool granularity. A2A governance (FE6) gives inter-agent boundaries. Injection defense (16 rules) reduces the attack surface. Elicitation gates (G-ELICIT) put humans in the loop for impersonation actions. Together they raise OWASP coverage from 3/10 to 10/10 (5 full, 5 partial). The 5 partial risks are fundamentally runtime problems that compile-time governance can reduce but not eliminate — and that's the honest answer.

## Key Principles

### e: The OBO boundary is the most intuitive security primitive — "would a reasonable person expect to be asked?"

- FOR-user actions (read, draft, summarize) need no gate — the agent is assisting
- AS-user actions (send, post, pay, delete) ALWAYS need a gate — the agent is impersonating
- Deny-default with timeout: if the human doesn't respond, the action is DENIED (not approved)
- Signed approval tokens prevent Agent A from forging approval to Agent B
- OBO delegation chain: max 1 hop, original human always approves, never another agent

> **Principle: When an agent acts AS the user rather than FOR the user, the human must approve.** The "reasonable person" test is intuitive for developers, auditors, and CISOs alike — it doesn't require understanding trust tiers or risk scores to apply correctly.

---

### d: Per-tool risk scoring (R1-R5) turns trust tiers from a blunt gate into a graduated control

- Trust tier is the CEILING: "can this workspace use this tool at all?"
- Risk score is the FLOOR: "how much governance does this tool get?"
- A T2 workspace can have R1 tools (read-only, audit only) and R4 tools (execute, sandbox required) — each gets different governance
- Five capability categories (READ/WRITE/COMMUNICATE/EXECUTE/TRANSACT) map to escalating governance requirements
- Data sensitivity labels (PUBLIC through RESTRICTED) with high-water-mark escalation

> **Principle: Security classification should be per-tool, not per-workspace.** A workspace trust tier gates whether a tool is available; a tool risk score determines what governance applies. The same tool in different workspaces gets the same risk score — governance intensity follows the tool, not the environment.

---

### c: Prompt injection is a persistent threat — compile-time governance reduces the surface, not eliminates it

- 16 governance rules across 4 layers (input validation, context isolation, output guards, bounded reasoning)
- Compile-time rules emit runtime guard stubs — structural patterns that reduce the injection surface
- System prompt isolation is the #1 defense: user input must NEVER reach system instructions
- Bounded reasoning (step limits, tool limits, budget caps) is the safety net — even if injection succeeds, damage is capped
- The "guardrail sandwich": input sanitization → bounded reasoning → output validation

> **Principle: Treat prompt injection like SQL injection — you can't prevent it with one technique, but you can reduce the surface structurally.** Parameterized queries didn't "solve" SQL injection, they made it structurally harder. Compile-time injection patterns do the same for prompt injection.

---

### b: A2A governance requires default-deny trust and FE6 as a new fence pass

- No transitive trust: A trusts B, B trusts C does NOT mean A trusts C
- Agent identity at 4 levels (L0 declared through L3 attested/PKI)
- Default-deny: agents can't communicate unless explicitly allowed by trust policy
- Data flow labels: every A2A channel has a sensitivity ceiling (PUBLIC/INTERNAL/CONFIDENTIAL/RESTRICTED)
- Delegation permission ceiling: Agent B never gets more permissions than Agent A has
- FE6 validates all A2A policy at compile time — catches contradictions, wildcards, transitive chains

> **Principle: Inter-agent trust must be explicit, non-transitive, and validated at compile time.** The absence of A2A governance is why lateral movement is the #5 agentic risk. Default-deny with explicit trust groups is the only safe starting point.

---

### a: The OpenClaw security landscape validates every design decision in Q12h

- 138 CVEs, 37% malicious skills, 135K exposed instances — the threat is real and active
- OWASP Agentic Top 10 maps directly to glint's governance rules
- OC exec approvals are coarse (per-tool, not per-action), drift-prone, and runtime-only
- ClawPilot is advisory, not enforcement — glint fills the enforcement gap
- 14 of 17 attack sub-classes are partially or fully defensible at compile time

> **Principle: Design security governance against the actual threat landscape, not theoretical risks.** The 138 CVEs, 37% malicious skills, and specific attack patterns (ClawJacked, link preview exfil, CVE-2026-30741) drove concrete governance rules — not abstract security principles.
