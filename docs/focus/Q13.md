## Question

The architecture is settled: claws-sdk sits ON TOP of compiler-sdk + agent-sdk. It does NOT
import craftworks-sdk. No extraction needed — just a new composition layer.

```
compiler-sdk          agent-sdk
(RELAX, readers,      (govern, execute,
 emitters, IRs,        eval, hashing,
 PRESS, cache)         delegation)
      ↑                    ↑
      └────────┬───────────┘
               │
          claws-sdk  (NEW)
               ↑
          claws-cli  (NEW — thin, 35 commands)
```

But three deep technical questions remain:

### 1. OperationIR → TypeScript generation

OperationIR already transforms SkillIR → executable operations:
- Maps tool grants to operation types
- Classifies mechanical vs reasoning operations
- Builds dependency graphs
- **Injects ConfirmationStep for T4 skills** (this IS the elicitation gate!)
- Has effects.ts and bundler.ts

Can OperationIR be used to generate TypeScript skill code? Today it produces an IR;
claws needs it to produce ACTUAL .ts files. The lowering pipeline is:

```
SkillIR → OperationIR → ???  → TypeScript
           (exists)      (new)   (the goal)
```

### 2. QueryIR → OC data queries

QueryIR emits to 5 targets: odata, sql, graphql, fetchxml, flash-local.
Can we add a 6th target: **openclaw-memory** (OC's memory.search() API)?

Generated skills need data access. Two patterns:
- `claws compile` materializes DataFrames → const objects (compile-time)
- Generated skill calls OC's `memory.search()` at runtime (QueryIR → OC adapter)

### 3. DataFrame adapter inversion

In Craftworks, we are the host — DataFrames call our adapters.
In OC, the Gateway is the host — generated skills call OC's helpers.

```
CRAFTWORKS (we are the host):
  dataFrame.query() → our adapter → Dataverse/SQL

OPENCLAW (OC is the host):
  generatedSkill() → needs data → OC memory.search() / OC config.get()
```

The adapter interface needs to flip. How?

### Hypothesis

claws-sdk reuses 4 existing IRs and inverts 1 adapter:

1. **OperationIR** — reuse for operation classification + dependency graphs.
   NEW: add TypeScript emitter (OperationIR → .ts file). The ConfirmationStep
   maps directly to G-ELICIT.

2. **QueryIR** — reuse for data access compilation.
   NEW: add openclaw-memory target. Generated skills can query OC's memory
   system with compiled queries.

3. **PolicyIR** — reuse as-is. Already has policy-compiler.ts, policy-relax-compile.ts.
   This IS the governance rule compilation engine.

4. **PRESS (→ pinch)** — reuse with configuration. Same bipartite-split, quality-matrix,
   rewrite-rules pipeline, different domain (tokens → governance).

5. **DataFrame adapter** — INVERT. Create OC-native adapter that wraps OC's memory,
   config, and skills APIs. At compile time: materialize to const. At runtime: call
   OC helpers.

## Answer

claws-sdk composes on compiler-sdk + agent-sdk through **selective cherry-picking**: 13 modules
across 2 SDKs, zero from craftworks-sdk. The architecture works because claws-sdk and
craftworks-sdk are SIBLINGS at the same dependency level — they both compose on the same
foundation but for different domains.

### The Composition

Of 49 IR subdirectories in compiler-sdk, claws uses:
- **4 DIRECT** (PolicyIR, GovernanceIR, ToolIR, TierIR) — the governance engine, unchanged
- **4 EXTEND** (OperationIR, QueryIR, PRESS, SkillIR) — new emitters/targets added by claws-sdk
- **5 INSPIRE** (ReportIR, SchemaIR, ContextIR, RubricIR, MemoryIR) — patterns borrowed
- **36 SKIP** — Craftworks-internal (plugin system, routing, workspace management)

From agent-sdk, claws uses GovernanceManager, CGR chain, policy walker, audit trail, gates,
hashing, and eval — all via stable subpath exports.

### The Three Extensions

1. **OperationIR -> TypeScript Emitter (OP9-ts-emit)**: New pass added to the existing 8-pass
   Operation IR pipeline. The 16 AST node types each map to a TypeScript code pattern
   (sequence -> await chain, parallel -> Promise.all, confirmation -> elicitation gate, etc.).
   The existing ConfirmationStep for T4 skills maps directly to G-ELICIT. claws extends the
   trigger: inject confirmation for ANY R5 tool, not just T4 skills.

2. **QueryIR -> openclaw-memory Target**: 6th emit target for QueryIR. FilterNode ->
   memory.search() filters, ProjectionNode -> field selection, SortNode -> orderBy,
   PaginationNode -> limit/offset. AggregationNode and NavigationNode compile to client-side
   operations (lossy=true) because OC memory doesn't support server-side aggregation or
   relationships.

3. **DataFrame Adapter Inversion**: Three data access patterns in generated code:
   - Compile-time materialization: static data -> const objects (tool classifications, policies)
   - Runtime query: dynamic data -> ctx.memory.search() (agent state, session context)
   - Runtime config: admin settings -> ctx.config.get() (policy overrides, feature flags)

### The Package

claws-sdk is the 10th package in the monorepo:
- ~20 source files across 5 directories (compile, analyze, emit, optimize, adapter)
- ~15 import paths from compiler-sdk, ~5 from agent-sdk
- 2 runtime dependencies (zod, yaml)
- Standard monorepo integration (npm workspaces, tsup, vitest)

### The Critical Boundary

claws-sdk does NOT import from craftworks-sdk. Ever. craftworks-sdk is the Craftworks domain
glue (waves, plans, reviews, disciplines, handlers, makers, dreaming). claws-sdk is the OC
governance glue. They are siblings:

```
compiler-sdk + agent-sdk
       /            \
  craftworks-sdk   claws-sdk
  (Craftworks)     (OC governance)
```

## Key Principles

1. **Composition over extraction**: No code moves out of compiler-sdk or agent-sdk. claws-sdk
   imports existing modules and adds new passes/targets.

2. **Generated code is OC-native**: Craftworks abstractions stay inside claws-sdk. The customer
   sees clean TypeScript that uses `@openclaw/sdk` patterns. No `@craftworks/*` imports in
   generated output.

3. **Sibling architecture**: claws-sdk and craftworks-sdk are at the same dependency level.
   Neither imports from the other. This prevents circular dependencies and keeps the
   composition clean.

4. **Extend, don't fork**: New passes (OP9-ts-emit), new targets (openclaw-memory), new
   profiles (pinch) — all additions to existing infrastructure, not forks.

5. **Materialization boundary**: Static data embeds at compile time (const objects). Dynamic
   data queries at runtime (OC APIs). The decision is deterministic based on data volatility.

## Follow-Up Questions

1. Should QueryTargetSchema be extended in compiler-sdk, or should claws-sdk cast to any?
   Extending is cleaner but couples compiler-sdk to OC concepts.

2. Should the OP9-ts-emit pass live in compiler-sdk (available to all) or claws-sdk (OC-specific)?
   Current decision: claws-sdk. TypeScript codegen from OperationIR is OC-specific until
   proven otherwise.

3. How should claws-sdk test the TS emitter? Snapshot tests against expected output? AST
   comparison? Compile-and-run the generated code? All three are needed at different tiers.
