# Q12i: How does glint enforce governance at runtime?

**Priority**: Critical
**Status**: Proposed
**Owner**: giodl
**Resolves**: Runtime enforcement of compile-time governance rules; 5 insertion points into OpenClaw Gateway; `glint init` as the installer that wires everything up; bridge between glint pinch (compile-time) and runtime protection; how guard stubs execute
**Blocks**: glint runtime package design, OpenClaw plugin/hook integration, enterprise sidecar architecture

## Question

Q12h designed four security layers with 17 governance rules — but all at compile time. The
guard stubs glint emits need somewhere to EXECUTE. OpenClaw's Gateway has several extension
points (skills, hooks, plugins, exec-approvals). The key insight from the user:

> "If we run the tool we can install this."

`glint init` already creates `glint.json` and `.glint/`. What if it ALSO wires up the
runtime enforcement layer? When you run `glint init` in an OpenClaw workspace, it doesn't
just create governance config — it installs itself into the Gateway as a skill, a hook, a
plugin, and an exec-approvals manager. The user runs ONE command and gets compile-time
governance AND runtime enforcement.

Five insertion points exist, each with different trade-offs:

| # | Insertion point | What it intercepts | Can agent bypass it? |
|---|----------------|-------------------|---------------------|
| 1 | Governance Skill | Agent context (instructions) | YES — weakest |
| 2 | before_tool_call hook | Every tool invocation | No — gateway-level |
| 3 | Gateway Plugin | All traffic (ingest, A2A, tools, output) | No — gateway-level |
| 4 | Exec Approvals bridge | Tool execution approval | No — host-level |
| 5 | Sidecar / Reverse Proxy | All gateway traffic | No — separate process |

### Hypothesis

**Use ALL FIVE, layered.** Each layer catches what the layer above misses:

1. **Skill** (advisory): Agent sees governance instructions. Weakest but free — no config needed.
2. **Hook** (enforcement): `before_tool_call` enforces G-CLASS and G-ELICIT at the gateway. The primary enforcement point.
3. **Plugin** (A2A + data): Gateway plugin enforces G-A2A rules, intercepts inter-agent traffic, applies data flow labels.
4. **Exec bridge** (HITL): glint manages `exec-approvals.json` as the source of truth for human-in-the-loop gates.
5. **Sidecar** (enterprise): Optional separate process for total isolation, SIEM streaming, and forensics.

`glint init` installs layers 1-4 automatically. Layer 5 is opt-in for enterprise.

## Working Notes

### OpenClaw Extension Points (from web research)

**Skills**: Markdown + optional JS/TS files installed to `skills/` directory. Agent loads skill instructions into context. Can include a `guard.js` handler that runs server-side.

**Hooks**: `before_tool_call`, `after_tool_call`, `before_agent_response`. Configured in openclaw.json. Handler is a JS module that receives the tool call and can ALLOW, DENY, or MODIFY.

**Plugins**: Slot-based system (`plugins.slots.*`). Deeper integration — can intercept routing, modify agent behavior, add middleware. More powerful but more complex to install.

**Exec Approvals**: `exec-approvals.json` at the host level. Per-agent allowlists. Ask mode gates execution. Managed by `openclaw approvals set`.

**Gateway Plugin API**: The Gateway exposes a plugin lifecycle (init, onMessage, onToolCall, onAgentResponse, onA2A). Plugins can intercept any Gateway event.

### The "glint init" Installer Vision

```bash
$ glint init --template soc2

  Detected OpenClaw workspace (SOUL.md, AGENTS.md)

  Governance setup:
  ✓ Created glint.json (SOC2 baseline)
  ✓ Created .glint/ (policies, audit, cache)

  Runtime enforcement:
  ✓ Installed governance skill → skills/glint-governance/
  ✓ Configured before_tool_call hook → openclaw.json
  ✓ Registered gateway plugin → plugins.slots.governance
  ✓ Synced exec-approvals → exec-approvals.json

  4 enforcement layers active. Run 'glint pinch' to validate.
```

One command. Full stack. Compile-time + runtime.

## Answer

**Five defense-in-depth layers enforced automatically by `glint init`: governance skill (advisory), before_tool_call hook (primary tool enforcement), Gateway plugin (A2A + output guards), exec-approvals bridge (HITL backup), and optional enterprise sidecar (survives Gateway compromise). 19 of 29 rules have full compile-time + runtime enforcement. R5 fail-closed is non-negotiable. One command installs everything.**

### The Runtime Enforcement Architecture

```
COMPILE TIME (glint pinch + glint build)
  │  Validates all 29 rules
  │  Emits: classification.json, policy.json, a2a-trust.json
  │  Emits: guard stubs (hook handler, plugin module, skill)
  │
  ▼
RUNTIME (5 layers, installed by glint init)
  │
  ├── L1: Governance Skill (advisory)
  │     skills/glint-governance/SKILL.md + guard.js
  │     Agent sees classification table, OBO protocol, trust boundaries
  │     WEAKEST — agent can ignore. But free and always available.
  │
  ├── L2: before_tool_call Hook (PRIMARY for tool governance)
  │     hooks/glint-guard.js → configured in openclaw.json
  │     Enforces: G-CLASS, G-ELICIT, G-BOUND, G-PERM
  │     CANNOT BYPASS — Gateway-level, fires before every tool call
  │     Risk-based fail mode: R1-R2 open, R3-R4 configurable, R5 CLOSED
  │
  ├── L3: Gateway Plugin (PRIMARY for A2A + output)
  │     plugins/glint-gateway/index.js → plugins.slots.governance
  │     Enforces: G-A2A-* (5 rules), G-OUTPUT, G-INPUT, G-CONTEXT
  │     ONLY enforcement point for A2A governance
  │     Intercepts: messages, tool results, agent responses, A2A traffic
  │
  ├── L4: Exec Approvals Bridge (HITL backup)
  │     config/exec-approvals.json → managed by glint
  │     Enforces: G-ELICIT (backup), G-CLASS (backup)
  │     Host-level static allowlists reflecting tool classification
  │
  └── L5: Sidecar / Reverse Proxy (enterprise, optional)
        docker-compose.sidecar.yml or k8s/sidecar-deployment.yaml
        Independent process — survives Gateway compromise
        Full SIEM streaming, forensic logging, emergency kill switch
        ONLY defense if Gateway itself is exploited (CVE-2026-25253)
```

### What `glint init` Does

`glint init` detects the platform and installs all available enforcement layers automatically:

- **OpenClaw**: All 4 layers (skill + hook + plugin + exec-approvals). Creates 16 files, modifies 3 existing files. Backs up originals. One command, full stack.
- **Cursor**: Advisory only (governance section in `.cursorrules`). No runtime enforcement possible.
- **Claude Code**: Advisory + limited (CLAUDE.md instructions + tool permission restrictions).
- **AWS Bedrock**: API guardrails (topic filters, PII redaction, prompt attack detection).
- **LangGraph**: Python guard decorators + callback handler.
- **CrewAI**: YAML guard config + step callback.

OpenClaw is the only platform with all 5 insertion points. Every other platform is a subset.

### The Fail-Mode Policy

Risk-based fail mode is the core runtime decision:

| Risk | On error | Rationale |
|------|----------|-----------|
| R1-R2 | FAIL-OPEN | Don't break read-only operations for zero security benefit |
| R3-R4 | CONFIGURABLE (default: closed) | Write/execute is risky; enterprise policy decides |
| R5 | **FAIL-CLOSED (non-negotiable)** | OBO impersonation must never proceed without governance |

R5 fail-closed is enforced by `glint pinch` — the compiler REFUSES to emit a policy with R5 fail-open. This is a hard-coded safety constraint.

### 4 Gaps Where No Layer Can Operate

1. **Agent-internal reasoning** — no layer can inspect chain-of-thought. Mitigated by G-BOUND caps.
2. **Client-side rendering** — chat client behavior is outside the Gateway boundary. Mitigated by G-OUTPUT URL blocking.
3. **Direct MCP bypass** — tools accessed outside the Gateway. Mitigated by sidecar network policies.
4. **Model-level attacks** — adversarial inputs exploiting LLM behavior. Mitigated by G-INPUT surface reduction.

### Bottom Line

Runtime enforcement is not one mechanism — it's five layers stacked so each catches what the layer below misses. The skill layer is the posted speed limit. The hook layer is the speed camera. The plugin layer is the border checkpoint. The exec layer is the physical barrier. The sidecar is the external auditor watching the security cameras. `glint init` installs layers 1-4 with one command; layer 5 is opt-in for enterprise. The single most important design decision is R5 fail-closed — impersonation tools must never execute when governance is degraded.

## Key Principles

### c: Defense-in-depth requires a fail-mode policy that scales with risk — R5 is always closed

- R1-R2 (observe/read): fail-open. Don't break low-risk operations for zero security benefit.
- R3-R4 (write/execute): configurable. Enterprise policy decides the availability vs. safety trade-off.
- R5 (OBO/transact): **ALWAYS fail-closed.** This is not configurable. The compiler refuses to emit a policy with R5 fail-open.
- 19 of 29 rules have full compile-time + runtime enforcement. 4 are compile-only. 6 are runtime-heavy.
- 4 gaps exist at system boundaries (agent internals, client rendering, network bypass, model behavior) — these are fundamental limits of external governance.

> **Principle: Fail-mode policy must follow risk level, not convenience.** A uniform fail-open policy allows impersonation. A uniform fail-closed policy breaks read-only operations. Risk-based fail mode is the only policy that serves both safety and usability.

---

### b: `glint init` is an installer, not a config generator — one command wires up the full enforcement stack

- OpenClaw: creates 16 files, modifies 3, backs up originals, installs 4 enforcement layers
- Other platforms: installs what's available (advisory instructions, decorators, API guardrails)
- `--dry-run` shows every file created and every config change before executing
- `--uninstall` cleanly removes all enforcement while preserving audit trail and policy definitions
- The user runs ONE command and gets compile-time governance AND runtime enforcement

> **Principle: Runtime enforcement that requires manual wiring won't be adopted.** If glint told users "now create a hook handler, register a plugin, and update exec-approvals.json," nobody would do it. `glint init` must wire everything up automatically — the "if we run the tool we can install this" insight.

---

### a: Each enforcement layer catches what the layer below misses — 5 layers, no single point of failure

- Layer 1 (Skill): Advisory. Agent self-governs. Weakest, but always present and zero-config.
- Layer 2 (Hook): Primary tool enforcement. Gateway-level. Agent cannot bypass. Covers G-CLASS, G-ELICIT, G-BOUND.
- Layer 3 (Plugin): A2A + output enforcement. The ONLY layer that intercepts inter-agent traffic. Without it, A2A governance is advisory-only.
- Layer 4 (Exec): HITL backup. Host-level allowlists reflecting tool classification. Defense-in-depth for elicitation gates.
- Layer 5 (Sidecar): Enterprise. Separate process. Survives Gateway compromise. The only defense against CVE-2026-25253-class RCE attacks.

> **Principle: No single enforcement layer is sufficient.** The hook can't catch A2A. The plugin can't stop a compromised Gateway. Exec-approvals are static. The skill is advisory. Only all five together provide defense-in-depth. `glint init` installs 1-4 automatically; layer 5 is opt-in because it requires infrastructure changes.

| exp-b + exp-c | **5 layers: Skill + Hook + Plugin + Exec + Sidecar** | *(nothing — this holds)* |

## Design Impact

- **GLINT-MAP.md**: `glint init` behavior expands to include runtime enforcement wiring. Command #1 (`glint init`) becomes the full installer, not just config generator.
- **Q12g schema**: glint.json gains `runtime` section: `failMode` (per-risk-level), `hook` (handler path, timeout), `plugin` (module path, config), `sidecar` (container image, ports, SIEM endpoint).
- **Q12h security**: Every G-rule now has a runtime enforcement mapping (19 fully enforced, 4 compile-only, 6 runtime-heavy). The 6 "partially in scope" pitfalls from GLINT-PITFALLS.md are now addressed by specific layers.
- **Q12b upstream**: Runtime enforcement primitives (`@craftworks/glint-guard-hook`, `@craftworks/glint-gateway-plugin`) could be contributed as standalone packages.
- **GLINT-PITFALLS.md**: P-030 through P-035 (prompt injection, supply chain, excessive permissions) now have specific runtime enforcement layers.

## Follow-Up Questions

1. **Q12i-F1**: Should `glint init` detect existing hook/plugin registrations and warn about conflicts? What happens if another governance tool (e.g., ClawPilot) already occupies the `hooks.before_tool_call` slot?
2. **Q12i-F2**: How should the sidecar (Layer 5) integrate with existing service mesh infrastructure (Istio, Linkerd)? Should glint emit Envoy WASM filters instead of a standalone sidecar container?
3. **Q12i-F3**: Should the before_tool_call hook support a "challenge" response alongside ALLOW/DENY/MODIFY — where the hook asks the agent for additional justification before allowing an R4 tool?
4. **Q12i-F4**: How should runtime enforcement handle glint.json schema version upgrades? If the compiled artifacts were built with policy v1 but the runtime expects v2, what's the migration path?
5. **Q12i-F5**: Should `glint watch` (live recompilation) also hot-reload the runtime enforcement handlers? If the user changes a classification, should the hook handler pick up the new classification without Gateway restart?
