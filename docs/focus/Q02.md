# Q12b: What should Craftworks contribute upstream to OpenClaw?

**Priority**: High
**Status**: Proposed
**Owner**: giodl
**Resolves**: Which governance primitives to open-source vs keep proprietary; package naming (@openclaw/* vs @craftworks/*); upstream PR strategy; community positioning
**Blocks**: Open-source roadmap, @openclaw/ npm scope registration, ClawHub publishing strategy
**Experiments**: a, b, c, d (4 total)

---

## Question

Q11 established the strategy: "B-first (EnterpriseClaw governance product), selective upstream contributions, C-evolution (cross-platform bridge)." Q12a confirmed claws complements openclaw with zero command overlap — different layers (governance compilation vs runtime management).

But "selective upstream contributions" is vague. Which specific pieces? The governance work spans runtime primitives (audit chains, SIEM formatting, identity bridges) and compile-time engine work (policy IR, fence passes, cross-compilation). The runtime primitives could be contributed without eroding the moat. But which ones? In what order? Under what npm scope? As PRs to openclaw/openclaw or as standalone packages?

The upstream contribution strategy also serves brand positioning: Craftworks becomes "the governance authority" for OpenClaw. Contributing the right primitives creates a funnel — enterprises adopt the free runtime tools, discover they need compile-time enforcement, and buy claws.

### Hypothesis

Contribute 5 runtime governance packages under `@openclaw/` scope (audit-chain, siem-emitter, identity-bridge, secret-scanner, budget-meter) plus the workspace format spec and validator. Keep all compile-time engine work (policy IR, fence passes, trust tiers, cross-compilation, CGR, fleet orchestration) proprietary in claws. Publish specs as RFCs to establish format authority.

### The Funnel Logic


### Open Questions

1. **npm scope**: `@openclaw/audit-chain` (community-native) vs `@craftworks/audit-chain` (branded)? Community-native has better adoption but less brand. Could use `@openclaw/` for contributed packages and `@craftworks/` for proprietary.
2. **Contribution vehicle**: PRs to openclaw/openclaw (integrated into core) vs standalone packages (independent lifecycle)? PRs get wider distribution but lose control. Standalone packages keep release cadence.
3. **License**: MIT (matching OpenClaw) vs Apache 2.0 (patent protection)? MIT is simpler and matches ecosystem. Apache 2.0 adds patent grant.
4. **Timing**: Contribute before or after claws ships? Before = "good citizen" brand building. After = contributes from a position of strength.

## Answer

**Contribute 5 runtime governance packages + 1 spec PR across 3 waves (16 weeks). Keep all compile-time engine work proprietary. Ship the GuardrailProvider spec PR in week 1.**

### First PR: GuardrailProvider Spec

The single highest-leverage first contribution is a spec PR to `openclaw/openclaw` targeting issue #46441 (Pluggable Guardrail Provider Interface). It:
- Defines the `GuardrailProvider` interface (preAuthorize, postAudit, getCapabilities)
- Specifies `AuthorizationDecision` type (allow, deny, review, modify)
- Includes chain-of-responsibility provider registry
- Ships a reference `ShellExecProvider` wrapping OpenClaw's existing exec approvals
- Requires zero code extraction, zero npm infrastructure, zero foundation agreement

Submit week 1. Packages follow weeks 2-4. The spec frames the conversation; the packages prove execution.

### Bottom Line

Contribute the runtime governance layer (audit, identity, budgets, secrets, SIEM) as open-source packages. This makes Craftworks the governance standard-setter for OpenClaw's 3.2M users. Keep the compile-time engine (policy compiler, guard passes, fence enforcement, RELAX evaluation, cross-compilation) as the paid product. The free layer creates governance awareness; the paid layer delivers compile-time enforcement. Start with a spec PR in week 1 that defines the governance interface — then ship implementations that prove it.

## Key Principles

### d: Ship the GuardrailProvider spec first — define the interface before implementing it

- The spec PR scores 8.35 weighted (highest on dependency chain: 10/10, zero prerequisites)
- Addresses #46441 directly: OpenClaw has exec approvals for shell commands but no general-purpose authorization for file writes, MCP tools, browser actions, messaging
- Defines an interface architecturally congruent with Craftworks' fence passes — the compile-time version becomes the premium implementation of our own spec
- "Propose-then-prove" cadence: spec in week 1, packages in weeks 2-4, formalization specs in weeks 5-16
- Never block engineering on foundation politics — publish under @craftworks/ if @openclaw/ scope stalls

> **Principle: Define the interface before shipping the implementation.** The organization that writes the spec becomes the architecture authority. Every subsequent governance contribution — including competitors' — conforms to the contract you defined.

---

### c: The community is building ad hoc governance — fill the gap before competitors do

- 28+ thumbs-up on RBAC issue #8081; workaround tools (Pinchy, Clawprint, OpenClaw Firewall, Mission Control) validate every proposed package
- Third-party commercial products exist solely to fill governance gaps (OpenClaw Firewall for budgets, AxonFlow for audit)
- 135K exposed instances, 63% with auth disabled, 824+ malicious skills, 138+ CVEs — the governance deficit is actively exploited
- Security teams are the gatekeepers: "The demo takes ten minutes. Getting through security review takes ten weeks."
- NemoClaw, AWS Bedrock AgentCore, and Microsoft Copilot Studio are positioning as governance alternatives

> **Principle: When the community builds ad hoc solutions for a gap you can fill, ship before they consolidate.** Third-party workarounds validate demand but fragment the ecosystem. First-party governance primitives become the standard.

---

### b: Standalone monorepo with dual-scope npm — control release cadence, share the namespace

- `@openclaw/` scope for contributed packages (community-native adoption), `@craftworks/` for proprietary products (brand retention)
- Standalone monorepo (`craftworks/openclaw-governance`) beats PRs to core: maintains release cadence control, architectural integrity, and independent versioning
- MIT license matches ecosystem (zero friction); Apache 2.0 reserved for proprietary products where novel IP lives
- Never fork OpenClaw — maintenance tax and community hostility make forking catastrophically worse than any alternative
- Foundation scope agreement is prerequisite for @openclaw/ publishing; do not block on it — @craftworks/ fallback is always available

> **Principle: Control the release cadence for security-critical code.** PRs to upstream lose versioning control — a critical audit-chain fix could sit in maintainer review for weeks. Standalone packages let you hotfix in hours.

---

### a: The moat is compiler integration, not governance primitives — contribute freely

- 18 capabilities (60%) are runtime-only with High separability and S/M extraction effort
- 8 capabilities (40%) are deeply coupled to compiler IR (guard passes, RELAX evaluator, policy compiler, expression enforcement)
- RELAX is the key coupling point — 5 capabilities have RELAX dependencies; extract non-RELAX paths with injection points
- Individual primitives (audit trail, budget enforcement) are not defensible — any team could build them
- The moat is guard passes analyzing skill IR, FE5 trust-tier resolution through role hierarchies, RELAX-evaluated policies at zero token cost, CGR emission integrated with the full compilation pipeline

> **Principle: Contribute what anyone could build; keep what only you can build.** Runtime governance primitives (hash chains, OIDC validation, state machines) are implementations of standard patterns. Compile-time enforcement through the IR is the 18-month head start.

## Design Impact

- **Q11**: "Selective upstream contributions" is now concrete: 5 runtime packages + 1 spec PR + 2 specs across 3 waves
- **Q12a**: claws must consume its own upstream packages (audit-chain, siem-emitter, identity-bridge) — dog-food the open-source layer
- **claws fleet**: Free fleet-governance (drift detection) must clearly stop at "detect" — paid fleet orchestration owns "enforce"
- **SDK extraction**: craftworks-sdk and compiler-sdk need clean extraction boundaries for the 18 CONTRIBUTE capabilities
- **RELAX**: Parser-injection pattern needed for governance-rule-loader and policy-engine-core — default to prose-only mode without RELAX
- **Foundation**: Initiate contact in week 1 for @openclaw/ npm scope and RFC process — critical path item
- **Monorepo**: `craftworks/openclaw-governance` repo with npm workspaces, Changesets versioning, Vitest testing
- **Brand**: The GuardrailProvider spec PR positions Craftworks as governance architect before any package ships

## Follow-Up Questions

1. **Q12b-F1**: Should glint consume the upstream packages directly? → **Resolved: Yes, dog-food.** `glint` uses `@openclaw/audit-chain`, `@openclaw/siem-emitter`, etc. as direct dependencies. This validates the packages in production and builds credibility ("we use our own open-source layer"). Internal copies create drift risk. If upstream breaks, fix upstream.
2. **Q12b-F2**: How should the RELAX parser-injection pattern work in governance-rule-loader? → **Deferred to implementation.** Extension point API design belongs in the spec for the governance-rule-loader package. RELAX coupling is the key architectural decision — spec it when building Wave 1.
3. **Q12b-F3**: Scope boundary between free fleet-governance and paid fleet orchestration? → **Resolved: Detect vs Enforce.** Free (upstream): `drift` (detect), `scan` (discover). Paid (glint): `broadcast` (push policies), `push` (deploy artifacts), `promote` (snapshot promotion), `kill --fleet` (fleet emergency stop). The GLINT-MAP reflects this — detection is open-source, enforcement is proprietary.
4. **Q12b-F4**: Should Craftworks propose the RFC process to OpenClaw foundation? → **Resolved: Yes, Wave 2 (weeks 5-8).** Per the contribution roadmap, Week 5-8 includes governance-types and spec work. Proposing the RFC process itself is a governance-of-governance move that establishes Craftworks as the standards authority.
5. **Q12b-F5**: Telemetry in upstream packages? → **Resolved: Anonymous, opt-in.** Standard pattern: anonymous install/usage counts via package telemetry (like Next.js telemetry). No PII, opt-out with env var. Tracks: installs, daily active workspaces, which packages are co-installed. Enough to measure funnel without privacy risk.
