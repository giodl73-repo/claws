# Q12: What is the right CLI surface and operational boundary for OpenClaw enterprise users?

**Priority**: High
**Status**: Proposed
**Owner**: giodl
**Resolves**: Product CLI design for OpenClaw users; clawsc vs clawops split; snapshot/rollback/live-push operational boundary; where build-time ends and runtime begins
**Blocks**: clawsc-cli package, clawops-cli package, openclaw-sdk domain in craftworks-sdk, Q11 Phase 1 (EnterpriseClaw launch)
**Experiments**: a, b, c, d, e (5 total)

---

## Question

Q11 established that EnterpriseClaw is the right strategy. Now we need to design the product
surface. OpenClaw users don't know what Craftworks is — they need CLIs that speak their
language. Three design questions interlock:

**1. CLI Split**: Should there be one CLI (`clawsc`) or two (`clawsc` + `clawops`)? The
three-CLI split (craft/guard/fleet) exists because verb families don't mix for Craftworks
users (SU-01 §1.1). But OpenClaw users think in two modes: "govern my workspace" vs
"govern my org." Does the same separation test apply?

**2. Operational Boundary**: We have snapshots (save/restore/diff/deploy), incremental
compilation (dependency graph, targeted invalidation), amendments (runtime workspace
modifications), forest sessions (watch mode, session mode), and a context DAG (fork/sync/diff).
Where does clawsc end and clawops begin? Can a developer push a live change? Can ops roll
back a fleet to a snapshot? Where's the line?

**3. SDK Depth**: Is clawsc a thin CLI over existing craft+guard commands, or does it need
its own SDK domain? Auto-detection, terminology translation, migration advice, and quickstart
flows suggest real SDK logic — not just command aliasing.

### Hypothesis

Two CLIs (`clawsc` for developer + compliance, `clawops` for platform + CISO) with a real
SDK domain in craftworks-sdk. The boundary is: **clawsc owns single-workspace operations
including live compilation sessions; clawops owns multi-workspace operations including
fleet-wide snapshots and rollback.** Amendments and watch mode live in clawsc (they're
workspace-local). Fleet snapshots and broadcast live in clawops (they're org-wide).

### Open Design Questions

1. **Snapshot scope escalation**: Can a workspace snapshot become a fleet snapshot? (clawsc save -> clawops promote?)
2. **Live push semantics**: When `clawsc watch` detects a change and recompiles, does the new build auto-deploy? Or is deploy always explicit?
3. **Rollback granularity**: Can clawops rollback one workspace in a fleet to a snapshot while leaving others? Or is rollback always fleet-wide?
4. **Amendment + broadcast interaction**: If a workspace is amended via clawsc, does clawops drift detect that as "local change" or "policy violation"?
5. **Session mode over network**: Can a remote clawops session control a local clawsc compilation host? (fleet -> workspace command channel)
6. **Snapshot integrity across fleet**: Fleet-wide snapshot needs integrity hash over all workspace snapshots — is this the forest integrity hash or a separate fleet-level hash?

## Answer

**Two CLIs: `clawsc` (23 commands, workspace scope) and `clawops` (17 commands, fleet scope). SDK domain in `craftworks-sdk/src/domains/openclaw/` with 10 modules. The boundary is scope: clawsc owns single-workspace operations including live compilation; clawops owns multi-workspace operations including fleet snapshots. Watch mode does NOT auto-deploy. Amendments are NOT drift violations. Fleet rollback supports workspace-level granularity.**

### The Split

| CLI | Commands | Persona | Mental model | Scope |
|-----|----------|---------|-------------|-------|
| `clawsc` | 23 | Developer, Compliance | "I'm building and governing my agent" | One workspace |
| `clawops` | 17 | Platform Eng, CISO | "I'm governing my organization's agents" | All workspaces |

### Why Two, Not One or Three

**Not one**: `clawsc snapshot restore production` — is that your workspace or your entire fleet? Scope ambiguity on destructive operations is dangerous. Two CLIs make scope unambiguous by construction.

**Not three** (mirroring craft/guard/fleet): OpenClaw users see governance as integral to building. `clawsc check` is as natural as `clawsc build`. Separating them would force CLI-switching mid-workflow.

### Operational Boundary

```
                    WORKSPACE (clawsc)              FLEET (clawops)
                    ──────────────────              ────────────────
Build               compile, build, optimize        -
Govern              check, comply, assess, audit    broadcast, drift, report
Amend               amend add/remove/modify         -
Watch               watch, session                  -
Snapshot            save/restore/diff (local)       save/restore/diff (fleet)
                                                    promote (local→fleet)
Deploy              build <target>                  push (fleet-wide)
Rollback            snapshot restore (local)        rollback (fleet/team/workspace)
Emergency           -                               kill
Identity            -                               secrets, identity (SSO/RBAC)
```

### Six Design Decisions

| # | Question | Answer |
|---|----------|--------|
| 1 | Can workspace snapshot promote to fleet? | Yes, via explicit `clawops promote` |
| 2 | Does watch auto-deploy? | No. `--deploy` flag for opt-in. |
| 3 | Can rollback target one workspace? | Yes. `--workspace` and `--team` flags. |
| 4 | Are amendments drift violations? | No. Drift measures policy strength, not content. |
| 5 | Can clawops control clawsc remotely? | Phase 3. Phase 1 is filesystem-based. |
| 6 | Fleet snapshot integrity? | Two-level: per-workspace hash + fleet hash. |

### Bottom Line

`clawsc` and `clawops` are product CLIs that let OpenClaw users access the full Craftworks governance pipeline without learning Craftworks terminology. The two-CLI split matches how enterprise users actually think (my workspace vs my org) and passes the SU-01 separation test. The SDK domain in craftworks-sdk provides 10 modules of real OpenClaw-specific logic — auto-detection, terminology translation, migration advice, snapshot coordination. CLIs are thin adapters over this SDK layer, following the established monorepo pattern.

## Key Principles

### e: 40 commands across two CLIs with progressive disclosure and clean cross-references

- 23 clawsc + 17 clawops = 40 commands total
- Every command maps back to craft/guard/fleet with no orphans
- Progressive disclosure: Maker sees 4 commands, Developer sees 14, Advanced sees 23/17
- 7 collision redirects prevent common mistakes
- 3 genuinely new capabilities (promote, push, fleet snapshot) needed

> **Principle: Product CLIs are translations, not inventions.** Every clawsc/clawops command maps to an existing craft/guard/fleet operation. The value is terminology, progressive disclosure, and auto-detection — not new functionality. New capabilities should be minimal (3 fleet operations).

---

### d: SDK domain in craftworks-sdk with 10 modules — CLIs are thin adapters

- `craftworks-sdk/src/domains/openclaw/` follows the guard/fleet/review domain pattern
- 10 modules: detector, resolver, formatter, template-mapper, migration-advisor, quickstart, snapshot-manager, fleet-snapshot, push-manager, rollback-manager
- All compiler-sdk modules already exist — no new compiler code for Phase 1
- Diagnostic formatter is highest-impact module (makes clawsc feel native to OC users)

> **Principle: The SDK owns all logic; CLIs own all UX.** Detection, terminology, migration advice, snapshot coordination are domain decisions that belong in the SDK. Argument parsing, output formatting, progressive disclosure are UX decisions that belong in the CLI. Never mix them.

---

### c: The boundary is scope — workspace-local vs fleet-wide — with six resolved decisions

- 20 capabilities are workspace-local (clawsc), 13 are fleet-wide (clawops), 3 are transitional
- Watch does NOT auto-deploy (feedback yes, deployment explicit)
- Amendments are NOT drift violations (drift = policy weakness, not content change)
- Fleet rollback supports workspace-level granularity (cherry-pick from manifest)
- Snapshot promotion is the explicit bridge from workspace → fleet
- Remote session control is Phase 3 (not Phase 1)

> **Principle: Scope determines CLI, not function type.** Governance exists in both CLIs. Build exists in both (compile locally, deploy fleet-wide). The invariant is: clawsc never touches another workspace; clawops always operates across workspaces. This is simpler and safer than splitting by function.

---

### b: Two CLIs pass the SU-01 separation test — not one, not three

- 8 sentence tests confirm: build+govern-local is one family; operate+govern-fleet is another
- One CLI would create scope ambiguity on destructive operations (rollback)
- Three CLIs (mirroring craft/guard/fleet) would over-separate — OC users see governance as part of building
- Snapshot is the only cross-CLI capability (disambiguated by CLI name = scope)

> **Principle: The separation test is about personas-in-the-moment, not job titles.** A compliance officer running `clawsc check` is in "workspace" mode. The same person running `clawops report` is in "fleet" mode. The CLI split follows the mental model shift, not the org chart.

---

### a: 47 capabilities map cleanly to 30 clawsc + 24 clawops commands with zero orphans

- Build, incremental, amendment, governance, fleet, snapshot — all mapped
- Snapshots appear in both CLIs at different scopes (workspace vs fleet)
- 3 new capabilities needed: fleet push, fleet rollback, snapshot promote
- Dependency graph and targeted invalidation are internal (no user command)

> **Principle: Map capabilities bottom-up, not commands top-down.** Start from what the system can do, then design the command surface. This prevents both orphan capabilities (no command) and phantom commands (no capability). Every command should trace to a shipped or planned capability.

## Design Impact

- **SU-01 architecture**: Extends from 3 CLIs to 5 — same package, same version alignment
- **SU-04 command map**: COMMAND-MAP.md needs clawsc/clawops -> craft/guard/fleet mappings
- **craftworks-sdk**: New `domains/openclaw/` module with real SDK logic
- **compiler-sdk**: Snapshot, incremental, forest session APIs exposed for clawsc consumption
- **Praetor CP-3 (fleet)**: Fleet snapshot/broadcast/rollback are prerequisites for clawops
- **Praetor CP-5 (context DAG)**: Fork/sync/diff enable fleet-level snapshot coordination
