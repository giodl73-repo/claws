| M1  | claws-sdk/src/fleet/report.ts    | L142-155 `readKillStatus`  | **Kill sentinel path mismatch**: `readKillStatus` checks `.claws/kill.json` but the kill module (`kill.ts:59`) writes `.claws/KILL`. The report will never detect a killed workspace because it reads the wrong file. This means fleet reports silently undercount killed workspaces, a compliance visibility gap.                                                                                                                         | Change `readKillStatus` to import and use `readSentinel` from `./kill.js` (which reads `.claws/KILL`), or at minimum change the path from `'kill.json'` to `'KILL'`. | M2  | claws-sdk/src/fleet/broadcast.ts | L328-399 `broadcastPolicy` | **Sequential broadcast with no concurrency**: broadcast iterates all workspaces in a serial `for...of` loop with per-workspace I/O (trust compat check + atomic write + manifest write). For a 50-workspace fleet, this could take 5-10 seconds with each workspace doing 4-5 filesystem round-trips. The runner module (`runner.ts`) already provides `runParallel` with configurable concurrency — broadcast should use it.              | Refactor the confirm-mode loop to use `runParallel` with the existing fleet concurrency setting (default 8). The dry-run path is already fine since it does no I/O.                                                                                            |
| M3  | claws-sdk/src/fleet/broadcast.ts | L386-399                   | **Broadcast manifest written per-workspace with full fleet results**: after broadcast, every successfully-updated workspace receives a copy of the entire `BroadcastManifest` including all per-workspace results. A 100-workspace fleet writes 100 copies of a manifest containing 100 result entries. This is O(n^2) in disk writes and also leaks workspace paths across the fleet (workspace A's manifest reveals workspace B's path). | Write only a per-workspace receipt (timestamp, policyFile, reason, success status for _that_ workspace) rather than the full fleet manifest. Or write the fleet manifest to a single fleet-level location.                                                     |
| M4  | claws-sdk/src/snapshot/diff.ts   | L344-351                   | **Double manifest read per snapshot**: `diff()` reads the manifest and verifies integrity for both snapshots in the verification loop (L344-351), then reads both manifests again on L365-366 to get timestamps. Each `readManifest` call does a file read + JSON parse. This doubles the I/O for every diff operation.                                                                                                                    | Store the manifests from the verification loop and reuse them for timestamps: `const baseManifest = await readManifest(...)` before verification, then pass to `verifyManifest`.                                                                               |

## Summary

The CP-3 implementation is structurally sound with good separation of concerns — the snapshot system has proper integrity verification, the fleet scanner correctly discovers and classifies workspaces, and the kill switch has a well-designed double-kill prevention mechanism with audit chain integration. The most critical issue is M1: `report.ts` reads the wrong sentinel file path (`.claws/kill.json` instead of `.claws/KILL`), meaning fleet reports will never detect killed workspaces. The performance findings (M2, W3, W7, W8) around serial fleet operations should be addressed before production fleet sizes exceed ~20 workspaces, and the manifest leak in M3 has both performance and information-disclosure implications.
