## Findings

### Major (M)

| #   | File                     | Line/Section | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                               | Suggested fix                                                                                                                                                                                                                                      |
| --- | ------------------------ | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M1  | keys/rotate.ts           | 187-189      | **Sequential re-signing of artifacts blocks the event loop.** The `for` loop at line 187 calls `reSignArtifact` sequentially with `await` inside the loop. Each iteration reads a file, computes an Ed25519 signature, and writes a file. For a workspace with hundreds of compiled artifacts, this blocks the Gateway event loop for the entire duration. Ed25519 signing via `crypto.sign` is CPU-bound and synchronous under the hood.             | Batch artifacts and use `Promise.all` with a concurrency limiter (e.g., chunks of 10). Or use `crypto.sign` with the callback form to yield between batches. Add a total re-sign timeout (e.g., 30s) to fail fast if artifact count is extreme.    |
| M2  | keys/rotate.ts           | 45-56        | **Lock file based concurrency control is not safe — stale locks cause permanent lockout.** `acquireLock` writes a lock file and throws if it exists, but there is no staleness check. If a previous rotation crashes (OOM, SIGKILL, power failure), the lock file persists forever and all future rotations are permanently blocked. In a Gateway context, this means a single crash during rotation bricks key management until manual intervention. | Add a PID-liveness check: read the lock file, parse the PID, and check if that process is still running (`process.kill(pid, 0)`). If the PID is dead or the lock is older than a configurable timeout (e.g., 5 minutes), delete it and re-acquire. |
| M3  | keys/ceremony.ts         | 25-36        | **GF(256) lookup tables are computed eagerly at module load time via an IIFE.** This runs ~255 iterations of XOR/shift arithmetic synchronously when any file that transitively imports `ceremony.ts` is first loaded. In a Gateway plugin that imports the keys barrel (`index.ts`), this executes on every Gateway restart — adding startup latency for a feature that most users never invoke.                                                     | Lazy-initialize the tables: wrap in a `let initialized = false` guard, call from `shamirSplit`/`shamirReconstruct` on first use. Or move ceremony to a separate deep subpath import so it's not pulled in by the keys barrel.                      |
| M4  | publish/publish.ts (CLI) | 55-64        | **Real registry client uses `fetch` with no timeout, no retry, and no abort controller.** The `submit` method at line 55 calls `fetch(registryUrl, ...)` with no `AbortSignal` or timeout. If the registry is slow or unresponsive, this hangs the Gateway process indefinitely. A hanging publish blocks the entire event loop since the response is awaited.                                                                                        | Add an `AbortController` with a 30-second timeout: `const ctrl = new AbortController(); setTimeout(() => ctrl.abort(), 30_000);` and pass `signal: ctrl.signal` to fetch.                                                                          |
| M5  | keys/registry.ts         | 42-50, 56-61 | **Registry read/write is not atomic — concurrent reads during write can see partial JSON.** `readRegistry` and `writeRegistry` use plain `readFile`/`writeFile` with no locking. If two CLI invocations run `registerKey` concurrently, one can overwrite the other's entry (last-writer-wins). In a Gateway with parallel tool calls, two simultaneous `claws keys generate` invocations can corrupt the registry.                                   | Use atomic write (write to temp file, then rename) and optionally a lock file around registry mutations. At minimum, use `writeFile` with `O_TRUNC` after acquiring a flock.                                                                       |

### Warning (W)

| W1  | keys/storage.ts            | 78-79        | **EnvStorage.write mutates `process.env` at runtime.** Setting `process.env` is a global side effect visible to the entire Gateway process. Any other plugin or governance hook sharing the process can read the key material from the environment. This is a security concern in multi-tenant or multi-skill Gateway deployments.                                                       | Document that env storage is single-tenant only. Consider using an in-memory Map instead of `process.env` for the `write` path, or mark env tier as read-only (write throws, only pre-existing env vars are read). |
| W2  | keys/rotate.ts             | 194-195      | **Rollback uses `!` non-null assertion on `oldPrivateKey` and `oldPublicKey`.** If the storage `read` at line 168-169 returned `null` (e.g., key material was in env tier but env var was unset), the rollback path will write `null` as key material, silently corrupting the key. The `!` assertions suppress the type checker's warning about this.                                   | Guard with an explicit null check before rollback. If old material is null, throw a more specific error ("Cannot rollback: original key material not available") instead of writing null.                          |
| W3  | annotate/heuristics.ts     | 196-209      | **Tool name patterns are tested against skill names with no word boundary on the entire name.** A skill named "unsearchable" matches the `search` pattern (R1), and "unreadable" matches `read` (R1). A skill named "postmortem" matches `post` (R4). These false positives inflate risk scores or undercount them, and the Gateway gets governance hooks wired to incorrect risk tiers. | Use `\b` word boundaries more carefully on the name-level patterns, or match against hyphen-split segments of the skill name (since skill names use kebab-case).                                                   |
| W4  | scaffold/scaffold.ts       | 139-143      | **Scaffold loads full workspace config (`loadConfig`) just to read `trustTier`.** If `loadConfig` performs validation, file I/O on `claws.json`, or YAML parsing, this adds latency to a scaffolding operation. In a Gateway context where `claws new` is triggered by a governance hook (auto-scaffolding), this blocks the event loop unnecessarily.                                   | Accept `trustTier` as an optional parameter so callers who already have the config loaded can skip the redundant load.                                                                                             |
| W5  | publish/key-resolution.ts  | 91, 115      | **`resolveFromFleetKey` and `resolveFromIdentityKey` each call `readRegistry` independently.** If the publish pipeline calls `resolveSigningKey`, the registry file is read up to 3 times (CI env check doesn't read, but fleet and identity each read once). For large registries this doubles I/O.                                                                                     | Read the registry once in `resolveSigningKey` and pass the entries to the fleet and identity resolvers.                                                                                                            |
| W6  | cli.ts                     | 256-258      | **Algorithm and storage options are cast with `as` without validation.** The CLI accepts `--algorithm <alg>` and `--storage <tier>` as free-form strings and casts them to typed unions (`as 'ed25519'                                                                                                                                                                                   | 'hmac-sha256'`). A typo like `--algorithm rsa`passes the cast silently, and`generateKey`would hit the exhaustive switch default (which in TS without a default branch just returns`undefined`).                    | Validate the algorithm and storage values against a whitelist before casting. | W7  | keys/ceremony.ts           | 297-301      | **`deriveSingleDevKey` uses a fixed 100,000 PBKDF2 iterations.** OWASP recommends 600,000+ iterations for PBKDF2-SHA256 as of 2023. 100k is below the recommended minimum and makes offline brute-force against weak passphrases feasible. Since this is a root key derivation, the cost should be high.                                                                                 | Increase to at least 600,000 iterations, or make it configurable with 600k as the default. Document the tradeoff (higher iterations = slower derivation but stronger key).                                         |
| W8  | annotate/annotate.ts (CLI) | 58-85        | **`runAnnotate` reads skill directories sequentially with `await` in a loop.** Each iteration does `readFile` + `analyzeHeuristics` + potentially `writeFile`. For a workspace with many skills, this blocks the event loop for the entire scan. In a Gateway hook context (e.g., post-install annotation), this is measurable latency.                                                  | Use `Promise.all` with concurrency control, or at minimum collect all paths first and process in parallel batches.                                                                                                 |
| W9  | publish/atomicity.ts       | 99-103       | **`stageLocally` writes artifacts sequentially in a loop.** Each artifact is written with a separate `await writeFile`. For publish operations with many artifacts, this adds unnecessary I/O latency.                                                                                                                                                                                   | Collect all write promises and resolve with `Promise.all`.                                                                                                                                                         |

## Summary

The CP-4 implementation is architecturally sound with clean SDK/CLI separation, well-typed interfaces, and correct cryptographic primitives. The primary gateway-eng concerns are: (1) sequential I/O loops in rotate, annotate, and publish that block the event loop under load; (2) the lock file mechanism lacking staleness recovery; (3) registry file mutations with no atomicity guarantees; and (4) eager module-load computation in ceremony.ts. These are all fixable without restructuring — the foundations are solid, but the code needs hardening for a production Gateway where every millisecond of event loop blocking and every crash-recovery gap matters.
