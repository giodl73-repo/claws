| M1  | keys/ceremony.ts + cli.ts:319-320 | cli.ts:319-320                            | **Ceremony init generates random key material in the CLI adapter, not the SDK.** The cli.ts `ceremony init` handler calls `randomBytes(32)` to generate the key that gets split via Shamir. This is business logic — the CLI is deciding what secret to protect. A solo developer running `claws keys ceremony init --shares 3 --threshold 2` gets a random key they never see stored anywhere. The key is split and printed, but never registered in the key registry, never written to storage. The ceremony produces shares of a key that has no identity in the system. This breaks the adoption funnel: a user who completes the ceremony has no way to use the result for signing or publishing. | Move key generation + registry integration into an SDK function `initCeremony()` that generates the key, registers it as a root key, stores it, then splits it. The CLI should call that single function. The ceremony result should include the key ID so users can reference it later.                                        |
| M2  | publish/publish.ts:108            | `readFleetPublishPolicy(undefined)`       | **Fleet policy is always default — never reads from config.** The publish CLI adapter hardcodes `readFleetPublishPolicy(undefined)`, which always returns the default permissive policy. Fleet operators have no way to set `requireVerifiedPublish: true` because the config is never loaded. This means the entire fleet policy subsystem is dead code in practice — the enterprise governance story doesn't work.                                                                                                                                                                                                                                                                                   | Load fleet policy from the workspace config (claws.json) or a dedicated fleet config file, similar to how `scaffoldSkill` loads `loadConfig(workspaceRoot)`. Pass the config's fleet policy section to `readFleetPublishPolicy`.                                                                                                |
| M3  | publish/publish.ts:126            | `const version = \`1.0.0-${Date.now()}\`` | **Publish version is a hardcoded timestamp, not semantic versioning.** Every publish produces a version like `1.0.0-1681382400000`. This is not a version — it's noise. There's no version bump logic, no way for a user to specify a version, no way to know what version they published. The badge store accumulates entries with meaningless version strings. An OC developer looking at their badge history would see opaque timestamps, not the `0.1.0 -> 0.2.0` progression they expect.                                                                                                                                                                                                         | Accept `--version <semver>` as a CLI option. If omitted, read from skill.yaml or package.json. Fail with a clear error if no version is found rather than fabricating one.                                                                                                                                                      |
| M4  | scaffold/templates/index.ts       | typedTemplate, verifiedTemplate           | **Generated code imports from `@bic/claws-skill-kit` — a package that doesn't exist yet.** The scaffolded handler files import `@Skill`, `@Input`, `@Output`, `GovernanceValidator`, `SecurityScanner` from `@bic/claws-skill-kit`. The dependency checker in `dependency.ts` looks for this package in node_modules and prints an install instruction if missing. But the package isn't published. Every new user who runs `claws new skill my-skill --tier typed` will get non-compilable code with a warning they can't act on. The first 5 minutes of the adoption funnel are broken.                                                                                                              | Either (a) ship `@bic/claws-skill-kit` as a real package before this feature lands, or (b) generate plain TypeScript that works without any special dependency for the typed tier, and reserve the decorator syntax for verified tier with a clear "coming soon" message. The declared tier (YAML only) is fine as the default. |
| M5  | keys/storage.ts:78-79             | EnvStorage.write                          | **EnvStorage.write mutates `process.env` — volatile, misleading, enterprise-hostile.** `EnvStorage.write()` sets `process.env[name] = material`. This survives only for the lifetime of the current process. A user who runs `claws keys generate --storage env` will have a key registered in the JSON registry but the actual key material vanishes when the CLI exits. Next invocation, key resolution finds the registry entry, tries `EnvStorage.read()`, gets the env var (which is gone), returns null, and fails silently. The user thinks they have a key; they don't.                                                                                                                        | For env storage, `write()` should print the env var assignment (`export CLAWS_KEY_ED25519_XXXX=...`) and instruct the user to add it to their shell profile. Or write to a `.env` file in `.claws/`. The current implementation is a footgun.                                                                                   |

| W1  | keys/rotate.ts:183-200            | reSignArtifact loop                        | **Re-sign on rotation signs ALL .sig files with the same key, regardless of which key originally signed them.** `listCompiledArtifacts` grabs every `.sig` file and re-signs them all with the new key. In a workspace with multiple keys (one per skill publisher, or signing + session), rotating any Ed25519 key re-signs artifacts that belong to other keys. For a governance product targeting enterprise + community, Ed25519 signatures on manifests would allow the registry, fleet operators, and downstream consumers to verify without holding the private key. | Use Ed25519 signatures for manifest signing (the key infrastructure already supports it). | W3  | annotate/heuristics.ts:73-104     | TOOL_NAME_PATTERNS                         | **Risk heuristics are anglophone-only.** The entire heuristic engine matches English keywords: "send", "delete", "purchase", etc. OpenClaw has 3.2M MAU globally. ## Summary

CP-4 delivers a coherent product skeleton across keys, scaffold, annotate, and publish — the full lifecycle an OC developer would walk through. The adoption funnel shape (declared -> typed -> verified, file -> env -> kms) is well-designed. However, five major issues threaten the first-run experience: ceremony init produces an orphaned key (M1), fleet policy is hardcoded-permissive (M2), publish versions are meaningless (M3), scaffolded typed/verified code imports a nonexistent package (M4), and env key storage silently loses key material (M5). These are all fixable without architectural changes, but they must be fixed before the product ships — a new user hitting any of these in their first 10 minutes will not come back.
