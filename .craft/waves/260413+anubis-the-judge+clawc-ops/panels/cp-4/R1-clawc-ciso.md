## Findings

### Major (M)

| # | File | Line/Section | Finding | Suggested fix |
|---|------|-------------|---------|---------------|
| M1 | keys/ceremony.ts | L297-306 (`deriveSingleDevKey`) | **PBKDF2 iteration count too low for 2026.** 100,000 iterations was OWASP-minimum circa 2021. Current OWASP guidance is 600,000+ for PBKDF2-SHA256. An attacker with GPU hardware can brute-force 100k iterations at meaningful speed. This directly protects root key material in single-dev mode. | Raise to `600_000` iterations minimum. Better: expose as a parameter with a hard floor of 600,000, so future callers can increase without code changes. |
| M2 | keys/storage.ts | L43-52 (`FileStorage.write`) | **No file permission enforcement on Windows.** `chmod(0o600)` is a no-op on Windows (NTFS ACLs are different). On the platform this project permanently runs on, private key files are world-readable. The comment acknowledges this but treats it as acceptable — it is not for an auditor. | Use `icacls` via `child_process.execSync` (or the `windows-permissions` approach) to restrict NTFS ACLs to current user only. At minimum, emit a WARNING to stderr when running on Windows that key files are not permission-restricted. |
| M3 | keys/registry.ts | L56-61 (`writeRegistry`) | **Registry writes are not atomic.** `writeFile` truncates-then-writes. If the process crashes mid-write (or power loss), the registry.json is corrupted — all key metadata is lost. For a governance-critical file, this is a data integrity risk. | Write to a temp file first (`registry.json.tmp`), then rename (atomic on both POSIX and NTFS). Pattern: `writeFile(tmp) -> rename(tmp, target)`. |
| M4 | keys/rotate.ts | L192-196 (rollback path) | **Rollback uses non-null assertion on potentially null old key material.** If `storage.read(keyId)` returned null at L168 (key not in file storage — e.g., env tier or key file was deleted), then `oldPrivateKey!` is `null`, and `storage.write(keyId, null!)` will write the string "null" as key material, silently corrupting the key. | Guard with an explicit null check before rotation begins: `if (!oldPrivateKey) throw new Error('Cannot read old key material for rollback safety')`. Refuse to rotate if rollback is impossible. |
| M5 | keys/rotate.ts | L170-172 (archive before new write) | **Archived key material remains on disk without zeroization.** When a key is rotated, the old file is renamed to `.v{N}.key` and left on disk indefinitely. Old key versions are never securely deleted. An attacker with disk access gets every historical version of every key. | After successful rotation, securely overwrite archived key files with random bytes before unlinking, or at minimum document a retention/purge policy. Add a `purgeArchivedKeys(keyId)` function. |
| M6 | cli/commands/keys.ts | L306-313 (ceremony init, JSON output) | **Share data printed to stdout in JSON output.** Shamir shares are key material equivalents. `console.log(JSON.stringify({ shares: [...] }))` sends all N shares to a single output stream. In CI/automation, this ends up in build logs, which are often world-readable within the org. A single log leak exposes the full key. | Never print share data to stdout in JSON mode. Write each share to a separate file (one per participant). At minimum, redact share data from JSON output and print a file path instead. |
| M7 | cli/commands/keys.ts | L318-320 (ceremony init, text output) | **All share data printed sequentially to same terminal.** Even in human-readable mode, all N shares are printed to one terminal session. The entire point of M-of-N is that no single party sees all shares. Printing them all to one screen defeats the security model. | Each share should be written to a separate file. Display only the share index and file path, not the share data itself. |
| M8 | publish/key-resolution.ts | L50-62 (`resolveFromCiEnv`) | **CI signing key from env var has no validation.** The `CLAWS_CI_SIGNING_KEY` env var is accepted without any format validation, length check, or hex encoding verification. A misconfigured env var (empty string after whitespace trim, wrong encoding, truncated paste) silently produces bad signatures. | Validate: non-empty after trim, valid hex encoding, minimum 32 bytes (256 bits). Fail loudly with a specific error message on invalid CI key material. |
| M9 | publish/key-resolution.ts | L50-62 | **CI env key bypasses revocation check.** The `resolveFromCiEnv()` path reads directly from env vars and never checks the key registry for revocation status. A revoked key ID set in CI continues signing artifacts. | After resolving from env, if a key ID is provided (`CLAWS_CI_SIGNING_KEY_ID`), look it up in the registry and check `assertKeyNotRevoked()` before returning. |

### Warning (W)

| # | File | Line/Section | Finding | Suggested fix |
|---|------|-------------|---------|---------------|
| W1 | keys/registry.ts | L42-51 (`readRegistry`) | **Swallowed parse errors hide corruption.** If `registry.json` exists but contains garbage (truncated write, disk error), the catch returns `[]` — the system silently acts as if zero keys exist. Revocation checks, rotation schedules, and key lookups all silently fail open. | Distinguish file-not-found (return `[]`) from parse-error (throw with a clear message: "Registry file corrupted"). Use `err.code === 'ENOENT'` to differentiate. |
| W2 | keys/rotate.ts | L48-57 (lock file) | **Lock file has no stale-lock detection.** If the process crashes during rotation, the lock file persists forever. The error message tells the user to manually remove it, but provides no PID/timestamp staleness check. In CI, this silently blocks all future rotations until manual intervention. | Write PID + timestamp to lock file (already done at L52). On lock acquisition failure, read the existing lock, check if the PID is still alive (`process.kill(pid, 0)`), and auto-clean stale locks older than a threshold (e.g., 10 minutes). |
| W3 | keys/ceremony.ts | L73-88 (`splitByte`) | **Random polynomial coefficients are not zeroized after use.** The `coefficients` array and the `rand` Buffer containing cryptographic randomness persist in memory until GC. In a long-running process, this increases the window for memory disclosure attacks. | Overwrite `coefficients` with zeros and `rand.fill(0)` after the split loop. While V8 doesn't guarantee zeroization, it's defense-in-depth and signals intent. |
| W4 | keys/storage.ts | L72-84 (`EnvStorage`) | **Environment variable storage persists key material in `process.env`.** This is readable by any module in the process, survives until process exit, and is visible via `/proc/{pid}/environ` on Linux. For session keys this may be acceptable, but for signing keys it's a broad exposure surface. | Document that `env` tier is for ephemeral/CI use only, not production signing keys. Warn at key generation time if a signing-purpose key is stored in env tier. |
| W5 | keys/revoke.ts | L30-66 (`revokeKey`) | **Revocation does not destroy key material.** Marking a key as revoked in the registry is metadata-only. The actual key material remains in storage (file or env). An attacker who bypasses the registry check (or reads the file directly) can still use the revoked key. | On revocation, also delete/overwrite key material from the storage backend. Add `storage.delete(keyId)` to the storage interface and call it during revocation. |
| W6 | keys/rotate.ts | L180-201 (re-sign loop) | **Re-signs ALL `.sig` files, not just those signed by the rotating key.** `listCompiledArtifacts` returns every `.sig` file in `.claws/compiled/`. If multiple keys exist (e.g., separate signing and session keys), rotating one key re-signs artifacts that belong to a different key. This silently changes signature provenance. | Each `.sig` file should record which key ID produced it. Only re-sign artifacts whose recorded key ID matches the rotating key. |
| W7 | publish/manifest-state.ts | L70-74 (`computeContentHash`) | **HMAC key used for content hashing, but key material is the signing key.** Using the signing key as HMAC key for content hashing means the content hash function is secret-dependent. If the signing key rotates, all previously-valid content hashes become invalid. This makes stale-signed detection dependent on key identity, which is fragile. | Use a non-secret hash (SHA-256) for content hashing and reserve the signing key for signature verification only. Separate content integrity (hash) from authenticity (signature). |
| W8 | publish/atomicity.ts | L106-113 (staging metadata) | **Transaction metadata written to staging dir is not signed.** The `_tx.json` file records transaction state but has no integrity protection. An attacker who can modify the staging directory can alter transaction metadata to claim committed state for a rolled-back transaction. | Sign the `_tx.json` with the same signing key used for artifacts, or include a hash of `_tx.json` in the commit response. |
| W9 | publish/fleet-policy.ts | L86-128 (`evaluateFleetPolicy`) | **Policy is read from in-memory defaults, never from fleet config on disk.** The CLI calls `readFleetPublishPolicy(undefined)` at `publish.ts:108`, so the policy always returns defaults (permissive). The `requireVerifiedPublish` setting is never actually enforced from fleet configuration. | Wire up fleet config reading from `.claws/fleet.yaml` or equivalent. The current code provides the enforcement logic but never loads the actual policy. |
| W10 | cli/commands/publish.ts | L55-63 (registry client) | **Registry submission sends artifacts over HTTPS with no authentication.** The `fetch` call has no auth token, no API key, no mTLS. Any endpoint that accepts unauthenticated POST can receive the artifact payload. | Add authentication header (bearer token, API key) to registry submissions. The signing key proves artifact provenance but does not authenticate the publisher. |

### Notes (N)

| # | File | Line/Section | Finding |
|---|------|-------------|---------|
| N1 | keys/registry.ts | L68-72 (`generateKeyId`) | Key ID uses only 4 bytes (32 bits) of randomness. While collision probability is low for small registries, enterprise fleets with hundreds of keys over years will approach birthday-bound collision risk (~1 in 65k at ~256 keys). Consider 8 bytes. |
| N2 | keys/ceremony.ts | L217-218 | Ceremony ID is also 8 bytes of randomness (`randomBytes(8)`). For a globally-unique ceremony identifier that may appear in audit logs cross-org, consider UUIDv4 (16 bytes). |
| N3 | keys/schedule.ts | L41 (`MS_PER_DAY`) | Rotation deadline calculation uses `86_400_000 ms/day`, which doesn't account for DST transitions or leap seconds. For 90-day intervals this is negligible, but worth a comment noting UTC-only semantics. |
| N4 | scaffold/defaults.ts | L49-54 (`maxRiskForTier`) | `tier` parameter is `number` not `TrustTier`. While validated at runtime, the type signature allows any number through. Use the `TrustTier` union type for compile-time safety. |
| N5 | annotate/heuristics.ts | L187-248 | The heuristic engine operates on pattern matching against source text strings. An adversary who controls the skill source can trivially evade detection (e.g., dynamic `import()`, obfuscated variable names, indirect require). This is acknowledged by the confidence scoring but should be documented as a known limitation in the threat model. |
| N6 | publish/badge.ts | L122-125 (`extractField`) | The regex `^${field}:` uses field name directly in a regex constructor without escaping. If a field name contains regex metacharacters (unlikely for known fields but possible for future extensibility), this produces incorrect matches. |
| N7 | keys/generate.ts | L47-54 (`generateHmac`) | HMAC secret is returned as hex-encoded string, doubling its in-memory footprint (32 bytes -> 64 chars). Consider returning raw bytes and encoding only at the storage boundary. |
| N8 | cli/commands/keys.ts | L53-98 (`runKeysGenerate`) | The CLI outputs "Key generated" on success but never prints the key material itself — good practice. However, it also doesn't indicate where the key was stored (file path or env var name), which makes operational verification harder. Consider adding storage location to the output. |
| N9 | keys/rotate.ts | L220-221 | `acquireLock` and `releaseLock` are exported from the module. These are internal implementation details of the rotation flow. Exporting them invites direct use by consumers, potentially causing lock state inconsistency. |
| N10 | publish/key-resolution.ts | L69-79 (`selectBestKey`) | Key selection uses string comparison of ISO timestamps for "most recent". This works but is fragile — if timestamps have different timezone offsets or precision, comparison may be wrong. Use `Date.getTime()` for numeric comparison. |

## Summary

The key management infrastructure demonstrates solid architectural separation (registry metadata vs. key material, storage tier abstraction, audit chain integration). However, there are significant security gaps that would concern an auditor: **private key files have no effective access control on Windows** (M2), **PBKDF2 iterations are below current OWASP guidance** (M1), **Shamir ceremony outputs all shares to a single stream defeating M-of-N guarantees** (M6/M7), **CI signing keys bypass revocation checks** (M9), and **registry writes are not crash-safe** (M3). The revocation system is metadata-only without material destruction (W5), and the fleet policy enforcement is wired to defaults rather than actual configuration (W9). These findings need resolution before the governance story is auditor-ready.
