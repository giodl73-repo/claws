## Findings

### Major (M)

| # | File | Line/Section | Finding | Suggested fix |
|---|------|-------------|---------|---------------|
| M1 | openclaw-governance-spec.md | L111-150 (AuthorizationDecision) | **Flat interface allows invalid field combinations.** `modifiedArguments` is only meaningful when `decision === 'modify'`, `reason`/`ruleId` are only meaningful when `decision === 'deny'`, and `requiresExternalApproval` is N/A when `decision === 'deny'`. A flat interface with 5 optional fields means consumers must mentally track which fields are valid for which decision, and nothing prevents constructing `{ decision: 'allow', modifiedArguments: {...} }` or `{ decision: 'modify' }` with no `modifiedArguments`. This is the canonical "make invalid states representable" anti-pattern. | Replace with a discriminated union on `decision`: `type AuthorizationDecision = AllowDecision \| DenyDecision \| ReviewDecision \| ModifyDecision`. `DenyDecision` requires `reason: string` (non-optional) and `ruleId?: string`. `ModifyDecision` requires `modifiedArguments: Record<string, unknown>` (non-optional). `AllowDecision` has `requiresExternalApproval?: boolean`. `ReviewDecision` has `requiresExternalApproval: true` (literal, since the spec says review decisions always require external confirmation). All four share `riskLevel?: RiskLevel` and `metadata?: Record<string, unknown>`. |
| M2 | openclaw-governance-spec.md | L198-216 (AuditableResult) | **`executed` boolean with optional `output`/`blockReason` is a weak encoding.** The spec says `output` is for `executed: true` and `blockReason` is for `executed: false`, but the type allows both to be present, both to be absent, or mismatched (`executed: true` with `blockReason` and no `output`). This is a discriminated union that was flattened into booleans and optionals. | Replace with: `type AuditableResult = ExecutedResult \| BlockedResult` where `ExecutedResult = { executed: true; decision: AuthorizationDecision; output: unknown; durationMs: number; timestamp: string }` and `BlockedResult = { executed: false; decision: AuthorizationDecision; blockReason: string; durationMs: number; timestamp: string }`. The discriminant `executed` already exists; make the type system enforce the mutual exclusivity. |
| M3 | openclaw-governance-spec.md | L87-93 (ToolCall.context) | **Index signature alongside typed fields silently absorbs typos.** `context` has typed fields `conversationId`, `agentId?`, `workspaceId?` PLUS `[key: string]: unknown`. This means `{ conversatonId: 'x' }` (typo) compiles without error -- the misspelled key falls into the index signature. For a security-critical governance pipeline, silent typo absorption is a correctness hazard: a missing `conversationId` (because it was mistyped) means broken audit correlation. | Split into two types: a typed struct for known fields and a separate `extensions: Record<string, unknown>` property for host additions. This mirrors the pattern already used in `ApprovalRequestEvent.extensions`. Alternatively, use a branded/intersection approach: `type ToolCallContext = { conversationId: string; agentId?: string; workspaceId?: string } & { extensions?: Record<string, unknown> }`. |
| M4 | openclaw-governance-spec.md + approval-event-schema.md | L470-478 / L92-101 (risk.level + risk.label) | **No type-level coupling between `risk.level` and `risk.label`.** The spec defines `level: RiskLevel` (1-5) and `label: 'read' \| 'write' \| 'communicate' \| 'execute' \| 'transact'` as independent fields. Nothing prevents `{ level: 1, label: 'transact' }` or `{ level: 5, label: 'read' }`. The approval-event-schema.md rationale doc is even weaker: `level: number` (not `RiskLevel`). Since these labels have fixed semantics per level, a mismatch is always a bug. | Define a mapped type or discriminated union: `type RiskClassification = { level: 1; label: 'read' } \| { level: 2; label: 'write' } \| { level: 3; label: 'communicate' } \| { level: 4; label: 'execute' } \| { level: 5; label: 'transact' }`. Embed this in `ApprovalRequestEvent.risk` and anywhere risk level + label appear together. This makes level/label mismatches a compile error. |

### Warning (W)

| # | File | Line/Section | Finding | Suggested fix |
|---|------|-------------|---------|---------------|
| W1 | openclaw-governance-spec.md | L71 (RiskLevel) | **`RiskLevel = 1 \| 2 \| 3 \| 4 \| 5` has no representation for unknown tools.** The spec says "default to R5" for unknown tools (L334, L412), but there is no type-level distinction between "we classified this tool as R5 because it forwards credentials" and "we defaulted to R5 because we don't know what this tool does." A consumer that receives `riskLevel: 5` cannot distinguish genuine R5 from unknown-defaulted-to-R5 without parsing the `reason` string. | Either: (a) keep `RiskLevel = 1 \| 2 \| 3 \| 4 \| 5` but add a sibling field `riskClassificationSource: 'classified' \| 'default'` to AuthorizationDecision, or (b) extend to `type RiskLevel = 1 \| 2 \| 3 \| 4 \| 5 \| 'unclassified'` where `unclassified` is treated as R5 at enforcement but preserves provenance for audit. Option (a) is lower churn. |
| W2 | openclaw-governance-spec.md | L551-564 (ApprovalTimeoutPolicy) | **`alwaysDenyRiskLevels: RiskLevel[]` is mutable and allows duplicates.** The spec says R5 MUST always be in this list (non-negotiable). But the type is a plain mutable array -- callers can `policy.alwaysDenyRiskLevels.pop()` to remove R5, or pass `[]` to bypass the safety rail entirely. This is a runtime invariant that the type does not enforce. | Use `readonly alwaysDenyRiskLevels: readonly RiskLevel[]` to prevent mutation. For the R5 invariant, consider a branded type or a constructor function that validates R5 is present and returns an opaque `ApprovalTimeoutPolicy`. The constructor approach is pragmatic: `function createTimeoutPolicy(config: TimeoutPolicyInput): ApprovalTimeoutPolicy` that throws if `5` is not in `alwaysDenyRiskLevels`. |
| W3 | openclaw-governance-spec.md | L448-502 (ApprovalRequestEvent.schemaVersion) | **`schemaVersion: 1` is a literal type with no version negotiation strategy.** When version 2 ships, the type becomes `schemaVersion: 1 \| 2`. But consumers written against v1 will have `schemaVersion: 1` in their types and will reject v2 events at the type level. The spec says "consumers MUST handle unknown versions gracefully" but the literal type makes this impossible without `as` casts or widening. | Define `schemaVersion: number` in the base type, then use discriminated unions per version: `type ApprovalRequestEvent = ApprovalRequestEventV1 \| ApprovalRequestEventV2`. Consumers pattern-match on `schemaVersion` to narrow. Alternatively, keep `schemaVersion: 1` but document that the published type will be `schemaVersion: number` with runtime validation, and provide a type guard `isV1(event): event is ApprovalRequestEventV1`. |
| W4 | openclaw-governance-spec.md | L660-663 (AuditEvent) | **`AuditEvent` is effectively `Record<string, unknown>` with a required `type`.** This is the loosest possible type for events entering the audit chain. Any object with a `type` string qualifies. For a hash-chained audit trail where event shape matters for replay and verification, this provides zero compile-time safety on event structure. | Define a union of known event types: `type AuditEvent = ToolCallEvent \| ApprovalEvent \| PolicyViolationEvent \| ...`. Each has `type` as a literal discriminant. Keep an escape hatch for custom events: `\| { type: string; [key: string]: unknown }`. This lets known events be type-narrowed while still accepting arbitrary events from third parties. |
| W5 | openclaw-governance-spec.md | L684 (ExportFormat) | **`ExportFormat = 'sarif' \| 'cef' \| 'json' \| 'syslog'` is closed and non-extensible.** But `@openclaw/siem-emitter` uses `'cef' \| 'ndjson' \| 'syslog' \| 'sarif'` (note: `ndjson` vs `json`). The two packages define different format enumerations for what appears to be the same concept. `audit-chain` says `json` (flat JSON array), `siem-emitter` says `ndjson` (newline-delimited). These are semantically different but easy to confuse.  | Unify into a single `ExportFormat` type shared across packages: `type ExportFormat = 'sarif' \| 'cef' \| 'json' \| 'ndjson' \| 'syslog'`. Export it from a shared types package or from `@openclaw/audit-chain`. Make `json` and `ndjson` both available with clear documentation: `json` = array, `ndjson` = line-delimited. If extensibility is needed, use `type ExportFormat = 'sarif' \| 'cef' \| 'json' \| 'ndjson' \| 'syslog' \| (string & {})` to allow custom strings while preserving autocomplete. |
| W6 | approval-event-schema.md | L94 (risk.level) | **Design rationale doc uses `level: number` instead of `level: RiskLevel`.** The canonical spec (openclaw-governance-spec.md L476) correctly uses `level: RiskLevel`, but the approval-event-schema.md rationale doc (L94) uses `level: number`. If implementors reference the rationale doc instead of the canonical spec, they get a weaker type that allows `level: 0`, `level: 99`, or `level: -1`. | Update approval-event-schema.md L94 to use `level: RiskLevel` and add an import comment referencing the canonical type. Ensure the rationale doc is clearly labeled as non-normative with a pointer to the canonical spec types. |
| W7 | approval-event-schema.md | L189 (ApprovalTimeoutPolicy.alwaysDenyRiskLevels) | **Rationale doc uses `alwaysDenyRiskLevels: number[]` instead of `RiskLevel[]`.** Same divergence as W6. The rationale doc's type is weaker than the canonical spec, allowing invalid risk level values like 0, 6, or negative numbers in the timeout policy configuration. | Update to `alwaysDenyRiskLevels: RiskLevel[]` and ensure consistency with the canonical spec. |

| N1 | openclaw-governance-spec.md | L220-245 (ProviderCapabilities) | `ProviderCapabilities.name` duplicates `GuardrailProvider.name`. If a provider returns different names from `getCapabilities().name` vs the `name` property, the registry has contradictory identity. Consider removing `name` from `ProviderCapabilities` and having the registry inject it, or making `ProviderCapabilities` generic on the provider name: `interface ProviderCapabilities<N extends string = string> { name: N; ... }`. Low severity since this is a documentation/consistency issue, not a soundness hole. |
| N2 | openclaw-governance-spec.md | L263-297 (ProviderRegistry) | The `register()` method returns `void`. There is no error signaling if a duplicate provider name is registered. The `preAuthorize()` composition says "last modify wins" for multiple modify decisions, but the type system does not constrain or document this ordering. Consider returning a result type from `register()` or throwing on duplicates, and documenting the "last modify wins" semantics in the return type JSDoc. |
| N3 | claws-aether-integration.md | L108-133 (host-approval-policies.json schema) | The JSON schema for `host-approval-policies.json` uses `schemaVersion: 1` with a runtime fallback ("if version is higher than supported, fall back to default"). This mirrors the same version negotiation gap as W3 but in a JSON artifact rather than a TypeScript type. The pattern is consistent, but the lack of a typed version negotiation strategy is a systemic concern across the contribution surface. |
| N4 | openclaw-governance-spec.md | L808-828 (Identity types) | `Identity.roles` and `Identity.groups` are both `string[]`. There is no distinction between a role name and a group name at the type level. A caller could accidentally pass a group where a role is expected. Consider branded types (`type RoleName = string & { __brand: 'RoleName' }`) if role/group confusion is a real risk, or accept the trade-off for API simplicity since these are user-provided strings from SSO claims. |

## Summary

The type definitions across these specs have a systemic pattern: structures that should be discriminated unions are encoded as flat interfaces with optional fields. AuthorizationDecision (M1) is the most critical -- it is the central type of the entire governance pipeline, and it allows 4 categories of invalid state. AuditableResult (M2) has the same shape problem. The risk level/label coupling gap (M4) means the most safety-critical classification in the system -- distinguishing R1/read from R5/transact -- has no type-level enforcement. These are published API contracts under `@openclaw/*`; once shipped, fixing them requires semver-major breaks. The time to get discriminated unions right is now, before v1.0.0.
