# R1 Craft Dragon Review -- Session Model (Pulses 60-63)

**Reviewer**: craft/dragon (invariant rigor > feature velocity)
**Review type**: plan (pre-implementation design review)
**Round**: 1
**Date**: 2026-04-15
**Scope**: Pulses 60 (session types), 61 (session routes), 62 (TUI sessions), 63 (approval session context), plus CL-10 Session Model section and CL-11 sessionId/sessionType in ToolCall.context

---

## Findings

### Critical (C)

| ID | Location | Finding |
|----|----------|---------|
| C-01 | Pulse 60 `resolveSessionTools` + CL-11 `ProviderRegistry` R5 enforcement | **A cron session hitting `requiresExternalApproval: true` at 3 AM has no human to approve -- the approval request hangs until the `ApprovalTimeoutPolicy` fires, and the timeout `failMode` determines whether R5 enforcement holds.** CL-11 defines `ApprovalTimeoutPolicy` with `failMode: 'deny' | 'allow'` and an `alwaysDenyRiskLevels` invariant that forces R5 to deny on timeout. This means R5 is safe: cron sessions that trigger R5 tools at 3 AM will time out and deny. But R3-R4 tools with `requiresExternalApproval: true` (e.g., fleet-policy-mandated approval on `create-task`) have configurable `failMode`. If a fleet admin sets `failMode: 'allow'` and does not include R3/R4 in `alwaysDenyRiskLevels`, cron sessions silently auto-approve gated R3/R4 tools on timeout with no human review. **This is a governance bypass: the approval gate exists precisely because a human should evaluate the call, but the timeout policy allows unattended sessions to skip that evaluation.** Fix: Pulse 60 must define a `SessionApprovalPolicy` that overrides the workspace-level `ApprovalTimeoutPolicy` per session type. For cron and agent sessions (unattended), `failMode` must be forced to `'deny'` for ALL risk levels with `requiresExternalApproval: true`, not just R5. The session type must be an input to the timeout policy, not just the risk level. |
| C-02 | CL-11 `ToolCall.context` + Pulse 60 session types | **`sessionId` and `sessionType` in `ToolCall.context` are optional fields (`sessionId?: string`, `sessionType?: 'main' | 'cron' | 'channel' | 'agent'`). A tool call with omitted session context bypasses all session-scoped governance.** CL-11 defines `sessionId` and `sessionType` as optional on `ToolCall.context`. Pulse 60 adds them to the context "per CL-11 amendment." But the `resolveSessionTools` function and the `ProviderRegistry` composition logic both depend on these fields. If a caller constructs a `ToolCall` with `sessionId: undefined` and `sessionType: undefined`, providers cannot apply session-scoped restrictions. The ProviderRegistry has no invariant that says "tool calls without session context are denied" -- it processes whatever it receives. A caller can omit session context entirely and the tool call proceeds under workspace-level permissions, skipping any session-level restrictions. **Fix**: For claws-managed workspaces, `sessionId` and `sessionType` must be required (not optional) on `ToolCall.context`. The optionality in CL-11 is correct for the upstream spec (non-claws hosts may not have sessions), but `claws serve` and the claws gateway plugin must enforce a stricter invariant: reject any tool call where `sessionId` is absent. Add a validation guard in the gateway plugin's `preAuthorize` that returns `{ decision: 'deny', reason: 'Missing session context' }` for tool calls without session identity. |

### Major (M)

| ID | Location | Finding |
|----|----------|---------|
| M-01 | Pulse 60 `resolveSessionTools` + CL-10 Session Model | **The session-scoped tool resolver operates as a filter on workspace tools, but the ProviderRegistry R5 enforcement operates independently on the composed decision. These are two separate enforcement paths with no reconciliation.** `resolveSessionTools(workspaceTools, session)` returns a filtered `ToolDefinition[]` for the session. A cron session gets a "restricted allowlist." Separately, when a tool call arrives at the ProviderRegistry, R5 enforcement forces `requiresExternalApproval: true` regardless of session type. The problem: a cron session's restricted allowlist could exclude an R5 tool, but if the cron session somehow invokes a tool not in its allowlist (e.g., through an agent delegation chain, or because the tool resolver is only called at session creation time, not at invocation time), the R5 enforcement at the ProviderRegistry still fires. But this creates ambiguity: is the session tool resolver authoritative (tool not in session = denied) or advisory (tool not in session = logged but allowed, ProviderRegistry makes the real decision)? **Fix**: Pulse 60 must specify the enforcement semantics: `resolveSessionTools` returns the authoritative tool set, and any tool call for a tool not in the session's resolved set must be denied before reaching the ProviderRegistry. The session tool resolver is a pre-filter, not a post-filter. Add a test: "tool call for tool not in session's resolved set returns deny before ProviderRegistry evaluation." |
| M-02 | Pulse 60 `SessionType` union + `SessionState` | **A session can claim any `sessionType` at creation time and there is no validation that the claimed type matches the session's actual execution context.** `SessionType` is `'main' | 'cron' | 'channel' | 'agent'`. `SessionState` carries `type: SessionType`. But neither Pulse 60 nor the CL-10 Session Model specify how session type is determined or validated. If session creation is an API operation (e.g., a cron scheduler creates a session by POSTing to an internal endpoint), the caller provides the session type. A malicious or buggy caller can create a session with `type: 'main'` when it is actually a cron job. Since `resolveSessionTools` gives `main` sessions the full workspace tool set and `cron` sessions a restricted allowlist, a cron job claiming to be `main` gets elevated tool permissions. **Fix**: Session type must be determined by the session creation context, not self-declared. The server must validate: (a) only one `main` session can exist per workspace (or per-user per-workspace), (b) `cron` sessions can only be created by the HEARTBEAT.md scheduler, (c) `agent` sessions must reference a valid delegating session, (d) `channel` sessions must reference a bound channel. Add a `SessionFactory` that enforces these creation constraints. |
| M-03 | Pulse 63 `ApprovalRequestEvent` + session context | **Pulse 63 adds `sessionId` and `sessionType` to `ApprovalRequestEvent` and updates `createApprovalRequest()` to require session context. But the `displayLabel` computed property uses session metadata (name) that may not be available or may be spoofable.** The `displayLabel` returns "Daily Triage (cron)" based on `sessionType` and "optional session name metadata." But session name metadata is not a validated field -- it comes from whoever created the session. A cron session could be named "Main Session" to confuse approvers into thinking it is the primary interactive session. When an approver sees "Main Session wants to send-email" at 3 AM, they may approve because they think a human is actively using the agent. **Fix**: `displayLabel` must include a non-spoofable session type indicator that cannot be overridden by metadata. Format: "cron: Daily Triage" (type prefix is derived from `sessionType` enum, not metadata). The session type prefix must be hardcoded from the `SessionType` discriminant, with the session name appended. Approvers can trust the type prefix even if they cannot trust the name. |
| M-04 | Pulse 60 `session-tool-resolver.ts` + CL-10 "Governance per session" | **The session tool resolver defaults cron sessions to a "restricted allowlist" but the pulse does not define what that allowlist is, how it is configured, or whether it can be overridden.** Pulse 60 says "Cron sessions default to a restricted allowlist" and "Channel sessions use workspace defaults." But there is no specification of: (a) what the default cron allowlist contains, (b) where the allowlist is configured (HEARTBEAT.md? claws.json? per-session in SessionConfig?), (c) whether a workspace admin can expand the cron allowlist to include R5 tools, (d) what happens if the allowlist is empty (deny all tools? error?). If the allowlist is configurable and an admin adds an R5 tool to a cron session's allowlist, the session has R5 tools with no human present to approve. The ProviderRegistry will still force `requiresExternalApproval: true`, but per C-01, the timeout policy determines whether that blocks or passes. **Fix**: The cron allowlist must have an invariant: it cannot include tools with `risk.level >= 4`. R4 and R5 tools in cron sessions must be structurally excluded from the allowlist regardless of admin configuration. This makes the session tool resolver a defense-in-depth layer alongside the ProviderRegistry. |
| M-05 | Pulse 61 routes + Pulse 60 types | **The `GET /api/sessions/:id/tools` route delegates to `resolveSessionTools` but there is no specification of when the tool set is computed -- at session creation time (snapshot) or at query time (live).** If the tool set is computed at session creation and cached in `SessionState`, workspace-level tool changes (e.g., a fleet policy adding a new R5 tool) do not propagate to existing sessions until they are recreated. A long-running cron session could operate with stale permissions indefinitely. If the tool set is computed live at query time, it is always current but may produce different results on consecutive calls if the workspace is being edited concurrently. **Fix**: Pulse 60 must specify that `resolveSessionTools` is computed at invocation time (each tool call resolves against current workspace state), not at session creation time. The `/api/sessions/:id/tools` route computes the tool set fresh on each GET. Session state stores session identity, not cached permissions. |

### Warning (W)

| ID | Location | Finding |
|----|----------|---------|
| W-01 | Pulse 60 `SessionState` + session lifecycle | **`SessionState` has no tamper resistance. It is a plain TypeScript interface with no integrity guarantees.** `SessionState` carries `id`, `type`, `status`, `createdAt`, `lastActiveAt`, and `metadata`. These are mutable in-memory fields. On the `claws serve` server, session state lives in memory (no persistence layer is specified). If the server process is compromised or if a debug endpoint exposes session state, an attacker can modify a session's `type` from `'cron'` to `'main'` to gain elevated tool permissions. There is no HMAC, signature, or hash chain on session state transitions. **Fix**: Session state transitions must be recorded in the audit chain (`@openclaw/audit-chain`). The session's `type` field must be immutable after creation -- the type is set at creation and cannot change for the session's lifetime. Add an invariant: `SessionState.type` is `readonly` not just in TypeScript (which is a compile-time check) but enforced at runtime by the session store rejecting any mutation of the `type` field. |
| W-02 | Pulse 62 TUI + Pulse 61 routes | **The TUI sessions screen shows session type badges but does not indicate whether a session has pending approval requests.** The TUI renders type badges (main=blue, cron=yellow, channel=green, agent=purple) and status indicators (active/idle/error). But it does not show whether a cron session is currently blocked waiting for an approval that will never come (because no human is present). A cron session with `status: 'running'` and a pending R5 approval request will appear healthy in the TUI while actually being blocked indefinitely. **Fix**: The TUI must show a distinct status indicator for "waiting for approval" (e.g., orange exclamation). The `/api/sessions/:id` response should include `pendingApprovals: number` so the TUI can surface this. For cron sessions, a pending approval that has been waiting longer than the timeout threshold should show as an error, not as running. |
| W-03 | Pulse 63 `createApprovalRequest` + CL-10 Session Model | **The updated `createApprovalRequest()` requires session context as a parameter, but the CL-11 `ApprovalRequestEvent.context` does not include `sessionId` or `sessionType` -- only `conversationId`, `workspaceId`, and `agentId`.** Pulse 63 adds `sessionId` and `sessionType` to `ApprovalRequestEvent` as top-level fields, but the existing `context` block in CL-11's `ApprovalRequestEvent` does not carry them. This creates a schema inconsistency: session identity is in two places (top-level `sessionId`/`sessionType` from Pulse 63, and `ToolCall.context.sessionId`/`sessionType` from CL-11). Consumers must know to look at the top-level fields for approval events and the context fields for tool calls. **Fix**: Align the schemas. Either add `sessionId` and `sessionType` to `ApprovalRequestEvent.context` (matching `ToolCall.context`), or document the canonical location for each consumer. Do not split session identity across two different locations in related event schemas. |
| W-04 | Pulse 60 `SessionType` union | **The `SessionType` union is closed (`'main' | 'cron' | 'channel' | 'agent'`) with no extensibility mechanism.** If a future session type is needed (e.g., `'webhook'` for HTTP-triggered sessions, or `'scheduled-agent'` for time-triggered delegated sessions), the union must be modified, which is a breaking change for any code that exhaustively matches on `SessionType`. CL-11 uses the same closed union in `ToolCall.context.sessionType`. **Fix**: This is not urgent but should be documented as a known constraint. Add a comment on the `SessionType` union: "Adding a new session type is a breaking change. Plan for v2 of the session model if new types are needed." Alternatively, consider a discriminated object (`{ kind: string; ... }`) with known-type guards rather than a closed string union. |
| W-05 | Pulse 60 agent session delegation | **Agent sessions "inherit their delegator's permissions minus any revoked tools" but there is no specification of how revocation is tracked or whether it is transitive.** If session A (main) delegates to session B (agent) with tools X, Y, Z minus Z, and session B delegates to session C (agent) with tools X, Y minus Y, the final set should be {X}. But if session A later revokes tool X, does session B's resolved set update? Does session C's? Pulse 60 does not specify whether delegation revocations are live (tracked against current delegator state) or snapshot (fixed at delegation time). **Fix**: Specify that agent session permissions are resolved live against their delegator's current resolved set, recursively. Add a test: "revoking a tool from the delegating session removes it from the delegated session's resolved set on next resolution." Also add a depth limit (e.g., max 5 delegation levels) to prevent infinite delegation chains. |

### Note (N)

| ID | Location | Finding |
|----|----------|---------|
| N-01 | Pulse 60 test gates | **The L1 integration tests for `session-tool-resolver` have only 3 tests covering 4 session types.** There are tests for cron (restricted), agent (delegator minus revoked), and main (full). Channel sessions ("use workspace defaults") have no dedicated test. If "workspace defaults" means the same as main, this should be tested explicitly to prevent a future regression where channel sessions accidentally get cron-level restrictions. |
| N-02 | Pulse 62 `RunHistoryTimeline` | **The run history timeline shows success/error/timeout but does not show "denied by governance" as a distinct status.** A cron run that was blocked because it attempted an R5 tool (and the approval timed out with `failMode: 'deny'`) would appear as either "error" or "timeout." Neither label communicates that governance enforcement stopped the run. Add a `'governance_denied'` status to the run history model so operators can distinguish infrastructure errors from policy enforcement. |

## Dragon Lens Checklist

| Question | Assessment |
|----------|------------|
| Does this change weaken any existing validation or type constraint? | **Yes.** The session-scoped tool resolver introduces a second permission layer that can be more permissive than the ProviderRegistry expects (M-01). If the resolver is advisory rather than authoritative, tools outside a session's set may still execute. Additionally, optional `sessionId`/`sessionType` in CL-11 (C-02) allows tool calls to bypass session-scoped governance entirely by omitting session context. |
| Are error paths still exhaustive after this change? | **No.** The cron-session-hits-approval-gate path (C-01) has no explicit handling -- it falls through to the generic `ApprovalTimeoutPolicy` which was designed for interactive sessions. The "tool not in session's resolved set" path (M-01) has no specified behavior. The "session claims wrong type" path (M-02) has no validation. |
| Would reverting this change break any new code that depends on a relaxed invariant? | **No.** Pulses 60-63 are additive. Reverting removes the session model without affecting workspace-level governance. However, Pulse 63's change to `createApprovalRequest()` makes session context required on that helper -- reverting would require callers to stop providing session context. |
| Can a session bypass R5 enforcement? | **R5 denial on timeout is preserved** by the `alwaysDenyRiskLevels` invariant in `ApprovalTimeoutPolicy`. However, R3-R4 gated tools in unattended cron sessions can auto-approve on timeout if `failMode: 'allow'` is configured (C-01). This is not an R5 bypass but is a governance bypass for non-R5 gated tools. |
| Is session state tamper-resistant? | **No (W-01).** Session state is a mutable in-memory object with no integrity guarantees. The `type` field is the security-critical discriminant (it determines tool permissions) but has no runtime immutability enforcement beyond TypeScript's `readonly` keyword. |

## Summary

The session model introduces a meaningful capability -- per-session tool scoping -- but it creates a second enforcement layer alongside the ProviderRegistry with no formal reconciliation between them. The two critical findings are:

1. **Unattended approval deadlock (C-01)**: Cron sessions that hit gated R3-R4 tools will silently auto-approve on timeout if the fleet's `ApprovalTimeoutPolicy.failMode` is `'allow'`. The approval gate was designed for interactive sessions where a human is present. Unattended sessions need a stricter policy: deny on timeout for all gated tools, not just R5.

2. **Optional session context (C-02)**: `sessionId` and `sessionType` are optional on `ToolCall.context` per CL-11. Any tool call that omits them escapes session-scoped restrictions entirely. Within claws-managed workspaces, these fields must be required and validated.

The major findings address session type spoofing (M-02), undefined cron allowlist boundaries (M-04), dual enforcement path ambiguity (M-01), approval event label spoofability (M-03), and permission snapshot vs. live resolution (M-05). These are all fixable within the current pulse structure -- they require tightening specifications, not redesigning the session model.
