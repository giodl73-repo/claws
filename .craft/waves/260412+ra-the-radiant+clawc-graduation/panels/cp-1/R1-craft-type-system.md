## Findings

### Major (M)

| # | File | Line/Section | Finding | Suggested fix |
|---|------|-------------|---------|---------------|
| M-01 | audit/chain.ts | L44 | **`private readonly entries: AuditEntry[] = []` is a lie** -- the `readonly` modifier on the field prevents reassignment, but `AuditEntry[]` is a mutable array. `append()` and `load()` both mutate via `.push()`. The field declaration implies immutability but the runtime behavior is fully mutable. This is not a readonly array -- `readonly` here only prevents reassignment, not mutation. Anyone with access to the private field (including subclasses if the class is extended) can mutate it. | Change type to `AuditEntry[]` without `readonly` to avoid false safety signal, or if immutability is desired for external consumers, keep the private mutable array and expose only `readonly AuditEntry[]` views via getters (which `allEntries` already does). The `readonly` keyword on a mutable array field is misleading. |
| M-02 | audit/wal.ts | L84 | **Unsafe `JSON.parse` cast to `AuditEntry`** -- `JSON.parse(trimmed) as AuditEntry` trusts the WAL file contents without validation. A corrupted or tampered WAL file could inject entries with missing fields (`index`, `hash`, `signature`) that pass the type assertion at compile time but fail at runtime. This is a deserialization boundary where shape validation is required. | Add a `validateAuditEntry(parsed: unknown): AuditEntry` function (similar to `validateShape` in ir/serialization.ts) that checks all required fields exist and have correct types before casting. |
| M-03 | audit/storage.ts | L124, L134 | **Unsafe `JSON.parse` casts in `loadChain`** -- both `JSON.parse(headerLine) as ChainFileHeader` and `JSON.parse(line) as AuditEntry` trust file contents without runtime validation. A tampered chain file could have entries with wrong shapes. This is the storage boundary -- the same concern as M-02 but for the main chain file. For a security-critical audit chain, deserializing without validation undermines tamper-evidence. | Add runtime shape validation for both `ChainFileHeader` and `AuditEntry` before casting. Reuse the same `validateAuditEntry` from M-02. |
| M-04 | ir/serialization.ts | L49-85 | **`validateShape` is shallow -- asserts `OCWorkspaceIR` but only checks top-level field presence** -- the type assertion `asserts value is OCWorkspaceIR` claims the value conforms to the full OCWorkspaceIR interface, but validation only checks that sub-IR fields are non-null objects and compiler metadata has the right primitive types. It does not validate any sub-IR structure (e.g., `SoulIR.persona` is a string, `ToolsIR.tools` is an array). A JSON blob like `{ soul: { garbage: true }, ... }` would pass validation and be typed as a valid `OCWorkspaceIR`. | Either (a) deepen validation to check at least the required fields of each sub-IR (persona, tools array, etc.), or (b) rename the function and weaken the assertion to `asserts value is Record<string, unknown>` and add a separate deep-validation pass, so the type assertion does not overstate what was checked. |
| M-05 | sidecar/resolver.ts | L306-314 | **`enforcement` field cast is unsound** -- `entry['enforcement'] as 'full' | 'advisory' | 'none'` casts any string to the enforcement union without validating the value. A sidecar file with `enforcement: "yolo"` would be silently accepted as a valid enforcement mode. | Add a validation check: `if (['full', 'advisory', 'none'].includes(entry['enforcement']))` before the cast. |
| M-06 | enforce/r5.ts | L10-13 | **`enforceR5` signature diverges from pulse plan** -- the pulse plan specifies `enforceR5(analysis: GovAnalysis, workspace: OCWorkspaceIR)` (2 params), but the implementation takes 3 params: `(analysis: GovAnalysis, conflicts: ConflictReport, workspace: OCWorkspaceIR)`. Similarly, `compileGuard` takes 3 params instead of the pulse plan's 2. The ConflictReport is a separate import from a different IR module. This is a signature correctness issue -- downstream callers coded against the plan will fail to compile. | Either update the pulse plan to reflect the 3-param signature, or fold conflict checking into the `GovAnalysis` type so the function signature matches the plan. The 3-param version is arguably better design, but it must be documented. |

### Warning (W)

| # | File | Line/Section | Finding | Suggested fix |
|---|------|-------------|---------|---------------|
| W-01 | ir/field-types.ts | L20 | **`TrustLevel` is a numeric union `0 | 1 | 2 | 3 | 4` -- not branded** -- any plain number literal 0-4 satisfies this type. A `TrustLevel` value can be accidentally mixed with other numeric values (array indices, enum ordinals, port numbers). Branding would prevent `const x: TrustLevel = someArray.length as TrustLevel`. | Consider branded type: `type TrustLevel = 0 & { readonly __brand: 'TrustLevel' } | 1 & { readonly __brand: 'TrustLevel' } | ...` or at minimum keep the numeric union but add a runtime validation function `isTrustLevel(n: number): n is TrustLevel`. |
| W-02 | ir/workspace-ir.ts | L55 | **Name collision: `ToolDeclaration` defined in both `readers/types.ts` (L105) and `ir/workspace-ir.ts` (L55)** -- the two types have different shapes (IR version has `trustLevel`, `oboFlag`; reader version does not). Both are exported from their barrel files. Consumers importing from both modules will get ambiguous references requiring explicit path imports. | Rename one: e.g., `ToolDeclarationIR` in workspace-ir.ts to distinguish from the reader's `ToolDeclaration`. Same issue exists for `AgentDefinition` (readers/types.ts L121 vs workspace-ir.ts L97), `MemoryEntry` (readers/types.ts L139 vs workspace-ir.ts L130), `HeartbeatSchedule` (readers/types.ts L177 vs workspace-ir.ts L211), `SkillMetadata` (readers/types.ts L193 vs workspace-ir.ts L239), and `LobsterStep` (readers/types.ts L211 vs workspace-ir.ts L265). Six name collisions total across readers and IR. |
| W-03 | sidecar/types.ts | L29 | **`trustTier` in `SidecarOverrides` is `number` -- unbounded** -- the field accepts any number, but trust tiers are 1-5 (per the comment). A sidecar with `trustTier: 999` or `trustTier: -1` would be accepted. | Use a union type: `trustTier?: 1 | 2 | 3 | 4 | 5` or at minimum add validation in `validateSidecar`. |
| W-04 | audit/types.ts | L11-28 | **AuditEntry lacks branded IDs** -- `chainId` (string), `hash` (string), `previousHash` (string | null), and `signature` (string) are all plain strings. A `hash` value could be accidentally assigned where a `signature` is expected, or vice versa. For a security-critical module, these should be distinguishable at the type level. | Introduce branded string types: `type AuditHash = string & { readonly __brand: 'AuditHash' }`, `type Ed25519Signature = string & { readonly __brand: 'Ed25519Signature' }`, `type ChainId = string & { readonly __brand: 'ChainId' }`. |
| W-05 | ir/workspace-ir.ts | L313-336 | **`OCWorkspaceIR` sub-IR fields are not optional -- missing files cannot be represented** -- all 9 sub-IR fields (`soul`, `tools`, etc.) are required in `OCWorkspaceIR`. But the reader layer (OCWorkspaceModel) models each as `WorkspaceReadResult<T>` (success/failure union), and many files are optional. The IR type forces all 9 to be present, meaning the mapper from reader results to IR must synthesize placeholder values for missing optional files. This creates a type-level gap: the IR pretends every file exists when the workspace may not have AGENTS.md, MEMORY.md, etc. | Make optional file IR fields `T | null` or `T | undefined` to honestly represent absence: `readonly agents: AgentsIR | null;` for the 7 optional files (all except SOUL.md and TOOLS.md which are required). |
| W-06 | normalize.ts | L13-19 | **Dead constants: `UTF8_BOM`, `UTF16_LE_BOM`, `UTF16_BE_BOM` are declared but never used** -- the `stripBOM` function works by checking `charCodeAt(0)` against numeric values directly. The three declared constants exist only as documentation. TypeScript will compile them but tree-shaking may not eliminate them. | Either use the constants in the function body (`if (input.charAt(0) === UTF8_BOM)`) or remove them and keep the numeric checks with inline comments. |
| W-07 | sidecar/resolver.ts | L324 | **`targets: targets as SidecarPlatformTarget[]` loses readonly** -- the validated `targets` array was `readonly` in the `ClawsSidecar` interface, but the cast here is to a mutable `SidecarPlatformTarget[]`. This briefly opens a mutation window before the object is returned. | Cast to `readonly SidecarPlatformTarget[]` or use `as const` assertion to preserve immutability through the validation boundary. |
| W-08 | audit/chain.ts | L44-48 | **Private fields `privateKey` and `publicKey` are stored as plain strings in memory** -- for a security-critical class, key material held in memory as unprotected strings can be exposed via heap dumps, debugger inspection, or process memory reads. | Consider using `KeyObject` from Node.js crypto (via `createPrivateKey`/`createPublicKey`) instead of raw PEM strings, which at least signals intent and enables future protection. This is a defense-in-depth note. |
| W-09 | readers/types.ts | L75-82 | **`WorkspaceReader<T>` interface: `filePath` is `string` but skills reader handles a directory** -- `filePath` suggests a single file, but `skillsReader` sets it to `'skills/'` (a directory path). The type does not distinguish file vs directory readers, meaning consumers cannot know the semantic meaning of `filePath`. | Either rename to `targetPath` or add a `readonly kind: 'file' | 'directory'` discriminant to the interface. |

## Summary

The CP-1 type system is well-structured: discriminated unions (`WorkspaceReadResult`, `SidecarResolveResult`, `FailClosedResult`) are properly designed with `ok`/`found` discriminants, all interfaces use `readonly` modifiers, and there is zero `any` usage. The major concerns are: (1) deserialization boundaries in audit/storage and audit/wal lack runtime type validation, creating type assertion holes at security-critical persistence boundaries (M-02, M-03, M-04); (2) six name collisions between reader data types and IR types will cause import ambiguity downstream (W-02); and (3) the `enforcement` field in sidecar overrides accepts any string value through an unsound cast (M-05).
