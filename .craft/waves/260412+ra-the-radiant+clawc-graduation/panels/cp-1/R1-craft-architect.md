## Findings

### Major (M)

| # | File | Line/Section | Finding | Suggested fix |
|---|------|-------------|---------|---------------|
| M-01 | readers/types.ts + ir/workspace-ir.ts | types.ts:105,121,139,177,193,211 / workspace-ir.ts:55,97,130,211,239,265 | **6 type name collisions between readers and IR barrel exports.** Both `compiler/readers/index.ts` and `compiler/ir/index.ts` export identically-named types: `ToolDeclaration`, `AgentDefinition`, `MemoryEntry`, `HeartbeatSchedule`, `SkillMetadata`, `LobsterStep`. These are structurally different types (reader types are flat parsed data; IR types carry trust levels, source refs, sensitivity, etc.). Any consumer importing from both modules gets a namespace collision. This is an architectural violation -- two sibling modules in the same package must not export ambiguous names. | Prefix or suffix the IR types: `ToolDeclarationIR`, `AgentDefinitionIR`, `MemoryEntryIR`, `HeartbeatScheduleIR`, `SkillMetadataIR`, `LobsterStepIR`. Alternatively, use distinct names that reflect the richer IR semantics (e.g. `ToolSpec`, `AgentSpec`). The reader types are the "parsed" layer and should keep the simpler names. |
| M-02 | enforce/r5.ts | Line 182 | **`enforceR5` function signature diverges from pulse plan.** Pulse 06 specifies `enforceR5(analysis: GovAnalysis, workspace: OCWorkspaceIR)` (2 params). The implementation takes 3 params: `(analysis: GovAnalysis, conflicts: ConflictReport, workspace: OCWorkspaceIR)`. The same divergence affects `compileGuard`. This is technically a reasonable design decision (ConflictReport is a separate concern), but it means the function contract differs from the planned API surface, which will propagate to downstream consumers. | Update the pulse plan to reflect the 3-param signature, or fold ConflictReport access into GovAnalysis so the API matches the plan. The 3-param design is architecturally cleaner (separation of concerns), so updating the plan is the preferred fix. |
| M-03 | crypto/keys.ts | Lines 32-38 | **Private key file written with no file permission restrictions.** `writeFileSync` uses default permissions (typically 0o644 on POSIX), meaning the Ed25519 private key PEM file is world-readable. This is a security-impacting architectural gap -- private keys MUST be written with restricted permissions (0o600). | Add `{ mode: 0o600 }` to the `writeFileSync` call for `privateKeyPath`. On Windows, rely on the parent directory ACL (mkdir already handles this), but set the mode for cross-platform correctness. |

### Warning (W)

| # | File | Line/Section | Finding | Suggested fix |
|---|------|-------------|---------|---------------|
| W-01 | sidecar/resolver.ts | Line 18 | **Sidecar module imports from sibling readers module.** `resolver.ts` imports `normalizeFileContent` from `../readers/normalize.js`. This creates a dependency arrow from sidecar -> readers, which is acceptable per the pulse plan (P02 depends on P01), but `normalize.ts` is a general utility, not reader-specific logic. A future refactor that moves readers will break sidecar. | Consider extracting `normalize.ts` to a shared `compiler/util/` or `compiler/common/` module that both readers and sidecar import from. This would make the dependency explicit and prevent coupling between two peer modules. |
| W-02 | audit/storage.ts | Lines 37-54 | **File locking uses `{ flag: 'wx' }` without stale lock detection.** If a process crashes while holding the lock, the `.lock` file persists and blocks all future writes. There is no PID staleness check, no timeout, and no force-unlock mechanism. For a single-workspace local tool this may be tolerable, but it will cause operational failures in practice. | Add stale lock detection: read the PID from the lock file, check if the process is still alive (`process.kill(pid, 0)` on POSIX), and reclaim if dead. Alternatively, use advisory locking (`flock`-style) via `fs.open` with `O_EXCL` and a PID heartbeat. |
| W-03 | readers/skills-reader.ts | Lines 96-106 | **Skills reader scans subdirectories sequentially with `for...of` + `await`.** Each skill subdirectory triggers a serial I/O call. For workspaces with many skills this becomes a bottleneck. The workspace-reader.ts correctly uses `Promise.all` for the 9 top-level reads, but this inner loop does not. | Use `Promise.all(subdirs.map(...))` for parallel skill file reads, matching the parallel pattern in workspace-reader.ts. |
| W-04 | readers/lobster-reader.ts | Lines 27-115 | **Hand-rolled YAML parser with no error recovery.** The minimal YAML parser handles only the known lobster.yaml schema, which is acceptable per the module doc comment, but it silently ignores malformed lines (`continue` on unrecognized patterns). A corrupted lobster.yaml could parse without any diagnostics, returning partial data as if valid. | Add a diagnostic for unrecognized lines (severity: warning) so the user knows the parser skipped content. This preserves the minimal approach while surfacing potential issues. |
| W-05 | sidecar/resolver.ts | Lines 99-240 | **Hand-rolled YAML parser in sidecar resolver duplicates pattern from lobster-reader.** Both lobster-reader.ts and resolver.ts contain bespoke YAML parsers with similar structure (state-machine line walking, key:value extraction). Two independent YAML parsers in the same checkpoint increases maintenance surface and divergence risk. | Extract a shared minimal YAML parser into `compiler/common/yaml-lite.ts` that both modules use. The parser only needs to handle the restricted schema each module requires (top-level scalars, arrays, 2-level maps). |
| W-06 | audit/chain.ts | Lines 130-137 | **`AuditChain.load()` accepts entries without verification.** The load method pushes entries into the internal array without verifying the hash chain or signatures. A corrupted storage file could load invalid entries that silently poison the chain. Consumers must remember to call `verifyChain` after `load`. | Either run verification inside `load()`, or rename to `loadUnverified()` to make the risk explicit in the API name. |
| W-07 | enforce/r5.ts + guard.ts | Lines r5.ts:11-14, guard.ts:10-12 | **Enforce module imports from `../../ir/` (outside `compiler/`).** The enforce module imports `GovAnalysis` and `ConflictReport` from `src/ir/`, which is outside the `src/compiler/` subtree. While these are claws-sdk-internal types (not external packages), this creates an upward dependency from the new `compiler/` tree to the pre-existing `ir/` tree. If `compiler/` is ever extracted as a separate package, these imports become cross-package. | Acceptable for now -- these are type-only imports from the same package. Flag for future extraction: when `compiler/` becomes its own package, these types will need to be passed in or re-exported. |

## Summary

CP-1 infrastructure is architecturally solid: module isolation is clean, dependency direction flows correctly (readers -> IR, crypto -> audit, enforce uses workspace IR + governance IR), barrel exports are curated (no `export *`), and there are zero imports from `@craftworks/compiler-sdk` or `@craftworks/agent-sdk`. The 3 major findings need attention before CP-2: M-01 (6 type name collisions between readers and IR) will cause import ambiguity for any module that consumes both, M-02 (API signature divergence from plan) should be reconciled, and M-03 (private key written world-readable) is a security gap. The warnings are quality improvements that should be addressed during the wave but do not block the next checkpoint.
