## Findings

### Major (M)

| # | File | Line/Section | Finding | Suggested fix |
|---|------|-------------|---------|---------------|
| M1 | crypto/keys.ts | L37 | **Private key written with default permissions (0o666 on POSIX).** `writeFileSync(paths.privateKeyPath, keypair.privateKey, 'utf-8')` creates the private key PEM file with umask-default permissions (world-readable on most systems). Ed25519 private keys must not be readable by other users. | Write with restrictive permissions: `writeFileSync(paths.privateKeyPath, keypair.privateKey, { encoding: 'utf-8', mode: 0o600 })`. On Windows this is a no-op but establishes the correct cross-platform contract. |
| M2 | sidecar/types.ts | L27-30 | **`skipRules` and `enforcement: 'none'` in SidecarOverrides can bypass R5 fail-closed.** The sidecar file is user-controlled input. If a consumer of `ClawsSidecar` applies `skipRules` or `enforcement: 'none'` without gating them to the paid tier, the free-tier R5 guarantee is violated. The types allow arbitrary rule skipping and advisory/none enforcement mode with no tier check. | Add validation in `validateSidecar()` that rejects `skipRules`, `enforcement: 'advisory'`, and `enforcement: 'none'` when running in free-tier mode. Alternatively, strip these fields during validation so they never reach downstream consumers. The free-tier resolver should never emit a `ClawsSidecar` with these override fields populated. |
| M3 | sidecar/resolver.ts | L298 | **`policyDir` field passes through unvalidated -- path traversal vector.** The `.claws` sidecar file is untrusted user input. `policyDir` is accepted as an arbitrary string with no path traversal validation. A `.claws` file containing `policyDir: "../../../../etc/shadow"` or `policyDir: "..\\..\\windows\\system32"` would be accepted. When a downstream consumer resolves this path relative to the workspace root, it escapes the workspace boundary. | Validate `policyDir` does not contain `..` segments, does not start with `/` or a drive letter, and resolves to a path within the workspace root. Reject or normalize to prevent traversal. Example: `if (policyDir.includes('..') \|\| path.isAbsolute(policyDir)) throw new SidecarValidationError(...)`. |
| M4 | sidecar/resolver.ts | L312 | **`skipRules` array elements not validated.** `entry['skipRules'] as string[]` casts without verifying each element is actually a string. A crafted JSON `.claws` file could inject non-string values (objects, arrays, numbers) into the skipRules array. These would survive the cast and propagate downstream. | Validate each element: `entry['skipRules'].every(r => typeof r === 'string')` before accepting the array. |
| M5 | audit/chain.ts | L130-137 | **`load()` accepts entries without verification.** The `load()` method pushes entries into the chain with no hash chain validation, no signature check, and no index continuity check. An attacker who can modify the chain storage file can inject fabricated entries that the AuditChain accepts unchecked. The `verifyChain()` function exists but is not called during load. | Call `verifyChain()` on the loaded entries before accepting them, or at minimum verify hash chain continuity and index ordering. Alternatively, document that callers MUST verify before loading (and enforce this contract with a `verified: true` flag parameter). |

### Warning (W)

| # | File | Line/Section | Finding | Suggested fix |
|---|------|-------------|---------|---------------|
| W1 | crypto/ed25519.ts | L55-57 | **Ed25519 verify does not use constant-time comparison.** Node.js `crypto.verify()` returns a boolean and internally uses constant-time comparison for the signature, but the function caller compares the boolean result with `===` which is fine. However, `ed25519Verify` is the only public verify function and it relies solely on Node's `crypto.verify()` internals for timing safety. The HMAC module correctly uses `timingSafeEqual`, but the Ed25519 module does not document this reliance. | Add a code comment documenting that `crypto.verify()` for Ed25519 is internally constant-time (verified in Node.js source). This makes the security property explicit for future auditors. |
| W2 | audit/storage.ts | L37-54 | **File-based locking is not crash-safe.** The `acquireLock()` / `releaseLock()` pattern uses a `.lock` file with `wx` flag. If the process crashes between `acquireLock()` and `releaseLock()`, the lock file is orphaned and all subsequent operations on that chain file will fail with "Audit chain file is locked." There is no stale-lock detection (e.g., checking if the PID in the lock file is still alive). | Add stale-lock detection: read the PID from the lock file, check if the process is still running. If not, remove the stale lock. Alternatively, use a lock timeout. This is especially important on Windows where process crashes are more likely to leave stale locks. |
| W3 | audit/wal.ts | L84 | **WAL recovery trusts parsed JSON without validation.** `JSON.parse(trimmed) as AuditEntry` in `recover()` deserializes WAL entries without any shape validation. A corrupted or tampered WAL file could inject entries with missing fields (no hash, no signature) that propagate into the chain. The WAL file is local but writable by the user or another process. | Validate the shape of each recovered entry: verify required fields (index, hash, signature, previousHash, timestamp, action, subject, payload) exist and have expected types before casting. |
| W4 | sidecar/resolver.ts | L313 | **`trustTier` not bounds-checked.** `trustTier` is accepted as any number (NaN, Infinity, negative, fractional). Valid trust tiers are 1-5 (per `SidecarOverrides` comment). A `.claws` file with `trustTier: 999` or `trustTier: -1` would pass validation. | Validate: `typeof entry['trustTier'] === 'number' && Number.isInteger(entry['trustTier']) && entry['trustTier'] >= 1 && entry['trustTier'] <= 5`. |
| W5 | sidecar/resolver.ts | L314 | **`enforcement` value not validated against enum.** The cast `entry['enforcement'] as 'full' \| 'advisory' \| 'none'` does not verify the string is one of the three allowed values. Any string passes through. | Add: `['full', 'advisory', 'none'].includes(entry['enforcement'])` guard before accepting. |
| W6 | readers/read-file.ts | L27 | **No path traversal guard on `relativePath`.** `readWorkspaceFile()` accepts `relativePath` and joins it to `workspaceRoot` using `path.join()`. While the 9 readers use hardcoded file paths, the function is exported and callable with arbitrary paths. A path like `../../etc/passwd` would escape the workspace. | Add a guard: after `join()`, verify the resolved path starts with (is a child of) `workspaceRoot`. Alternatively, make this function non-exported (internal to the readers module). |
| W7 | readers/skills-reader.ts | L97-104 | **Skills directory enumeration has no depth limit.** `readdir(skillsDir)` returns all entries in the `skills/` directory. Each entry is treated as a subdirectory containing `SKILL.md`. There is no check that the entry is actually a directory (not a symlink to another location). A malicious workspace could include a symlink `skills/evil -> /etc/` causing reads outside the workspace boundary. | Add `stat()` check on each subdir entry before reading `SKILL.md`. Or use `readdir(skillsDir, { withFileTypes: true })` and filter to directories only (which is more efficient and avoids symlink-following issues). |
| W8 | audit/storage.ts | L113-115 | **Error messages expose absolute file paths.** `loadChain()` and `saveChain()` include absolute file paths in error messages: `"Audit chain file not found: /absolute/path/to/.claws/audit-chain.ndjson"`. In a hosted/cloud deployment, these paths reveal server-side directory structure. | Use workspace-relative paths in user-facing error messages. Store the absolute path only in a non-enumerable property for debug logging. |
| W9 | sidecar/resolver.ts | L364-367 | **Parse error messages expose filesystem paths and parser internals.** `SidecarValidationError` includes the full absolute path and the raw parser error message: `"Failed to parse C:\\Users\\x\\.claws as YAML: unexpected token at line 3"`. | Redact absolute paths to workspace-relative paths in the error message. Keep the absolute path in the `SidecarValidationError.path` property for programmatic access only. |
| W10 | enforce/errors.ts | L17 | **Violation context may expose internal file paths.** `formatViolation()` includes `v.context` verbatim. Context strings from `r5.ts` include file paths and line numbers: `"File: SOUL.md, line: unknown"`. While these are workspace-relative today, the field is stringly-typed and there is no sanitization if a future caller includes absolute paths. | Consider a `sanitizePath()` utility that strips any non-workspace-relative prefix from context strings before formatting. |

## Summary

The CP-1 infrastructure is architecturally sound -- zero supply-chain leakage, correct use of Node.js crypto primitives (no homebrew), and the R5 fail-closed enforcement is genuinely non-bypassable in code. The 5 Major findings center on: (1) private key file permissions, (2) sidecar override fields (`skipRules`, `enforcement`, `policyDir`) that can bypass free-tier guarantees if not gated, (3) path traversal in `policyDir`, (4) unvalidated `skipRules` array elements, and (5) `AuditChain.load()` accepting unverified entries. The 10 Warnings identify input validation gaps (trustTier bounds, enforcement enum, WAL shape validation), path traversal vectors in the reader layer, stale lock handling, and information leakage in error messages. Recommended priority: fix M1-M5 before CP-2, address W2/W3/W4/W5/W6/W7 in the same checkpoint.
