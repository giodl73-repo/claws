# R1 Craft Dragon Review -- claws-tui Plan

**Reviewer**: craft/dragon (invariant rigor > feature velocity)
**Review type**: plan (pre-implementation design review)
**Round**: 1
**Date**: 2026-04-15
**Scope**: `claws-tui` plan -- TUI sends PATCHes to `claws serve`, renders governance state, demo mode fixture workspace

---

## Findings

### Critical (C)

| ID   | Location                                                    | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| C-01 | Plan section "Demo Mode"                                    | **Demo mode fixture workspace is writable by default -- TUI user can mutate governance state of the demo to produce a "clean governance" screenshot that misrepresents R5 enforcement.** The plan says `claws tui --demo` starts with a "pre-loaded fixture workspace" containing R5 tools and fleet locks. But the plan does not specify whether the fixture is read-only (copied to a temp dir and made immutable) or writable. If the TUI's demo mode points `claws serve` at the fixture workspace directly and `claws serve` accepts PATCHes that write to OC files, a user can edit the fixture's TOOLS.md to remove the R5 tool declaration entirely, recompile, and get a governance-clean state. This bypasses R5 enforcement by editing the source-of-truth, not by circumventing the validation layer. **The fixture must be: (a) copied to a temp directory on each `--demo` launch, (b) verified against a known-good hash before serving, and (c) discarded on exit.** Without this, the demo is a governance bypass vector. |
| C-02 | Plan "TUI Interactions" table, row "Try to disable R5 tool" | **Plan does not specify whether the TUI renders R5 lock fields as disabled controls or merely styled differently -- a cosmetic-only lock is bypassable.** The plan says `<LockIcon>` renders a lock with source tooltip, and `<ToolRow>` has a toggle. But the plan never states that the toggle component for R5-locked tools must be a **non-interactive element** (not a disabled button -- a structurally non-toggleable component). Ink's `<SelectInput>` and custom toggle components can be "visually disabled" via styling but still respond to keyboard input. If the toggle is a standard Ink toggle with a `disabled` prop, a user could potentially override it via raw stdin injection or by patching the React component tree. **The invariant**: R5 tools must render as **read-only text** with no toggle component in the DOM at all. The toggle should not exist for R5 items -- not disabled, absent.                                                                                                                   |

### Major (M)

| ID   | Location                                                                 | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M-01 | Plan "Package Location" section                                          | **TUI trusts the server's lock fields without client-side re-validation -- a malicious or buggy server could serve `lock.source: 'none'` for R5 tools and the TUI would render them as toggleable.** The plan states `claws-tui/` is a "consumer of `claws serve`, not part of it" and depends on `@bic/claws-sdk` for "types only." This means the TUI imports type definitions but does no runtime governance validation. If a modified `claws serve` (or a man-in-the-middle on localhost) returns a chunk where an R5 tool has `lock.source: 'none'`, the TUI will render it as editable. **Fix**: The TUI must import the `RuleLevel` type and apply a client-side invariant: any tool with `risk.level === 5` must be rendered as locked regardless of what the server sends for `lock.source`. This is defense-in-depth, not duplication -- the server enforces on PATCH, but the client must not offer a UI path that the server will reject.                                                                                                   |
| M-02 | CL-10 spec "Lock Enforcement" + Plan "SSE live updates"                  | **SSE event stream (plan H2) and WebSocket event stream (current server) have no authentication -- any process on the machine can subscribe and receive governance state changes including compilation results, violation counts, and risk shifts.** The current `claws-serve` WebSocket at `/ws` validates Origin headers for browser contexts but has zero authentication. The plan proposes SSE at `/api/events` with the same model. On a multi-user machine or a machine with untrusted software, any local process can connect to `http://127.0.0.1:3939/ws` or `/api/events` and passively observe governance changes. This leaks: which tools are R5, when compilations happen, violation counts, and tension state. **Fix**: At minimum, the plan must specify a shared-secret or bearer token for SSE/WS connections (e.g., a random token written to a file readable only by the current user, passed as a query parameter or header). This is consistent with how LSP servers and MCP servers handle local auth.                            |
| M-03 | Plan "PATCH integration" (Pulse 4) + CL-10 "Write-Time Validation Layer" | **The plan does not address PATCH request body validation beyond what the server does -- a TUI user with `curl` or a modified TUI binary can craft arbitrary PATCH payloads that the plan's UI would never produce.** The plan focuses on the TUI as the honest client, but `claws serve` listens on a TCP port. Any HTTP client can send a PATCH. The CL-10 spec defines server-side validation (R5 enforcement, fleet locks, governance checks), and this is correct. But the plan's test strategy says "lightly tested (snapshot tests for component rendering)" and relies on the TUI exercising the API to validate the contract. If the TUI only sends well-formed PATCHes, malformed payloads (missing fields, extra fields, type mismatches, oversized arrays, deeply nested objects) are never tested. **Fix**: The plan must include a pulse (or test task in Pulse 4) that exercises malformed PATCH payloads directly against `claws serve` -- not through the TUI. This validates the server's defensive parsing, not just the happy path. |
| M-04 | Plan "Lobster Collaboration Interactions" table, row "Edit soul section" | **SOUL.md deny rule removal through the TUI's soul editor could weaken governance without the TUI distinguishing compiler-injected vs. user-authored deny rules.** CL-10 spec (P-277) defines deny rule provenance: `compiler-injected` rules are immutable, `user-authored` rules produce a warning on removal. The plan's soul editor screen says "Compiler-injected rules shown as locked" but does not specify how the TUI determines provenance. If the TUI renders deny rules based solely on the `governance.denyRules` count from the chunk without per-rule provenance tags, the user cannot distinguish which rules are safe to edit. **Fix**: The `GET /api/loop/soul` response must tag each section's deny rules with provenance (`compiler-injected` vs `user-authored`), and the TUI must render compiler-injected rules as non-editable sections (same principle as C-02: absent, not disabled).                                                                                                                                        |
| M-05 | Plan "Policy violation interactions" table, row "Trigger risk drift"     | **Risk drift detection depends on external file editing triggering a recompile, but the TUI has no mechanism to verify that the SSE/WS event it receives corresponds to an authentic recompile and not a spoofed event.** The plan shows that editing `TOOLS.md` externally causes a risk drift event. The TUI subscribes to SSE and updates its display. But if a local attacker sends a crafted WebSocket message to the TUI's connection (WebSocket has no message authentication), they could inject a fake `compile:complete` event showing zero violations, causing the TUI to display a false "clean" governance state while the actual workspace has R5 violations. **Fix**: The TUI must re-fetch the chunk via GET after receiving any SSE/WS event that indicates a state change, and compare the fetched state against the event payload. The event is a notification to refresh, not a source of truth.                                                                                                                                    |

### Warning (W)

| ID   | Location                                                    | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---- | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| W-01 | Plan "TUI Components" table                                 | **`<ChunkPanel>` is described as "generic" but the plan does not specify input sanitization for rendered chunk data.** Ink renders React components to the terminal via ANSI escape sequences. If a chunk's `data` field contains ANSI escape codes (e.g., in a tool description or SOUL.md instruction text), the TUI will render them as terminal formatting commands. This is a terminal injection vector: a malicious OC file could include escape sequences that reposition the cursor, overwrite displayed lock indicators, or clear the screen. **Fix**: All chunk data rendered by TUI components must be stripped of ANSI escape codes before rendering. Ink provides this implicitly for `<Text>` children but not for all rendering paths. |
| W-02 | Plan "Pulse 8: Demo mode"                                   | **Demo mode fixture includes a HEARTBEAT.md with 3 scheduled tasks but the plan does not validate that the fixture's trust tier (T2) is consistent with the tool permissions in the fixture.** If the fixture declares T2 trust but includes T3-only tools as enabled, the demo shows a governance-inconsistent state. The fixture must be a compilable workspace that passes `claws check` before being used as a demo. **Fix**: Add a build-time validation step: `claws check` on the fixture workspace in CI, failing the build if the fixture has governance violations not intentionally included for demo purposes.                                                                                                                            |
| W-03 | Plan "Test Strategy" section                                | **"Lightly tested (snapshot tests for component rendering)" underspecifies the governance invariant testing surface.** Snapshot tests verify visual output, not behavioral invariants. A snapshot test will not catch a regression where a `<ToolRow>` for an R5 tool gains a click handler that was previously absent. **Fix**: Add behavioral tests (not just snapshots) that assert: (a) R5 tool rows have no toggle handler, (b) fleet-locked fields have no edit handler, (c) PATCH payloads sent by the TUI never include fields with `lock.source !== 'none'`. These are invariant tests, not rendering tests.                                                                                                                                 |
| W-04 | Plan "Package Location" + CL-10 "Compilation Queue (P-273)" | **The TUI can trigger rapid PATCH requests via keyboard repeat, potentially overwhelming the compilation queue.** The plan shows the TUI sends a PATCH for each toggle action. A user holding down the Enter key on a tool toggle could rapidly enqueue PATCHes. CL-10 specifies a compilation queue with max depth 100 and 429 on overflow. But the plan does not specify TUI-side debouncing or optimistic UI updates. Without debouncing, the user sees 429 errors in the TUI, which is a poor experience and could mask legitimate governance rejections. **Fix**: The TUI must debounce PATCH sends (e.g., 200ms after last keystroke) and show optimistic UI state with a "saving..." indicator, reverting to server state on rejection.        |
| W-05 | Plan "Experience 3: Companion App", "Audit Trail" screen    | **The audit trail screen exposes hash chain integrity status but does not specify what the TUI shows when integrity fails.** If `GET /api/audit` returns `auditChainIntact: false`, the plan says the TUI shows a "Hash chain integrity indicator" but does not specify the severity of the UX treatment. A broken audit chain is a governance-critical event (potential tampering). The TUI should render this as a blocking banner, not a subtle icon. **Fix**: Specify that `auditChainIntact: false` triggers a full-screen warning banner in the TUI with the message "Audit chain integrity compromised -- governance state may be tampered" and disables all PATCH interactions until the user explicitly acknowledges.                        |
| W-06 | Plan "Scope" table, "Groups" and "Entitlements" screens     | **Groups and Entitlements are marked read-only but the plan still includes `writeBack` in the Chunk schema for all tabs.** The `Chunk<K>` type has `writeBack?: { method: 'PATCH'; url: string }`. If the server includes `writeBack` on read-only chunks (even accidentally), the TUI might render edit affordances. **Fix**: The TUI must check for `writeBack === undefined` as the authoritative read-only signal. If `writeBack` is present on a chunk that should be read-only (groups, entitlements), the TUI should log a warning and still render as read-only. Do not trust the presence of `writeBack` to determine editability -- cross-check with a hardcoded read-only tab list.                                                        |

## Dragon Lens Checklist

| Question                                                                            | Assessment                                                                                                                                                                                                                                                                                                                   |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Does this change weaken any existing validation or type constraint?                 | **Yes.** The TUI introduces a new client that trusts server lock fields without client-side re-validation (M-01). A buggy server could serve unlocked R5 tools and the TUI would render them as editable. The server-side invariant is preserved, but the defense-in-depth principle requires client-side redundancy for R5. |
| Are error paths still exhaustive after this change?                                 | **Partially.** The plan specifies error rendering for R5 rejections and fleet lock violations, but does not address: malformed server responses, network errors mid-PATCH, SSE/WS disconnection during a PATCH round-trip, or audit chain integrity failures (W-05).                                                         |
| Would reverting this change break any new code that depends on a relaxed invariant? | **No.** The TUI is additive (new package, new command). Reverting it removes the TUI without affecting `claws serve` or `claws-sdk`. No invariants are relaxed by the TUI's existence -- the risk is that the TUI creates an expectation that certain governance states are toggleable when they are not.                    |
| Can the TUI become a backdoor for policy violations?                                | **Yes, in demo mode (C-01).** If the fixture workspace is writable, the demo is a governance bypass. In normal mode, the TUI is a thin client and the server enforces all invariants -- the risk is limited to UI-level confusion (rendering an R5 tool as toggleable even though the PATCH would be rejected).              |
| Is the SSE/WS event stream authenticated?                                           | **No (M-02).** Neither the current WebSocket nor the planned SSE endpoint has any authentication. Any local process can subscribe.                                                                                                                                                                                           |

## Summary

The claws-tui plan is architecturally sound as a thin client consuming the Chunk API. The server-side invariants (R5 fail-closed, fleet locks, write-time validation) are well-specified in CL-10 and are not weakened by the TUI's existence. However, the plan has two critical gaps:

1. **Demo mode fixture governance (C-01)**: The fixture workspace must be ephemeral and hash-verified, or it becomes a governance bypass vector.
2. **R5 toggle rendering (C-02)**: R5 tools must have no toggle component -- not a disabled toggle, an absent toggle.

The major findings center on defense-in-depth: the TUI should not blindly trust server responses for R5 lock state (M-01), the event stream needs authentication (M-02), malformed PATCH testing is missing (M-03), deny rule provenance must be surfaced (M-04), and event payloads should not be treated as source of truth (M-05).

None of these findings require redesigning the TUI. They require tightening the plan's invariant specifications before implementation begins.
