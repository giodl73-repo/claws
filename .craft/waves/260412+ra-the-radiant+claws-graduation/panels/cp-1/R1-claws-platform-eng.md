| M-01 | `package.json` / `tsup.config.ts`          | exports + entry | **5 of 6 new modules have no subpath export or tsup entry point.** Only `compiler/crypto` is wired into package.json exports and tsup entry config. `compiler/readers`, `compiler/sidecar`, `compiler/ir`, `compiler/audit`, and `compiler/enforce` are not reachable by external consumers. | M-02 | `src/compiler/audit/storage.ts` + `wal.ts` | all sync I/O    | **Audit storage and WAL use synchronous blocking I/O (`readFileSync`, `writeFileSync`, `appendFileSync`, `existsSync`, `mkdirSync`, `unlinkSync`) on hot paths.** `saveChain` writes the entire chain file synchronously under a lock; `appendEntry` does sync I/O per audit entry; `AuditWal.write()` calls `appendFileSync` and `mkdirSync` per entry. | M-03 | `src/compiler/audit/storage.ts`            | L37-53          | **File lock implementation is brittle and lacks stale-lock recovery.** The PID-based `.lock` file has no timeout, no staleness check, and no cleanup on process crash. If a process crashes while holding the lock, the lock file persists forever and all subsequent operations fail with "Audit chain file is locked". This is particularly dangerous for fleet operations where a crash in one workspace blocks all future audit writes.                                                                                                                                                                                                             | Add lock staleness detection (check if PID in lock file is still alive), a configurable lock timeout, and automatic stale lock cleanup. Consider using `proper-lockfile` or implementing advisory locking with `flock`-style semantics.                                                                                                     |
| M-04 | `src/compiler/enforce/r5.ts` + `guard.ts`  | L11-12, L10-11  | **Enforce module has cross-module dependency on `../../ir/gov-analysis.js` and `../../ir/conflict-report.js` (the pre-existing top-level `src/ir/` module).** This creates a tight coupling between the new `compiler/enforce/` and the old `src/ir/` module. The enforce module also takes `ConflictReport` as a separate parameter, diverging from the pulse plan spec which shows `enforceR5(analysis: GovAnalysis, workspace: OCWorkspaceIR)` (2 params, not 3). | Either copy the needed types into `compiler/enforce/types.ts` (same pattern as the other 5 modules which are dependency-free), or re-export them through `compiler/ir/index.ts` so the dependency path is `../ir/` not `../../ir/`. For extraction readiness, copying is preferred since the goal is zero external dependencies per module. |

## Summary

CP-1 infrastructure is well-structured with clean module separation, good TypeScript typing discipline, and correct cross-platform path handling. The four major findings are: (1) 5 of 6 new modules are missing package.json exports and tsup entry points, making them unreachable to external consumers -- this is a packaging blocker for graduation; (2) the audit module uses synchronous blocking I/O on hot paths which will block the event loop during fleet operations; (3) the file lock implementation lacks stale-lock recovery, creating a fleet-scale availability risk; (4) the enforce module has a cross-module dependency on `src/ir/` that will break during package extraction. The type naming collisions (W-01) and platform identifier divergence (W-04) should be resolved before downstream pulses build on these APIs.
