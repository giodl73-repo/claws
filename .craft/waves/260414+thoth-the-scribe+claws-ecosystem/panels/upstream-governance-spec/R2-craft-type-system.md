## R1 Finding Resolution

| R1 ID | Status             | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

| M1    | RESOLVED           | AuthorizationDecision is now a 4-variant discriminated union (`AllowDecision \| DenyDecision \| ReviewDecision \| ModifyDecision`) on the `decision` field. `DenyDecision.reason` is required (non-optional). `ModifyDecision.modifiedArguments` is required (non-optional). `AllowDecision` has optional `requiresExternalApproval`. `ReviewDecision` has `requiresExternalApproval: true` (literal). Each variant carries only its valid fields. Invalid combinations like `{ decision: 'allow', modifiedArguments: {...} }` are now compile errors. Exactly what was requested.                                                                                                                      |
| M2    | RESOLVED           | `AuditableResult` is now `ExecutedResult \| BlockedResult`, discriminated on `executed: true \| false`. `ExecutedResult` requires `output: unknown`. `BlockedResult` requires `blockReason: string`. Both share `decision`, `durationMs`, and `timestamp`. Mutual exclusivity of `output` and `blockReason` is enforced by the type system.                                                                                                                                                                                                                                                                                                                                                             |
| M3    | RESOLVED           | `ToolCall.context` is now a typed struct with no index signature: `{ conversationId: string; agentId?: string; workspaceId?: string }`. Host-specific data goes through a separate `extensions?: Record<string, unknown>` field on `ToolCall` itself, mirroring the `ApprovalRequestEvent.extensions` pattern suggested in R1. Typos in context field names are now compile errors.                                                                                                                                                                                                                                                                                                                     |
| M4    | RESOLVED           | `RiskClassification` is now a 5-variant mapped union coupling level to label: `{ level: 1; label: 'read' } \| { level: 2; label: 'write' } \| ... \| { level: 5; label: 'transact' }`. Used in `ApprovalRequestEvent.risk` as `RiskClassification & { reason: string }`. The approval-event-schema.md rationale doc now uses `level: RiskLevel` (not `number`). A `{ level: 1, label: 'transact' }` mismatch is now a compile error.                                                                                                                                                                                                                                                                    |
| W1    | PARTIALLY RESOLVED | The fail-mode table now has an "Unknown / Missing / Invalid" row that reads "No risk classification = treat as R5. Non-negotiable." This addresses the behavioral gap. However, the `RiskLevel` type itself is still `1 \| 2 \| 3 \| 4 \| 5` with no `'unclassified'` variant or sibling `riskClassificationSource` field. The registry composition logic documents that unknown tools are forced to R5, but a consumer receiving `riskLevel: 5` still cannot distinguish genuine R5 from default-R5 at the type level. Acceptable for v1 -- the fail-mode table is the critical fix -- but the provenance gap remains for audit consumers who want to filter "real R5" from "unknown-defaulted-to-R5". |
| W2    | RESOLVED           | `ApprovalTimeoutPolicy` now uses `readonly` on all fields including `readonly alwaysDenyRiskLevels: readonly RiskLevel[]`. The R5 invariant is documented with a JSON Schema `contains: { const: 5 }` enforcement. The ProviderRegistry composition logic hardcodes R5 enforcement in the JSDoc. Mutation is prevented at the type level. The runtime invariant still depends on the constructor or JSON Schema validation, which is the correct pragmatic trade-off.                                                                                                                                                                                                                                   |
| W3    | RESOLVED           | `schemaVersion` in both `ApprovalRequestEvent` and `ApprovalResponseEvent` is now `number`, not a literal `1`. A version negotiation strategy is documented below the type: "Consumers check the version and handle unknown versions gracefully (skip or use a type guard like `isV1(event): event is ApprovalRequestEventV1`). When v2 ships, the type becomes `ApprovalRequestEvent = ApprovalRequestEventV1 \| ApprovalRequestEventV2`." This is the exact pattern suggested in R1.                                                                                                                                                                                                                  |
| W4    | NOT ADDRESSED      | `AuditEvent` in the audit-chain types section (L747-749) is still `{ type: string; [key: string]: unknown }` -- effectively `Record<string, unknown>` with a required `type`. No discriminated union of known event types, no narrowing path. This was a Warning in R1 and remains one. The pragmatic argument is that audit-chain is a generic storage layer and shouldn't constrain event shapes. Acceptable for v1 if the package explicitly documents that event shape validation is the caller's responsibility.                                                                                                                                                                                   |
| W5    | RESOLVED           | `ExportFormat` is now unified as `'sarif' \| 'cef' \| 'json' \| 'ndjson' \| 'syslog'` (L769), shared across both `audit-chain` (export) and `siem-emitter` (live dispatch). | W6    | RESOLVED           | The approval-event-schema.md rationale doc now uses `level: RiskLevel` (L94) with a comment `// RiskLevel = 1 \| 2 \| 3 \| 4 \| 5` and the explicit `RiskLevel` type definition at L183. No more raw `number`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

No more raw `number[]`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

No more dual-identity contradiction.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

The index signature means a consumer cannot narrow on `type` to access event-specific fields. | R2-W2 | openclaw-governance-spec.md | L450 (ShellExecProvider.preAuthorize) | Return type is `Promise<AllowDecision>`. This is correct -- ShellExecProvider can only allow (with or without external approval). But the `GuardrailProvider.preAuthorize()` signature returns `Promise<AuthorizationDecision>`. A provider that narrows its return type is fine in TypeScript (covariant return), but if a consumer stores the result as `AllowDecision` and later the provider is updated to also deny, the consumer's type is wrong. This is a subtyping subtlety, not a bug -- but worth a JSDoc note that reference implementations may narrow the return type for clarity while conforming to the full union contract. |
| R2-W3 | approval-event-schema.md    | L92-101 (risk)                        | The rationale doc's `ApprovalRequestEvent.risk` still has `level` and `label` as independent fields: `level: RiskLevel` (L94) and `label: 'read' \| 'write' \| ...` (L98). The canonical spec couples them via `RiskClassification & { reason: string }` (L531), but the rationale doc does not use `RiskClassification`. An implementor reading only the rationale doc could still construct `{ level: 1, label: 'transact' }`.                                                                                                                                                                                                             | Update the rationale doc's risk block to reference `RiskClassification` explicitly, or add a comment noting the coupling constraint is enforced in the canonical spec.                                                                                                                                                                                                                      |

## Summary

All 4 Major findings from R1 are fully resolved. The rewrite delivers exactly the discriminated union architecture recommended: `AuthorizationDecision` (4 variants), `AuditableResult` (2 variants), and `RiskClassification` (5 variants). The `ToolCall.context` index signature is eliminated. Of the 7 Warnings, 5 are resolved, 1 is partially resolved (W1 -- R5 provenance, acceptable for v1), and 1 is carried forward as R2-W1 (AuditEvent looseness). Three new Warnings surfaced, all low severity: the rationale doc's uncoupled risk fields (R2-W3), the ShellExecProvider return type narrowing (R2-W2), and the AuditEvent carryover (R2-W1). From the type-system lens, this spec is now ready for upstream submission -- the core governance types make invalid states unrepresentable and all narrowing paths are complete.
