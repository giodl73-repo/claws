## Findings

### Major (M)

| ID   | Section                                                 | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M-01 | Chunk API -- `locked: true` enforcement boundary        | **The `locked` field on R5 tools is described as server-enforced (line 860: "locked fields in chunks are server-enforced, not just UX hints"), but the enforcement mechanism is unspecified.** The `editable` record carries `locked: true, lockReason: "R5 tool -- cannot disable approval"` (line 749), and Phase 2 says "PATCH rejects any edit that would disable R5 approval" (line 859). But the spec defines no validation contract: no error response schema, no rejection reason type, no explicit mapping from `locked` fields to validation rules. A partner developer reading the spec sees `locked` as a JSON boolean on a schema field -- there is no formal statement that the server MUST reject a PATCH payload that includes a value for a locked field. Without this, an implementer could treat `locked` as advisory and apply the PATCH, silently bypassing R5. CL-11 is clear that R5 is "non-negotiable, non-configurable" (line 114) at the ProviderRegistry level, but CL-10 must independently enforce this at the PATCH API level because PATCH writes OC files _before_ recompilation. An R5 tool disabled via PATCH would exist in a window where the OC file says "no approval" and the next compilation has not yet run. The invariant must hold at the write boundary, not just the compile boundary. |
| M-02 | PATCH /api/workspace/:file -- governance validation gap | **The PATCH endpoint validates "the edit" (line 557) but the spec does not define which governance rules are checked at write time vs. compile time.** The response example (lines 559-566) shows `governance: { warnings: [], errors: [] }` after recompilation, but this is a _post-hoc_ result. The critical question: what happens _between_ the OC file write and the recompilation? If PATCH writes TOOLS.md to set `requires_approval: false` on an R5 tool, then triggers `claws build`, there is a temporal window where the OC file is in a governance-violating state. If the server crashes or the process is killed between the write and the build, the OC workspace is now durably invalid. The spec must define atomic write+validate semantics: either (a) validate before writing and reject invalid edits, or (b) write to a staging area and promote only after successful compilation. The current design ("writes it, and triggers recompilation") is not fail-safe.                                                                                                                                                                                                                                                                                                                                            |
| M-03 | `pre_authorizations: all` -- R5 bypass vector           | **The "Allow all" button maps to `USER.md` `pre_authorizations: all` (line 69), tagged as `G-ELICIT: blanket standing approval`. The spec does not state whether this blanket approval overrides R5 gating.** CL-11 is unambiguous: R5 requires external approval, non-negotiable, non-configurable. The ProviderRegistry forces `requiresExternalApproval: true` for any R5 tool regardless of what providers return (CL-11 lines 384-389). But `pre_authorizations: all` is an OC-file-level concept that claws compiles into `exec-approvals.json` or `host-approval-policies.json`. If the compiled output says "all tools pre-authorized" and the ProviderRegistry enforces R5 gating, these are two separate enforcement layers that must agree. The spec must explicitly state: `pre_authorizations: all` does NOT override R5 gating. Without this statement, a PATCH that sets `pre_authorizations: all` in USER.md could produce compiled artifacts that conflict with CL-11's R5 invariant, and the conflict resolution is undefined.                                                                                                                                                                                                                                                                                      |
| M-04 | Fleet policy vs. PATCH precedence -- no merge semantics | **If a fleet policy locks a tool (e.g., `approvalSource: "fleet-override"` on `create-task`, line 439), the spec does not define whether PATCH can override it.** The Chunk API includes `fleetOverride: boolean` in the governance context (line 660) and shows a lock icon for fleet-overridden settings, but the write path has no fleet-awareness. The `PATCH /api/chunks/connections/outlook` example (lines 800-809) sends `{ tools: [{ tool: "send-email", enabled: true }] }` with no acknowledgment of fleet state. If fleet policy says "create-task requires approval" and a local admin PATCHes it to not require approval, who wins? CL-11's composition model says "deny > review > modify > allow" across providers, but fleet policy is not a provider -- it is a configuration overlay. The spec must define: (a) fleet-locked fields are rejected at the PATCH level (same as R5 `locked`), or (b) local edits are stored but fleet policy takes precedence at runtime via composition. Without this, the PATCH API is a fleet policy bypass.                                                                                                                                                                                                                                                                       |
| M-05 | PATCH /api/trust/escalate -- missing approval gate      | **The trust escalation endpoint (line 344, line 873) allows `PATCH /api/trust/escalate` from the Companion App, but the spec does not define an approval workflow.** The GET /api/trust response shows `nextEscalation.requirements` includes "Manager approval" with `managerApproved: false` (line 209). But the PATCH endpoint has no request schema -- there is no definition of what the caller sends, what authorization is required, or how manager approval is verified. If the PATCH simply sets the trust tier in AGENTS.md, any Companion App user can escalate from T2 to T3 by calling the API. The trust model describes escalation as earned ("you delegate more as they earn your trust"), but the API has no earning gate. At minimum: the PATCH must require a manager approval token, or the escalation must be a _request_ that a manager approves asynchronously (POST /api/trust/escalation-request), not a direct tier mutation.                                                                                                                                                                                                                                                                                                                                                                               |

### Warning (W)

| ID   | Section                                                 | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |

| W-01 | Lossless round-trip -- PATCH writes OC files            | **claws's core design principle is "NEVER modifies original OC workspace files" (add-only, byte-for-byte round-trip). PATCH endpoints write OC files. This is a tension that the spec acknowledges implicitly but does not resolve explicitly.** The PATCH write path (lines 538-567) modifies TOOLS.md, SOUL.md, IDENTITY.md, MEMORY.md, USER.md, HEARTBEAT.md, and AGENTS.md. The spec says the write is "lossless -- preserves other content" (line 815). But "lossless" in the claws design principle means claws does not modify originals _at all_ -- it reads them and emits separate artifacts. The PATCH API introduces a new role for claws: OC file _author_, not just OC file _compiler_. The spec should explicitly acknowledge this role expansion and define what "lossless" means in the write context (presumably: section-level edits that preserve unmodified sections byte-for-byte). Without this definition, "lossless" means two different things in two specs, which will confuse implementers.                                                                                            |
| W-02 | Loop sync -- deny rule removal not caught at write time | **The Loop sync description (lines 230-233) says edits are "governance-aware: if a Loop edit removes a deny rule from SOUL.md, claws recompiles and surfaces a governance warning." But the warning is post-hoc -- the deny rule is already removed from the OC file.** The PATCH /api/loop/soul (lines 263-269) writes SOUL.md then triggers claws build. If a user edits the "Boundaries" section in Loop to remove "Never send email without approval," the PATCH writes this to SOUL.md, then recompilation produces a warning. But the deny rule is gone. The warning is a notification, not a gate. There is no mechanism to reject the edit, require confirmation, or restore the deny rule. For R5-adjacent deny rules (rules that gate R5 tools), this is an R5 bypass via content editing. The ProviderRegistry still enforces R5 gating at runtime, but the governance _policy_ (the deny rule) is gone from the workspace -- the agent's compiled governance no longer includes the prohibition. Deny rule removal should be a gated operation (confirmation required) for rules that affect R5 tools. |
| W-03 | POST /api/onboard -- unvalidated content injection      | **The onboard API (line 352, lines 883-884) seeds SOUL.md and MEMORY.md from an onboarding conversation transcript. The spec defines no content validation, sanitization, or governance constraint on the seeded content.** A Teams voice call transcript could contain anything -- prompt injection attempts, deny-rule-overriding instructions, or content that, when written to SOUL.md, alters the agent's governance boundary. The spec says "seed files from conversation" but does not specify: (a) what schema the seeded content must conform to, (b) whether the seeded SOUL.md is compiled and validated before being committed to the workspace, (c) whether existing SOUL.md content is preserved or overwritten, (d) what happens if the transcript contains content that would fail governance compilation. For a file that defines the agent's behavioral boundaries, unvalidated writes from conversation transcripts are a governance injection vector.                                                                                                                                          |
| W-04 | Audit trail -- PATCH operations deferred to Phase 2     | **Phase 2 states "every PATCH produces an audit event via @openclaw/audit-chain" (line 861). But the spec also defines PATCH endpoints in Phase 3 (Loop sync, trust escalation) and Phase 5 (onboard). If audit is a Phase 2 concern, Phase 3 and Phase 5 write endpoints risk shipping without audit.** The implementation path separates audit from the endpoints that need it. Audit should be a cross-cutting middleware concern from Phase 1, applied to all write endpoints regardless of which phase introduces them. Otherwise, trust escalation (Phase 3) and onboard (Phase 5) could ship without audit trail, and adding audit retroactively to established endpoints is harder than building it in.                                                                                                                                                                                                                                                                                                                                                                                                    |
| W-05 | Work queue -- no tamper resistance                      | **The work queue (lines 155-183) is a runtime task list served by `GET /api/workqueue`. The spec proposes `WORKQUEUE.md` or a runtime-only concept but defines no integrity model.** If the work queue is an OC file (WORKQUEUE.md), it is editable via the same PATCH mechanism as other OC files -- meaning a user or API caller could add, remove, or modify tasks. If it is runtime-only, the data source is unspecified. In either case, there is no mention of task integrity: (a) can a user silently remove a task assigned by a manager? (b) are task state transitions (pending -> in_progress -> completed) validated? (c) is there an audit trail for task mutations? The work queue bridges governance (HEARTBEAT.md schedules) with runtime state -- task tampering could allow an agent to skip scheduled governance-mandated work (e.g., "Daily inbox triage" with compliance implications).                                                                                                                                                                                                       |

## Summary

CL-10 introduces a write surface (`claws serve` PATCH API) over OC workspace files that contain governance-critical data. The read surface is sound -- the Chunk API is a well-designed partner abstraction, and the implementation path correctly sequences risk. The safety concerns are concentrated entirely in the write path.

**The core issue**: CL-11 defines a robust R5 invariant at the ProviderRegistry (runtime enforcement), but CL-10 introduces an OC-file write API that operates at authoring time, _before_ the ProviderRegistry runs. The spec says "server-enforced" (line 860) and "rejects any edit that would disable R5 approval" (line 859), but these are prose promises with no specified enforcement mechanism -- no validation contract, no error schema, no rejection flow. Five critical invariants (R5 lock, `pre_authorizations: all` scope, fleet policy precedence, trust escalation authorization, deny rule removal gating) are either unspecified or have gaps between the authoring-time write path and the runtime enforcement layer.

The fix is straightforward: define a **write-time validation layer** in the spec that runs before the OC file write, not after recompilation. This layer enforces: (1) `locked` fields are rejected, (2) R5 approval cannot be disabled, (3) fleet-locked fields are rejected, (4) deny rules affecting R5 tools require confirmation, (5) trust escalation requires authorization proof. This validation is the authoring-time analog of CL-11's runtime ProviderRegistry -- without it, the write API is an unguarded door to the governance basement.

M-01 through M-05 should be resolved before write API implementation begins (Phase 2). W-01 through W-05 can be addressed during Phase 2-3 design.
